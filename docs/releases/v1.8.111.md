# v1.8.111 工作台趋势图去重复加载（性能）

## 问题

工作台首页「订单金额走势 / 采购金额走势」要画近 n 期（默认 6 期）曲线，旧实现对**每个期间各调一次 `so_list` / `po_list`**。而 `so_list`/`po_list` 自 v1.8.109 起还会连带把整期间的明细行批量载出来——6 个期间就是 6 次「订单表 + 明细表」整表扫描，只为累加一个 `total_amount`。这是典型的 N+1：订单越多，首页越慢，且扫描的明细绝大多数是白拉的。

## 改法

- `crates/findb/src/scm.rs` 新增两个跨期间汇总函数，一条 `BETWEEN` 扫全、Rust 侧按期间累加（**不在 SQL 里 SUM**——金额列全库按 TEXT 存，SQLite 对 TEXT 的 SUM 返回 Integer/Real 会让 `get::<String>` 报错）：
  - `so_amount_by_period(db, from, to)`：`SELECT period, total_amount FROM sales_order WHERE period BETWEEN ?1 AND ?2`。
  - `po_amount_by_period(db, from, to)`：同款查 `purchase_order`。
- `crates/findb/src/workbench.rs` 的 `collect` 里，销售/采购两条趋势循环改成一次调上述汇总函数（复用已有 `y0`/`y1` 区间），删掉逐期 `so_list`/`po_list`。

## 三条规矩

1. **只动走势、不动卡片**：本期卡片（本期订单金额、份数）仍用当期 `so_list`/`po_list` 的实表（要数份数、判状态），走势只用金额汇总，两者数据源不混。
2. **口径不变**：汇总的是 `total_amount` 列（不含税、含所有状态），与逐期累加完全一致，没有引入「只算已确认单」这类新口径。
3. **不在 SQL 里 SUM 金额**：延续全库约定，金额在 Rust 侧用 `Money` 累加再转 `f64` 画图，`f64` 只用于画图、不参与账务计算。

## 测试与门禁

- findb 新增 `order_amount_by_period_batches_trend_totals`（1 月两张销售单 300、2 月一张 500；采购 1 月 1000、2 月 2000；断言按月汇总、范围外不计入）。
- 变异 136（销售趋势累加写成覆盖，只取每期最后一张单）、137（采购趋势查成销售订单表，金额串了）实跑拦下。
- clippy 0 error、preflight 六步全绿。

## 升级说明

纯后端性能优化，schema 不变、接口不变、界面不变，老账套直接升。工作台首页加载会更快（订单数据越多越明显）。
