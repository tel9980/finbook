# v1.8.42 —— 期初导完之后的那个动作：对账

v1.8.41 让期初能「下载表 → 填 → 预检 → 导入」。这一版补上最后一步：**导完了，账上到底对不对。**

## 为什么不能只看「导入成功」

导入返回 `ok: true` 只证明一件事：文件格式对、借贷平了、数据进了库。它证明不了：

- 台账上有 95,000 应收，`112201` 科目也是 95,000 —— 这两处是两条独立的写入路径，任何一条漏了，报表和账龄表就各说各话；
- 台账上写的客户编码，档案里到底有没有这个客户；
- 资产 115,000 与负债 28,000 + 权益 87,000 是否真的相等。

这三件事**只有导完之后回读库才能回答**。所以对账视图不是「导入的总结」，是一次独立复核。

## 新的接口与入口

| | |
|---|---|
| 接口 | `GET /api/books/opening-sheet/reconcile`（JSON） |
| 网页 | `期初余额` 页工具栏 →「导入后对账」 |
| 模块 | `crates/findb/src/opening_check.rs` |

返回四部分：四张纸各自的落库行数与合计、借贷与资产/负债/权益摘要、六条交叉校验、以及一句「哪里不对」。

**金额一律是字符串**（`fmt_plain`）。对账页上一个千分位错位就能让人怀疑数字算错了，而那只是显示问题。

## 六条校验

| 校验 | 抓的是什么 |
|------|------------|
| 往来台账 ↔ 应收科目余额 | 只导台账没导科目（报表里一分应收都没有） |
| 往来台账 ↔ 应付科目余额 | 同上，应付侧 |
| 期初借贷相等 | 期初凭证 / 手工补录留下的不平 |
| 资产 = 负债 + 权益 | 结构性错位 |
| 往来单位编码都在档案里 | 编码笔误（`C001` 打成 `C999`） |
| 没有重复的期初凭证 | 既导了期初、又录了一张摘要含「期初」的凭证 |

## 这一版自己踩到的坑：亏损被算成收益

写 `资产 = 负债 + 权益` 时，负债和权益「余额方向是贷」，所以数值在库里是**负的**。第一版为了好读，把两者都按绝对值累加：

```rust
let signed = if amt >= Money::ZERO { amt } else { -amt };   // ← 错
```

于是 `4103 本年利润` 有借方余额（= 亏损 67,000）时，权益变成 `87,000 + 67,000 = 154,000`，
而资产只有 `20,000` —— 差得离谱，可那条校验**照样报「通过」**，因为等式两边用的都是错数。

正确写法是按余额方向取反：

```rust
let add = match key {
    "asset" => amt,   // 借正贷负，直接累加
    _ => -amt,        // 负债/权益：贷方为正，所以要取反
};
```

现在亏损会把权益冲小。测试 `reconcile_treats_debit_profit_as_a_loss` 专门钉住这一点：
现金 20,000（借）/ 实收资本 50,000（贷）/ 本年利润 30,000（借），权益必须是 20,000。

## 用模拟数据跑过三遍

`crates/finweb/examples/chk_opening_reconcile.rs` 用真实路径造了一份账（建账 → 建档案 → 生成模板 → 在表里填数 → 导入 → 对账），然后故意制造两种常见错误：

| 场景 | 对账结果 |
|------|----------|
| A 填得对 | 6 项全过，一句话「期初对上了：借方 115,000 = 贷方 115,000」 |
| B 把 `112201` 的期初删掉（只导台账没导科目） | 3 处红：台账 95,000 ↔ 科目 0、借贷不平、资产 ≠ 负债+权益 |
| C 把一条台账的客户编码改成档案里没有的 `C999` | 4 处红，并点名「档案里找不到：C999(鑫盛电器)」 |

场景 B/C 就是老板拿着表问「我这不都填了吗」时，能当场指出是哪一张纸、哪个编码。

## 写测试时被同一类事骗了两次

1. **模板里没有客户行**：`① 客户应收` 是按账套档案预填的，测试账套一个客户都没有时那张纸只有表头 —— 只在「已有的行」上填数，就变成「什么都没填也全绿」。改成**没有就追加一行**，并在断言里要求四张纸都真被填上（`assert_eq!(filled, 4)`）。
2. **`POST /api/aux-batch` 只解析、不落库**：接口回 200，档案一条没有，于是「编码都在档案里」那条校验一直红。真正的写入是 `PUT`，而且必须把 POST 返回的 `rows` 原样带回去（后端刻意不重新解析，避免「确认了 A 写进去 B」）。

两次都是**接口回了成功、事情没做**。这类错误只能靠「断言最终状态」抓，靠「断言返回码」永远抓不到。
