## 唯一值得改的：一次 panic 让登录永久不可用

`RealmDb` 的 40 处写法是 `self.inner.lock().unwrap()`。`Mutex` 有「中毒」语义：
任一处**持锁时 panic**，锁就永久标记为中毒，此后**每一次** `.lock().unwrap()` 都 panic。

在这个项目里这意味着：登录、改密、开号、设备绑定登记 —— 全部失效，只能重启进程。
一次局部 bug 变成永久不可用。改成从毒化里取回内值：

```rust
fn conn(&self) -> MutexGuard<'_, Connection> {
    self.inner.lock().unwrap_or_else(|e| e.into_inner())
}
```

**为什么安全**：这把锁保护的是一条 SQLite 连接，不是「必须完全一致的内存不变量」。
一致性由 SQLite 事务保证，毒化后继续用这条连接不会读到半截事务。

反过来 —— 如果哪把锁保护的是「三步写完才算对」的内存状态，就该保留 `unwrap()`
让它崩，因为崩掉比带着半截状态跑安全。这个区别是这条修改的全部理由。

## 明确不改的三类

- **`scm.rs` 的 `serde_json::to_value(枚举)?.as_str().unwrap()`（10 处）**：枚举序列化
  成字符串必然成功。改成 `unwrap_or_default()` 只会把 panic 换成**静默写空串**，更糟；
  真要改是加 `as_str_or_err() -> DbResult`，那属重构不属修 bug。
- **166 处截断转换**：没有一个碰金额。为消 lint 引入 `try_into()` 会让每处多两行
  错误处理，收益为负。
- **568 条 pedantic**：`too_many_lines`（17 条）指的是 `handlers.rs` 里的巨型函数 ——
  拆它是另一件正经事（按域拆 handler 文件），不该混进「低危项」里偷偷做。
