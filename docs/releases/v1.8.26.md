# v1.8.26 —— 第二轮性能：省掉的每一次全表扫都要有等价性证明

v1.8.25 收尾时留了三项「量过但没动」。这一轮把能动的两项做掉，第三项做的是
**判它不值得做**——并写清理由（见 `docs/功能参考.md` §4.78）。

## 一、首页的「本年累计」不再重扫一遍账

首页要两个数：这个月赚多少、今年累计赚多少。改之前后者是再调一次
`financial_totals(db, cur, 年初, ..)`。看起来只是多调一个函数，实际是**一组全新的
查询键**：余额快照缓存按「期间区间」作键，`cur..cur` 与 `年初..cur` 是两份独立的
快照，等于把整本账又扫了一遍。

其实不用扫——快照里 `ytd_debit / ytd_credit` 本来就是「1 月至本期」的累计发生额，
资产、负债又都是时点数。新增：

```rust
pub fn financial_ytd(db: &Db, period: Period, scope: Option<&User>) -> DbResult<FinTotals>
```

它把 `from` 传成 `period`（查询键与 `financial_totals` 完全一致，必然命中同一份缓存），
只把损益读成 `ytd_*` 列。

**等价性有测试守着**：`financial_ytd_matches_scanning_from_january` 断言本年累计
收入/成本/净利润与「从 1 月再扫一遍」逐项相等、数值本身对（收入 70000、净利 56000）、
时点数与本期那份相同而本期净利只有当月那两笔。变异 ⑲ 把 `Flow::Ytd` 改成读区间列，
这条测试立刻变红。

## 二、快照扫描里最贵的一步，被九成行浪费掉了

剖析数据显示：7ms 的冷快照里，凭证扫描占 6.6ms，SQL 侧只占 2.1ms
（3960 行，含 118 字节的 `aux_json`）。也就是说瓶颈不在数据库，在这层循环的每行工作。

关键在另一组数字：**3960 条分录只落到 44 个（科目, 辅助键）组合上**，而
`serde_json::from_str::<AuxRef>(aux_json)` 写在 `or_insert_with` 之前——每一行都解析
一次，然后九成九的结果被丢掉。把解析挪进「这个键第一次出现」的分支，一次快照省约
1.3ms（占该步的 20%）。

刻意**没有**改用更快的 `AuxRef::from_key(aux_key)`（0.56ms）：`aux_key` 由
`key_parts` 生成，只含 `BALANCE_DIMS`（不含现金流量），而 `aux_json` 是全量。快照读的
是余额口径，眼下用不到现金流量维度，但这是**语义差异**而不是性能差异——为了 0.7ms
把「以后可能有人依赖的字段」悄悄丢掉，不划算。

## 三、静态资源：真正的大头不在服务器，在手机流量

服务器上省 5ms 用户感知不到；但 `app.js` 是 211KB（gzip 后），原来**每次打开都回源
验证**，在移动网络上那是一到两秒。`index.html` 里每个资源都带 `?v={{V}}`，版本号由
静态文件 mtime 推出——内容一变 URL 就变，所以让浏览器一年内不再回源是安全的：

| 请求 | `Cache-Control` | 理由 |
|---|---|---|
| `/app.js?v=1730…` | `public, max-age=31536000, immutable` | URL 随内容变化 |
| `/app.js`（手输直达） | `no-cache` | 没有版本号兜底，必须回源 |
| `/`（首页） | `no-cache` | 它负责注入 `{{V}}`，缓存住等于把旧版本号钉死 |

顺带修掉一个**只有开了长缓存才会致命**的漏洞：`asset_version()` 算版本号时漏了
`icons.js`。以前漏项只是「下次回源就对了」，现在漏项意味着「一直错到别的文件也被改」。

## 实测（release 构建，两年账套 3960 条分录，9 次中位）

| 接口 | v1.8.25 | v1.8.26 | 变化 |
|---|---|---|---|
| `/api/dashboard` | 47.7ms | **40.1ms** | −16% |
| `/api/workbench?periods=12` | 27.3ms | **23.2ms** | −15% |
| `/api/reports/balance-sheet` | 12.8ms | **10.9ms** | −15% |
| `/api/reports/income-statement` | 12.3ms | **10.2ms** | −17% |
| `/api/reports/trial-balance` | 12.0ms | **10.2ms** | −15% |

从 v1.8.24 起算（首页 233ms → 40.1ms），首屏快了 **5.8 倍**。

## 明确判定「不值得做」的两件

- `/api/workbench` 的 23ms 里，与期间数无关的固定成本约 20ms：`collect()` 只占 3.7ms，
  其余是「当期卡片」用的两张完整报表各取一次快照；趋势部分（3 期 → 12 期 → 24 期：
  24.7 / 27.3 / 32.9ms）每期只加约 0.4ms。再优化只能去打「快照本身」（把期间余额做成
  写时维护的汇总表），风险与收益不成比例。
- `app.js` 拆包：开了长缓存之后 211KB 一个版本只下一次，拆包换来的是构建复杂度与
  「少一次请求」之间不划算的交换。

## 测试

`cargo test --workspace` **932** 条全绿（v1.8.25 是 928）：新增 `findb` 1 条
（本年累计等价性）、新文件 `finweb` `tests/static_cache.rs` 3 条（版本化可长缓存 /
无版本号必须回源 / 首页绝不可缓存）。

变异套件 41 → **44** 条，本轮新增 3 条（⑲ 本年累计读成区间发生额、⑲ 版本化静态资源
不再长缓存、⑲ 首页被缓存住），实跑全部被拦下。

## 升级说明

无破坏性变更，无数据库迁移。浏览器首次访问会重新取一次静态资源，之后一年内走本地缓存；
发新版本时版本号随文件 mtime 变化，用户自动拿到新前端。
