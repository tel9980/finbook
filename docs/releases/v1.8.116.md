# v1.8.116 慢查询基准补结账 + 工作台待办加紧迫提示

## 问题

两件小事：① v1.8.114 那套热读基准只测了 4 个读路径（回款看板/账龄/到期月表/工作台），**期末结账 `month_close`** 这类重活没进基准，老板问「结账要多久」时没有数；② 工作台「待开发票」「快到期的应付」两个待办只报个数，老板点进去才知道是催哪张、有多急。

## 改法

- **基准扩面**：`crates/findb/benches/hot_reads.rs` 加 `bench_month_close`（`findb::month_close::report(db, p)`，500 单规模，criterion 0.5 同口径）。跑出 2.98ms。
- **待办加 `detail`**：`WbTodo` 结构体加 `pub detail: String`（空串前端不渲染），`todo()` 保持不变（空 detail），新增 `todo_with_detail()`。「待开发票」detail = 最早发货日（`so_uninvoiced_oldest_ship` 新函数，`MIN(s.date)` 口径同 `so_uninvoiced_count`）；「快到期的应付」detail = 最早到期日（`ap_due_soon_rows` 里 `min(due_date)`）。前端 `app-dashboard.js` 待办按钮与 `app-shell.js` 通知渲染 detail。

## 三条规矩

1. **报数之外给一句话**：`detail` 是「最早发货 2026-06-10」这种紧迫提示，不是又塞一张表；空串不渲染，不影响原有待办。
2. **口径不劈叉**：`so_uninvoiced_oldest_ship` 与 `so_uninvoiced_count` 共用同一套「已发货 + 无有效销项发票」过滤，只是多取一个 `MIN(s.date)`。
3. **基准可复现**：同一台机器、同一个 seed、同一组 criterion 参数，得数可对比；month_close 2.98ms 与其余四组一起构成热读基线。

## 测试与门禁

- findb 新增 `so_uninvoiced_oldest_ship_returns_earliest_among_uninvoiced`（最早发货/开票后回退/全开票 None）；`uninvoiced_orders_and_ap_due_soon_surface_as_todos` 加断言 `detail` 含「最早发货」「最早到期」。
- 变异 150（`so_uninvoiced_oldest_ship` 的 MIN 写成 MAX、detail 显示成最晚发货）实跑拦下；147 锚点随 `.collect()` 改造更新。
- 全量：findb 611 passed（+1）；clippy 0 error、preflight 六步全绿。
