# v1.8.33 —— 壁钟等于最长的那条链，不是最慢的那个 job

v1.8.32 把 26 分钟的 Windows release 编译从 push 上拿走之后，CI 从 26.6 分钟降到
18.6 分钟。**没降到我预估的 7~8 分钟**，这一版把这 10 分钟的差额查清楚了。

## 差额在哪：两个 job 被串成了一条链

上一次 CI（`f53e12f`）的 job 耗时：

| job | 耗时 |
|-----|------|
| Mutation shard 1/4 | 7.5 min |
| Mutation shard 2/4 | 7.2 min |
| Coverage (backend) | 7.0 min |
| Mutation shard 3/4 | 6.2 min |
| Test | 5.9 min |
| **Web E2E (Playwright)** | **11.2 min** |
| Build (Linux x64) | 3.4 min |
| Check (Windows x64 target) | 1.9 min |
| 其余 5 个 | 各 < 2 min |

单个最慢的是 E2E（11.2 分钟），但**壁钟是 18.6 分钟**。多出来的约 6 分钟来自：

```yaml
  e2e:
    needs: test          # ← 这行
```

E2E 等 `Test`（5.9 分钟）绿了才开始。可是 E2E 自己就 `cargo build --release -p finweb`
——它**不消费 `test` 的任何产物**，这个 `needs` 只是「顺理成章地」表达的依赖顺序，
代价是把两条本来就并行的路串成了一条：5.9 + 11.2 = 17.1 分钟，而其余 12 个 job
早就跑完了。

## 改了两处

### 1. 去掉 `needs: test`

两者并行跑。原来那句 `needs` 想守的东西（测试不过就别高兴太早）由 GitHub 自己保证：
**任何一个 job 红，整个 run 就是红的**，不需要让 E2E 陪着等。

代价（说清）：代码坏的时候 E2E 也会照跑一遍，白花几分钟。但它只在**坏的那次**浪费，
而 `needs` 是在**每一次**都要多等 6 分钟。

### 2. 缓存 Playwright 浏览器

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: "22"
    cache: npm
    cache-dependency-path: e2e/package-lock.json
- uses: actions/cache@v4
  with:
    path: ~/.cache/ms-playwright
    key: pw-chromium-${{ runner.os }}-${{ hashFiles('e2e/package-lock.json') }}
```

chromium 一百多 MB，每次重下就是几分钟。key 用 lockfile 哈希 —— Playwright 版本一变
（浏览器版本跟着变）自动换缓存，不会出现「拿旧浏览器跑新测试」这种更坏的错。
`npm install` 同时改成 `npm ci`（有 lockfile，装得快也更确定）。

`--with-deps` 保留：它装的是系统库（apt），缓存拿不到，那 30~40 秒省不掉。

## 这条链也有人盯着

`tools/check-ci.js` 新增第 **2.46** 项：CI 的壁钟时间取决于最长的那条链，而链子
是靠 yml 里的 `needs` 串起来的，改起来毫无痛感、退化也毫无声响。两个方向都报红：

| 有人干了什么 | 报错 |
|--------------|------|
| 给 e2e 加回 `needs: test` | `FAIL e2e 又挂回 needs: test 了 —— 壁钟 +6 分钟` |
| 删掉 `~/.cache/ms-playwright` 缓存 | `FAIL e2e 不再缓存 Playwright 浏览器 —— chromium 每次重下一百多 MB` |

两种改坏方式都实测报红，还原后通过。

## 预期与实测

| 指标 | v1.8.32 实测 | 本版预期 |
|------|--------------|----------|
| E2E job 自身 | 11.2 min | 8~9 min（浏览器走缓存、npm ci） |
| CI 壁钟 | 18.6 min | 由**最慢的 job**决定，约 8~9 min |

关键点不是「哪个 job 最慢」，而是**没有 job 需要等别人**。这一版的判断标准：
CI 壁钟应当接近单个最慢 job 的耗时；如果壁钟明显大于它，一定是 `needs` 串了链。
