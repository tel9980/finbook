# v1.8.39 —— 发版路径：门禁跑了两遍

这一版只有一件事：**打 tag 之后那 20 分钟里，15.8 分钟是重复劳动**。

## 重复在哪

`release.yml` 的 `Verify tag & tests` 干两件事：

1. 等**同一个 SHA** 的 CI 全绿（`gh api …/workflows/ci.yml/runs?head_sha=…` 轮询）
2. 再跑一遍 `cargo test --workspace --locked`

第 2 步是多余的，而且**比门禁弱**：CI 那边除了 `test`，还跑 67 条变异、clippy、
audit/deny/udeps、Playwright E2E、Docker smoke。同一个提交、同一份代码，
本地再跑一遍 `cargo test` 证明不了 CI 没证明的东西，只多花 15.8 分钟。

删掉的是重复的那一遍，不是门禁 —— **门禁是第 1 步**。真要手动把关，本地
`cargo test --workspace` 与 CI 完全等价。

## 实测（同一版 v1.8.38，修前修后）

| | 修前（v1.8.38） | 修后（v1.8.39 实测） |
|---|---|---|
| Release 壁钟 | 21.2 min | **6.5 min** |
| `Verify tag & tests` | 15.8 min | **0.1 min**（CI 已绿，轮询立即返回） |
| `Desktop (Linux x64)` | ~2 min | 6.0 min ← 现在是壁钟 |
| `Desktop (Windows x64)` | 2.7 min | 5.2 min |
| `Server (Linux x64)` | 1.9 min | 3.0 min |
| `Publish` | 0.2 min | 0.2 min |

修后的数字是这一版自己发版时实测的（`gh api /actions/runs/:id/jobs` 逐 job 算），
不是估计。注意一个附带结论：**壁钟现在等于最慢的那条 job（6.0 min）** ——
三条构建并行，这就是发版的下限了；再想快只能缩 Windows/Linux 的交叉编译本身，
而那不是「重复劳动」，是必要的活。

## 顺带记一笔：查壁钟的正确顺序

先看**哪一条 job 占了壁钟的大头**，再看那条 job 内部哪一步最长。v1.8.38 这一版
连着遇到两例：

| 现象 | 一眼看上去的原因 | 实际原因 |
|---|---|---|
| Release 卡 68 分钟 | 「Windows 交叉编译慢」 | `apt-get update` 没有超时，卡在 mirror 上（加固后 Windows job 只要 2.7 分钟） |
| Release 21 分钟 | 「三个构建并行，正常」 | `Verify` 里重复跑了一遍全套测试，占 15.8 分钟 |

`tools/check-ci.js` 新增 **2.49**：release.yml 的 verify 一旦再出现 `cargo test`
就报红；同时盯着「等同一 SHA 的 CI 变绿」那一步还在（删了它就等于谁都能发版）。
两个方向都实测过会红。

`README.md` 新增 **§8.2 发版路径**，把这两个数与判断顺序记下来了。
