# v1.8.90 — 工艺档：同一个工件，换个表面处理就是另一个价

## 问题

氧化厂的报价单上常见这种写法：

```
外壳 MB01 · 普通氧化 · 12 元/㎡
外壳 MB01 · 硬质氧化 · 18 元/㎡
```

同一个物料、同一个客户、同一种口径，只差一道表面处理。之前只能用命名区分
（`氧化-普通` / `氧化-硬质`），开单时靠人记得选哪条；批量导入时两条价还会被
当成「同一格」互相覆盖 —— 一份新表能悄悄把旧价删掉。

## 改法

`price_rule` 加一列 `process`（schema v50）。空串表示不分档：老数据不用动，
「这一档跟别的一个价」的物料也不用凭空编档名。

- 单价矩阵工具栏多一个「工艺」框，填了只看这一档。
- 本档没单独定价、借用通用价的格子，下面标「用通用价」—— 不标的话老板以为这一档
  定过价，实际开单按的是别的价。
- 报价试算、桌面端规则表与试算、批量导入模板都跟上。

## 匹配规则

1. 选了档位 → 只认这一档和不分档，且本档优先；没选档位 → 只认不分档。
2. 精度：物料+客户 > 只限物料 > 只限客户 > 通配。
3. 同一格取已生效里生效日最晚的那条；都没有才用未来价并标「未生效」。

**没选档位绝不拿档位价。** 报了档位价，客户拿普通氧化的单子来对账，反而说不清。

## 批量导入改成按列名对齐

有表头就完全按列名读（表里没这一列 = 没填），没表头才按固定顺序。此前按位置读，
客户把「工艺档」放在第五列时，系统把「硬质氧化」当起步价，只报一句
「起步价不是数字」，用户想不到是列错位。

## 测试与门禁

- `findb`：26 条（新增 5 条 + 按档/按列名对齐各一条）。
- `finweb` 接口测试：`tier_prices_stay_in_their_own_tier`（6 条总计）。
- 前端渲染检查：27 条（新增 2 条「用通用价」）。
- 变异清单 211 → 215（`77–80`），全部实跑确认被拦下。

## 升级

老账套直接升级，`price_rule.process` 默认空串 = 全部按不分档处理，报价行为不变。

## 顺带：把内嵌的 SQLite 从 3.53.2 升到 3.54.1

发版前 CI 的安全检查报了一条上游公告（CVE-2026-119375，RUSTSEC-2026-0459）：
SQLite 3.54.0 之前的版本，如果一个进程打开数据库时旁边有个页大小不一致的
`-wal` 文件，普通查询可能读到内存里的残留字节。

攻击面是「本地、且要有人先把这对文件塞给你」——账套备份和演示账套正是这么传的，
所以我们没有忽略这条公告，而是把 `rusqlite` 从 0.32 升到 0.41（内嵌 SQLite 3.54.1）。

- 代码只改了一处 API（`column_names()` 现在返回迭代器），`findb` 562 条、
  `finweb` 接口 222 条测试全绿。
- 账套文件格式没变，升级后照常打开。
