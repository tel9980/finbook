# v1.8.113 清冗余/死代码：修订单执行进度口径 + 删两列 + 删死函数

## 问题

三件事，都指向「看走眼」的风险：

1. **`so_get`/`po_get` 的进度读错列**：`so_line.qty_shipped` / `po_line.qty_received` 这两列建表后**从未被任何代码回写**（发货/收货只往 `so_shipment`/`po_receipt` 插行）。`so_list`/`po_list` 读完后会用流水表汇总覆盖这两列，但 `so_get`/`po_get`（单张读）直接读原始列，永远返回 0。`sales.rs` 的 `so_shipment_notice` 用 `so_get` 算「未发量 = 订购 − 已发」，于是未发量恒等于订购量，**超发校验失效**。
2. **两列是死存储**：既然从没回写过、读路径又都改成实时汇总，这两列只会留着一个「读原始列就拿到 0」的陷阱。
3. **`landed_cost_sum` 是死代码**：`crates/findb/src/landedcost.rs` 里该函数全仓库零调用（连测试都没有），删除无风险。

## 改法

- `crates/findb/src/scm.rs`：`so_get`/`po_get` 读完明细后，改为从 `so_shipment`/`po_receipt` 实时汇总执行进度，并对齐 `so_list`/`po_list` 的口径。
- `crates/findb/src/schema.rs`：删 `so_line.qty_shipped`、`po_line.qty_received` 两列——DDL 删列、`MIGRATE_V6` 删对应条目、新增 `migrate_v55`（幂等 `ALTER TABLE ... DROP COLUMN`），`SCHEMA_VERSION` 54→**55**，迁移链在 MIGRATE_V54 之后调用。
- `crates/findb/src/scm.rs`：`so_save`/`po_save`/`so_list`/`po_list`/`so_lines_by_order`/`po_lines_by_order` 的 INSERT/SELECT 同步去掉这两列。
- `crates/findb/src/landedcost.rs`：删除 `landed_cost_sum`。

## 三条规矩

1. **只删行级两列、不动订单级两列**：`sales_order.shipped_amount` / `purchase_order.received_amount` 会由 `so_save`/`po_save` 写回，本版不动；只删从没回写过的 `so_line.qty_shipped`/`po_line.qty_received`。
2. **删列幂等且向后兼容**：`migrate_v55` 先 `column_exists` 再 `DROP COLUMN`，旧账套（schema 54）升级时自动删两列，全新账套 DDL 已不含则跳过；升级后 `so_get`/`po_get` 的进度改为实时汇总，读到的值更真。
3. **死代码只删确认无调用的**：`landed_cost_sum` 全仓库（含测试）零调用才删；同文件 `by_item` 有调用（存货分析），保留。

## 升级说明

**schema 升级到 v55**：旧账套首次打开时自动删掉 `so_line.qty_shipped`、`po_line.qty_received` 两列（幂等，不影响数据）。订单执行进度改为从 `so_shipment`/`po_receipt` 实时汇总，`so_get`/`po_get` 读到的进度会比之前更真实（之前恒为 0）。接口、界面不变，纯后端清理。
