# v1.8.109 客户账期字段 + 待收货待办 + 订单明细批量加载（高效/便捷/性能）

## 问题

三件事一起做：

1. **高效**：客户「账期」在界面上没处设——账龄分析、回款看板、催款函都在用客户档案的 `pay_days`，但客户编辑框只有「信用额度」，没有「账期」输入。
2. **便捷**：工作台采购侧有「待确认采购订单」（草稿），但没有「已确认但货没到齐」的待办；老板只看工作台时，压着没催的到货看不见。
3. **性能**：订单列表 N+1——`so_list`/`po_list` 对每张订单单独查一次明细行，几十张单就是几十次往返。

## 改法

### ① 客户档案补「账期」字段（高效）

客户编辑框在「信用额度」下加「账期（天，留空 = 货到即付；到期按发货日起算）」输入，保存写进 `props.pay_days`。非空必须是 0-3650 的整数，否则前端拒绝。`pay_days` 本来就被账龄/回款/催款三处共用（`settle::customer_pay_days_map`），界面只是补上「能设」的入口，不改任何计算。

### ② 工作台补「待收货采购订单」待办（便捷）

`collect` 与 `collect_todos` 的采购块里，在 `po_todo` 之后加 `po_receive_todo`：数 `status ∈ {Confirmed, PartialIn}` 的采购订单。`Completed`/`Cancelled`/`Draft` 不算。跳「采购单据」页（`po-doc`）。

### ③ 订单明细批量加载（性能）

新增 `so_lines_by_order` 与 `po_lines_by_order`：`JOIN` 订单表限定期间、一次扫全明细行，Rust 侧按单分组；`so_list`/`po_list` 循环内不再逐单 `prepare`+`query_map`。字段映射与排序（`ORDER BY so_id, id`）与逐单查询完全一致。

## 三条规矩

1. **账期只补入口不改算法**：`pay_days` 的计算逻辑（账龄/回款/催款）一律不动，界面只补「能设」这一环。
2. **待收货只看状态**：`Confirmed`/`PartialIn` 就是「还有货没到齐」的语义，不另算 `qty_received < qty_ordered`，避免和收货流程的判定打架。
3. **批量加载不改变语义**：明细行的字段、排序与逐单查询一致，只换「一次取全 + 分组」，不做任何口径调整。

## 测试与门禁

- findb 新增 `pending_receipt_purchase_orders_surface_as_a_todo`（五种状态各一张，断言 `po_receive_todo` 的 `count==2`）、`list_batch_loads_lines_across_orders`（多行订单明细都回来、行序正确）。
- 变异 132（待收货把草稿也算进来）、133（订单明细批量加载只留第一行）实跑拦下。
- clippy 0 error、preflight 六步全绿。

## 升级说明

数据格式没变（schema 仍 v54），老账套直接升。客户账期字段在「设置 → 档案」里编辑客户时出现；工作台采购侧自动多一行「待收货采购订单」。
