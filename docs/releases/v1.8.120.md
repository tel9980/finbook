# v1.8.120 在制品成本去 N+1

## 问题

`findb::manufacturing::wip_cost`（工作台「在产品」列表）原来对每个未完工生产订单逐单查 4 次：

- `get_prod_cost` 内部 3 条 `GROUP_CONCAT`（材料 / 人工 / 制造费用各一条）；
- `order_hours` 1 条（报工工时）。

N 张在制单就是 4N 次查询。5000 单基准的 seed 不含生产订单，所以慢查询基准测不出它；但真实账套（几十上百张在制单）每次打开工作台都会触发。`wip_total_by_period` 的注释里早就点出这是「双重 N+1」——那只是趋势图绕开了，列表没绕。

## 改法

- 新增 `prod_cost_summary(db, po_ids)`：一条 `SELECT po_id, cost_type, amount FROM prod_cost WHERE po_id IN (...)`（走 `idx_pc_po`），Rust 侧按 `po_id + cost_type` 累加。口径与 `get_prod_cost` 一致——都是把 TEXT 金额解析成 Money 累加，不碰 SQL 的 `SUM`（全库约定「金额存 TEXT、不在 SQL 里 SUM」）。
- 新增 `order_hours_map(db, po_ids, period)`：一条 `SELECT po_id, hours FROM prod_op_log WHERE po_id IN (...) AND period=?`，Rust 侧累加。
- `wip_cost` 改成「`prod_list` 取订单 → 筛未完工 id → 两次批量取数 → Rust 侧组装」，从 4N+1 次查询降到 3 次。

## 三条规矩

1. **口径不变**：批量取数与逐单 `get_prod_cost` / `order_hours` 的结果逐单相等（测试里显式断言）。
2. **完工 / 作废单仍排除**：只对未完工订单批量取数。
3. **期间过滤仍在**：报工工时只取本期间，跨期间的 `prod_op_log` 不算进本期工时。

## 升级说明

无 schema 变更，无需操作。纯后端优化，界面无变化。
