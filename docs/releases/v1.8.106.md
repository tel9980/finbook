# v1.8.106 采购/销售对账去 N+1（性能）

## 问题

「采购对账」「销售对账」两个页面每渲染一次，就对**每张订单**分别查一次付款汇总：

- 采购：每张单查一次 `po_payment_sum`（已付款）+ 一次 `po_estimate_open_sum`（未冲回暂估）；
- 销售：每张单查一次 `so_payment_sum`（已收款）。

几十张开着的单就是几十到上百次 SQL 往返。这跟 v1.8.104 修的 `so_receivable`/`credit_check` 是同一类浪费，只是当时漏了这两个对账入口。

## 改法

新增两张批量汇总，只扫一遍表、按 `po_id` 累加成 HashMap：

- `procurement::po_payment_sums(db)`：全表扫 `po_payment`，按 `po_id` 累加已付款。
- `scm2::po_estimate_open_sums(db)`：全表扫 `po_estimate WHERE settled=0`，按 `po_id` 累加未冲回暂估。

然后 `po_reconcile` 用这两张表、`so_reconcile` 复用 v1.8.104 的 `sales::so_payment_sums`，替换逐单查询。行为完全不变，查询次数从 O(订单数) 降到 O(1) 次扫表。

## 三条规矩

1. 只扫一遍全表，对账不再在循环里查单张订单。
2. 口径不变：`unpaid = 订单金额 − 已付款`、`unreceived = 订单金额 − 已收款`、`open_estimate` 只算未冲回。
3. 不碰写路径：`po_payment_sum` / `po_estimate_open_sum` / `so_payment_sum` 都保留（桌面端与测试还在用），只是对账入口改用批量版。

## 测试与门禁

- 变异 126–129 全部实跑拦下。
- clippy 0 error、preflight 六步全绿、findb 594+ passed、finweb api 233 passed。
