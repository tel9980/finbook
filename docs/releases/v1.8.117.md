# v1.8.117 采购订单执行进度去 N+1

## 问题

采购订单「执行进度」页（`po_execution_track`）每显示一张采购单，就单独查一次 `po_receipt` 流水来算净收货量——典型的 N+1。销售侧 `so_execution_track` 早在 v1.8.107 就改成了 `so_shipment_sums` 一次扫全表、按单累加，**采购侧是那次漏掉的对称项**。

## 改法

- `crates/findb/src/procurement.rs` 在 `po_receipt_sum`（单单据版）之后新增 `pub fn po_receipt_sums(db) -> DbResult<HashMap<i64, Money>>`：`SELECT po_id, qty FROM po_receipt` 一次扫全表，Rust 侧按 `po_id` 累加（退货行是负值，自然轧成净收货）。与 `so_shipment_sums`（sales.rs）完全同款。
- `po_execution_track` 循环前先 `let sums = po_receipt_sums(db)?;`，循环内 `let received = sums.get(&o.id).copied().unwrap_or(Money::ZERO);`，删掉原来的逐单 `po_receipt_list` 循环。
- 其余 `po_receipt_sum`（`refresh_po_status` / 退货超退校验 / `fetch_lines_from_po`）都是**单张单据**调用，不在循环，保持不动。

## 三条规矩

1. **只改取数方式，不改口径**：`po_receipt_sums` 的净收货结果与原来逐单累加完全一致，只是从「每单一次查询」变成「一次扫全表 + 内存查表」。
2. **退货天然轧净**：`po_receipt` 里退货行是负值，累加即得净收货，不需要额外的正负判断。
3. **对称补齐**：采购侧对齐销售侧 v1.8.107 的 `so_shipment_sums`，两边「执行进度」都是批量汇总，不再有单侧 N+1。

## 测试与门禁

- findb 新增 `po_receipt_sums_aggregates_across_orders`（po1 收货 70 + 退货 10 → 净 60、po2 收货 30、po3 没收货 → 断言 `sums[po1]==60`、`sums[po2]==30`、`len()==2`）。
- 变异 151（`po_receipt_sums` 累加写成覆盖 `+=`→`=`，只留每单最后一笔收货）实跑拦下。
- 全量：findb 613 passed（+1）；clippy 0 error、preflight 六步全绿。

## 升级说明

无 schema 变更，无需操作。纯后端取数方式优化，无界面变化。
