# v1.8.107 订单执行进度去 N+1（性能）

## 问题

「销售单据 → 订单执行进度」每渲染一次，就对每张订单查一次 `so_shipment_sum`（净发货量），几十张单就是几十次 SQL 往返。跟 v1.8.104（回款看板）、v1.8.106（对账）修的是同一类 N+1，这里是订单执行进度的入口。

## 改法

新增 `sales::so_shipment_sums(db)`：全表扫 `so_shipment`，按 `so_id` 累加发货量。退货行是负值，`+=` 累加自然轧成净发货，和原来逐单 `so_shipment_sum` 口径完全一致。

`so_execution_track` 改用这张批量汇总，循环里不再逐单查库。

## 三条规矩

1. 只扫一遍全表，执行进度不再逐单查库。
2. 退货自然轧平（负行 `+=` 累加）。
3. 口径不变：`shipped_qty`、`rate` 和原来完全一致。

## 测试与门禁

- findb 新增 `so_shipment_sums_aggregates_across_orders`（发货 70 + 退货 10 → 净 60；没发货不出现在表里）。
- 变异 130（发货汇总只取最后一笔、退货没轧掉）实跑拦下。
- clippy 0 error、preflight 六步全绿。

## 升级说明

数据格式没变（schema 仍 v54），老账套直接升。纯后端性能改动，前端无感知。
