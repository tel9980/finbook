# v1.8.122

## 这一版修的是什么

### 1. 删单之后取号会撞号，用户看到「保存失败」

录了 3 张请购单（`QG202601-001/002/003`），删掉中间那张 002，再录一张——老代码用
`SELECT COUNT(*) ... LIKE '前缀%'` 取号，COUNT 变成 2，`2+1=3`，于是**又发了一次
`QG202601-003`**，撞上 `no` 上的 UNIQUE 约束，界面上弹的是「保存失败」。

同一个毛病在 9 个取号点上，其中 5 个**没有**撞号顺延（请购单 / 报价单 / 盘点单 /
资产盘点 / 批次号），4 个早就有 `loop` 顺延（催款单 / 返工单 / 工装夹具 / 工序检验）
所以一直没暴露。本轮把 9 个统一改掉。

### 2. 取号全表扫，批量导入 O(n²)

`LIKE '前缀%'` 用不上索引，每次取号都要全表扫一遍。批量导入历史数据时，
N 张单就是 O(N²)——实测 5000 单要 105 秒，其中绝大部分花在取号上。

### 3. 文档里三条过期声明 + 6 条真实限制没写

`README.md` §9「已知限制」里：合并报表写「未实现」（实际 Web 端早有了，§4.43）、
销售成本结转写「Web 入口待立项」（实际有 `POST /api/cost/sales-cost`）、批次功能写
「待立项」（实际批次盘点/调拨/成本报表都落地了）。反过来，真正的限制没写。
本轮按代码实证重写，并补上 6 条真限制。

## 怎么改的

- `crates/findb/src/lib.rs` 新增 `next_seq_by_prefix_col`（WHERE 从 `LIKE` 换成
  `no >= 前缀 AND no < 上界`，吃索引；取号仍用 `MAX(CAST(SUBSTR(...)))`，语义不变）
  与 `next_no_by_prefix`（拿到起点后逐个验空，被占就顺延，上限 1000）。
- 9 个调用点改走 `next_no_by_prefix`：请购单、报价单、盘点单、资产盘点、批次号、
  返工单、工装夹具、寄售单、工序检验。
- `README.md` §9 重写 3 条、删除 1 条、新增 6 条；小节编号 §4.128/§4.167 → §4.165。

## 三条规矩

1. **空号可以复用，已存在的号绝不能再发。** 删掉 002 之后 002 是空的，下一条发 002
   没问题；但发 003（已存在）就是 bug。
2. **撞号顺延有上限。** 连续 1000 个候选号都被占就报错，说明数据本身有问题，
   不能让程序静默死循环。
3. **取号语义不许漂。** 前缀不匹配的不算、后缀非数字的忽略、跨期间互不干扰——
   这三条只要有一样变了，用户就会看到号从头开始或突然跳一大截。

## 升级说明

无 schema 变更，旧账套直接打开即可。已经存在跳号历史的账套不受影响（本版只改
「下一个号怎么算」，不重排已有单号）。
