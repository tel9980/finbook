# v1.8.124

## 这一版修的是什么

### 出库一次，吃掉一整条发货通知

发货通知是「备货指令」：通知 3 + 3 + 4 共 10 件，仓管按通知备货，出库后通知闭环。
老实现只有一句话：

```sql
UPDATE ship_notice SET status='shipped'
WHERE id = (SELECT id FROM ship_notice WHERE so_id=?1 AND status='pending' ORDER BY id LIMIT 1)
```

**出库一次就把最早那条通知整条置成已发，完全不看数量。** 于是先发 2 件，第一条 3 件的
通知就被标成「已发完」——剩下 8 件还欠着，但通知列表里已经少了一条。备货指令和实际
出库一旦脱钩，仓管就失去了「还欠客户多少」的唯一线索，只能靠翻订单重算。

## 怎么改的

`ship_notice` 加一列 `qty_done`（已按本条通知出库的数量，schema v56 → **v57**）。

新的占用口径：按通知创建顺序逐条占用本次发货量——**占满一条才置已发**，占不满就只累加
`qty_done` 留在待发，本次量用完即停。一次发货可以跨多条通知（补满第一条再吃第二条），
也可以只占一条的一部分。

占用挂在**发货的同一个事务里**，两个入口都挂：

- `so_shipment_all`（Web 全链路：收入凭证 + 发货行 + 出库流水 + 通知占用）
- `so_shipment_add`（桌面端纯流水入口）

顺带删掉了 Web handler 里原来那行重复调用——占用挪进事务后它必须删，否则同一次出库会
被认领两遍、`qty_done` 翻倍。

前端通知列表把「数量」拆成三列：通知数量 / 已发 / **还欠**，「去出库」按钮带的是还欠
的数量而不是通知总量，否则点一次就会超发。

## 三条规矩

1. **通知占用与出库同事务。** 出库失败（仓库不存在等）时通知一件都不能被占——不能出现
   「报错了但通知已经被吃掉」。
2. **占满才算完成。** 已发通知的 `qty_done` 恒等于 `qty`，待发的恒小于 `qty`。
3. **通知是备货指令，不是发货前置条件。** 发货量超过所有待发通知之和时，多出来的部分
   只是没有通知可认领，照常发货、不报错。

## 升级说明

schema v56 → v57，老账套打开时自动补列。历史已发通知的 `qty_done` 会补齐成 `qty`
（老语义就是整条完成），待发的留 `0`——不补的话升级后老通知会显示成「已发货 0 / 10」，
看着像数据坏了。
