# v1.8.53 —— 设备绑定：从「最多两台」改成「首次绑定后禁改」

清 `SECURITY_TODO` 的 **M-4**（挂了很久的中危项）。这次不长，但改的是一条**会悄悄变松**
的安全政策，值得单独写一版。

## 问题到底是什么

`device_id` 是客户端自己生成的一串字符串。服务端没有任何办法证明「这台机器确实是上次
那台」—— 没有可信硬件标识、没有客户端证书；上 TLS 也只证明通道安全，不证明设备身份。
所以「校验 device_id 真实性」这条路走不通，我也没有假装去走。

问题在于**旧政策给了伪造者好处**：登录时自动往绑定名单里加到 2 台。于是拿到口令的人
可以：

1. 用口令在一台自己的机器上登录；
2. 服务端**自动**把这台登记为第 2 台合法设备；
3. 之后长期使用，而用户看到的名单里只是多了一行，跟自己的手机没区别。

## 改法：不给扩容的机会

| 情形 | 旧行为 | 现在 |
|------|--------|------|
| 名单为空（第一次登录） | 自动登记 | 自动登记（不变） |
| 名单里已有这台 | 刷新时间 | 刷新时间（不变） |
| 名单非空、这台没登记 | **自动加进去** | **拒绝登录**，提示找管理员重置 |
| 管理员「重置设备绑定」 | 清空名单 | 清空名单（不变） |

「首次」的判定是**名单为空**，不是「这台没登记过」—— 否则攻击者先登进来就占住了
首绑名额，等于把门交给先到的人。

拒绝文案写清下一步：

> 这台设备还没有被授权。该账号已在 1 台设备上绑定过；换设备需要管理员在「账号」页点
> 「重置设备绑定」，之后用新设备重新登录。

## 顺带：名单里不再存 `device_id` 原文

比对改成**设备指纹**：`sha256(盐 | 账号 | device_id)`，盐每库随机生成、存 `realm_option`。

要诚实说清它挡不住什么：盐就在同一个库文件里，能读库的人能一起读走。它的作用是让
「从名单里抄一行出去」不再是通行证（换部署、换盐都对不上），属于**降低凭据价值**，
不是主要防线 —— 主要防线是上面那条「不再扩容」。

两个必须做的配套，否则升级当场全锁死：

- **存量行回填指纹**（`WHERE device_hash = ''` 逐行补）。不补 → 老用户升级后「登录成功
  但每个请求都说设备未授权」，而且不报任何错。
- **`device_allowed` 保留 `device_id` 兜底比对**（仅指纹为空的行）。兜底只为「升级那一
  瞬间的请求」存在，不是常态。

## 测试与验证

| 项 | 结果 |
|----|------|
| `cargo test --workspace` | **1075** 全绿 |
| 新增 `realm` 单测 4 条 | 首绑自动 / 第二台被拒且提示含「重置设备绑定」/ 同设备重登不增行 / 重置后新设备可进 / 名单存的是 64 位指纹而非原文 |
| 改造既有集成测试 | `platform_device_binding_and_reset` 断言从「第二台应可登录」翻转为「第二台应被拒」，并把「重置后两台都能绑」改成「重置只重启一次首绑机会」 |
| 变异验证 | 107 → **108**，3 条全部拦下：政策回潮（`if count > 0` → `if false`）、同设备重登插新行、存量不回填指纹 |
| 删掉两条**假守卫** | 「上限退回 1 台」（常量已不存在）与「登录时清该账号全部会话」（普通账号现在只绑一台，`remove_by_username_and_device` 与 `remove_by_username` 移除的集合完全相同，任何测试都分不出来）。两条都是「永远绿、看不出没在守」的变异 |
| 自检 | check-ci / check-js / check-portable / check-design-doc / check-simple-nav 全过 |

那条既有集成测试是这一版唯一被我**翻转断言**的地方。翻转的时候我在注释里留了三代语义
的演变（一人一机 → 最多两台 → 首次绑定后禁改），因为「为什么改动了一条本来通过的测试」
是以后最容易被误读的地方。

## E2E 差点被这条政策打死（顺便修了一处测试设施）

`app.js` 的 `device_id` 存在 `localStorage`。Playwright 每个 test 开全新 context，
localStorage 是空的 → 每次登录都是「一台新设备」→ 第一条用例之后全被 403，
整套 E2E 挂在一句「等不到 `#book-list`」上（症状与设备毫无关系，最难查的那种）。

修法：`e2e/helpers.js` 新增 `pinDevice(page, username)`，把 `finbook_device_id` 钉成
`e2e-<账号>`（用 `addInitScript`，登录请求发出时就要读到）。同一账号在所有用例里
都是同一台设备 —— 这也正是真实用户的常态。

## 会影响谁

- 一直在同一台电脑 / 同一个浏览器登录的：**没有任何变化**。
- 换电脑、换浏览器、清空过浏览器数据（`device_id` 会重新生成）的：会被拒绝登录一次，
  找管理员在「账号」页点「重置设备绑定」即可。
- 管理员账号：不受设备绑定约束（运维账号不该被锁死）。
