# v1.8.112 工作台成本/报销走势去重复加载（性能）

## 问题

v1.8.111 只把工作台的「订单金额走势 / 采购金额走势」两条从逐期 N+1 改成了批量汇总，但工作台还有两条趋势是同一个毛病：

- **在产品走势**：对近 n 期各调一次 `wip_cost`，而 `wip_cost` 每期内部还要逐单查 `prod_cost` 三要素——是**双重 N+1**（外层逐期 + 内层逐单）。
- **我的报销走势**：对近 n 期各调一次 `claim_list` 再在 Rust 里逐单过滤本人，也是逐期整表扫描。

## 改法

- `crates/findb/src/manufacturing.rs` 新增 `wip_total_by_period(db, from, to)`：一条 `JOIN` 扫全（`production_order` 连 `prod_cost`），Rust 侧按期间累加。口径与 `wip_cost` 的 `total` 一致：只看未完工订单，金额 = 该单全部成本要素之和。
- `crates/findb/src/business.rs` 新增 `claim_amount_by_period(db, from, to, applicant)`：一条 `BETWEEN` 扫全、SQL 侧按 `applicant` 过滤。
- `crates/findb/src/workbench.rs` 的 `collect` 里，「在产品走势」「我的报销走势」两条趋势循环各改成一次调上述汇总函数。

## 三条规矩

1. **只动走势、不动卡片**：本期卡片仍用当期 `wip_cost`/`claim_list` 实表（要数单、判状态），走势只用金额汇总，数据源不混。
2. **口径不变**：在产品走势只看 `status NOT IN ('completed','cancelled')`、金额是全部成本要素之和；报销走势只算 `applicant` 等于本人、不分状态——都与旧循环逐字一致。
3. **不在 SQL 里 SUM 金额**：延续全库约定，金额在 Rust 侧用 `Money` 累加再转 `f64` 画图。

## 测试与门禁

- findb 新增 `wip_total_by_period_batches_across_periods`、`claim_amount_by_period_batches_across_periods`（都验证按月汇总 + 排除/过滤 + 范围外不计入）。
- 变异 138（在产品走势累加写成覆盖）、139（在产品走势把完工单也算进来）、140（报销走势漏掉本人过滤）、141（报销走势累加写成覆盖）实跑拦下。
- clippy 0 error、preflight 六步全绿。

## 升级说明

纯后端性能优化，schema 不变、接口不变、界面不变，老账套直接升。工作台首页加载会更快（生产订单和报销单越多越明显）。
