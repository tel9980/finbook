# v1.8.23 — 修「导入账套后进不去工作页面」

## 一句话

从桌面版搬上来的账套现在能直接进去了。已经导入过的账套**不用重新导入**，升级即可。

## 症状

上传 `.fbk` 显示成功，账套出现在选择页上，点进去又弹回选择页 —— 工作页面一次都进不去。

## 根因（两层，缺一层都不会发作）

**第一层：导入时「已有同名账号就一个字段都不动」。**

v1.8.21 的 `import_book` 里有这么一句判断：账套里已有同名用户则不动，理由是「可能是人家原来的密码」。这条判断对**口令**成立，对**改密标记**不成立。

桌面版建的账套里，`admin` 那行是「首次登录必须改密」（`must_change_pwd = 1`）—— 在桌面端从没改过，所以永远是 1。搬进 Web 之后，平台这边的 `admin` 是 `must_change_pwd = 0`，两边对不上。

**第二层：账套层拿这个影子标记鉴权。**

`CurrentUser` 提取器（`crates/finweb/src/state.rs`）在账套层还有一道强制改密闸门：`user.must_change_pwd` 为真时，除改密/退出之外一律 401「你的口令已过期或需首次设置，请先修改口令」。

问题在于：**平台层 `RealmUser` 上已经按真身拦过一次了**，平台要求改密时所有接口本来就过不去。所以账套这道闸门只可能在「平台说不用改、影子说要改」时触发 —— 那正好是误伤，不可能拦住该拦的人。

前端 `enterBook` 的顺序是 `select → /api/me → 建界面`。`/api/me` 收到 401，错误信息里既没有「登录」也没有「停用」，于是走 `showBookPicker()` —— 一句话不解释就退回选择页。

## 改法

1. **导入时对齐标记**（`crates/finweb/src/handlers.rs`）：同名账号行存在时，把 `must_change_pwd` 对齐成平台层的值；`disabled` 也一起放开（这是刚导入的、属于当前账号的账套，那行停用只可能来自桌面端的旧配置，留着就是把导入的人锁在门外）。对齐过的项记进审计（`账套内同名账号已与平台身份对齐（改密标记）`）。

   **口令哈希故意不动。** Web 端从不校验账套内口令（登录只认平台口令），改它唯一的效果是让桌面端原本能用的口令失效 —— 那是把一个「进不去」换成另一个「进不去」。

2. **账套层那道闸门撤掉**（`crates/finweb/src/state.rs`）：真身只有平台那一份，账套里的标记是 `sync_password_to_books` 同步下来的影子，不参与鉴权。这一条同时让**修复之前导入的账套**直接可用，不必重传。

## 验证

- **本地真账套复现**：拿 `小工厂账套.fbk`（桌面版建的，`admin` 行 `must_change_pwd=1`）走完整流程
  `login → POST /api/books/import → POST /api/books/{key}/select → GET /api/me`，
  修复前 `/api/me` 返回 401 `{"error":"你的口令已过期或需首次设置，请先修改口令"}`；
  修复后返回 200 并给出账套内身份，试算平衡接口也正常出数。
- **回归测试**（`crates/finweb/tests/export_xlsx.rs` 的 `upload_fbk_registers_a_usable_book`）：
  造的「外部账套」现在按真实形态带上 `must_change_pwd=1` 的同名 admin 行，
  断言进账套后 `/api/me` 必须 200；再单独验一层「事后把标记又置回 1 也不该拦人」。
  去掉修复后这条测试会失败，报的就是用户看到的那句 401 原文。
- **变异测试**新增 2 条并跑过：*导入账套后不对齐改密标记* / *账套层的改密标记又参与鉴权* ——
  两条都必须让上面那条测试失败。

## 升级提示

- 已经导入过的账套：升级后直接能进，不用删了重传。
- 桌面端打开同一个账套：口令不变（本次故意不动口令哈希）。
- 想让两边口令一致：在 Web 端改一次口令即可，`sync_password_to_books` 会同步到所有账套。
