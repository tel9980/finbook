# v1.8.34 —— 最后一个「白等」的 job

v1.8.33 去掉 e2e 的 `needs: test` 之后，CI 壁钟从 18.6 分钟降到 **11.2 分钟**。
这一版把最后 3.7 分钟的尾巴也切掉。

## 时间线暴露的真相

`94420cd` 那次 CI，所有 job 的启动时刻都是 **+0 分钟**（没有排队），各个 duration：

| job | 耗时 |
|-----|------|
| Coverage (backend) | 7.6 min |
| Test | 7.4 min |
| Mutation shard 2/4 | 6.9 min |
| Mutation shard 1/4 | 6.8 min |
| Web E2E (Playwright) | 5.9 min |
| Mutation shard 4/4 | 5.3 min |
| Mutation shard 3/4 | 4.3 min |
| Build (Linux x64) | 3.4 min |
| Check (Windows x64 target) | 1.3 min |
| **Docker image smoke test** | **3.7 min，但 `started_at` 是 +7.5 分钟** |

最慢的是 Coverage 7.6 分钟，壁钟却是 11.2 分钟。差额 = **+7.5（等 Test）+ 3.7（自己跑）
= 11.2** —— 也就是说整个 CI 的最后 3.7 分钟，只有 Docker 烟雾测试一个 job 在跑，
而它本来可以和 Test 同时跑。

```yaml
  docker:
    needs: test          # ← 同一处毛病，最后一个
```

它为什么没在第一轮被一起摘掉：**它的耗时取决于 Docker 层缓存**。缓存命中时 0.3 分钟
（几乎看不见），未命中时 3.7 分钟。所以它有时候看起来"根本不影响"。只有把
`started_at` 和 duration 摆在一起看才看得出来。

这个 job 同样不消费 `test` 的产物 —— 它自己在镜像里 `cargo build --release`
（Dockerfile 多阶段构建）。

## 改法：把规则一般化，不再一个个抓

`tools/check-ci.js` 原来只盯 e2e 一条链。现在换成一条通用规则：

> 任何一个 job 声明了 `needs: test`，**必须**有 `actions/download-artifact` 步骤。
> 否则它就是在白白排队 —— 不消费产物，就没有排队的理由。

e2e、docker 两个都是这么白等过的；写得再细也挡不住下一个。

## 结果

| 指标 | v1.8.32 | v1.8.33 | v1.8.34（预期） |
|------|---------|---------|------------------|
| CI 壁钟 | 18.6 min | 11.2 min | **≈ 7.6 min**（= 最慢的 job，Coverage） |
| Windows 相关 job | 26.5 min → 1.9 min | — | 1.3 min |
| E2E | 11.2 min | 5.9 min | 5.9 min |

判断标准可以固化了：**CI 壁钟应当等于最慢 job 的耗时**。大于它，说明还有人在排队。

## 验证

| 项 | 结果 |
|----|------|
| `node tools/check-ci.js` | 通过；给 docker 加回 `needs: test` 实测报红：`FAIL ci.yml 的 docker 排了 needs: test 却不下载任何产物` |
| 其余四个自检 | check-js / check-portable / check-design-doc / check-simple-nav 全 exit=0 |
| `cargo test --workspace` | 972 全绿（本版没动业务代码） |

## 一次自己踩的坑，记下来

第一次给这条规则做「改坏验证」时，替换的字符串没匹配上（注释行是
`# 层缓存命中：命中时 0.3 分钟…`，我从「命中时」开始截，前一个字不属于我的搜索串），
于是脚本报 `changed: False`、检查器「通过」——**看着是验证过了，其实变异没生效**。

这跟 v1.8.31 修的那三条假守卫是同一类错：**验证手段本身没被执行**。所以现在每次
改坏验证都必须看脚本回显（`mutated ok` / 检查器输出 FAIL），不能只看「通过」。
