# v1.8.40 —— 撤销核销：能撤一部分，但不能动已结账的月份

这一版做的是 P2 里风险最高的一条：**撤销核销**。它两个毛病，一个让人白干，一个能让
已经出过的报表对不上账。

## 一、只能整条撤销 → 可以撤一部分

现实场景：11 月收到 5 万，核销了三张单共 5 万；第二天发现其中一张该是 3 万，另外
2 万应该挂在下个月的单上。

以前只能**整条撤销再重录**。撤销的瞬间三张单全变「未核销」，账龄立刻虚高——而这段
时间里老板、客户看到的就是那个数。

现在可以只撤一部分：`unsettle_part(db, id, amount)`，减掉 `amount`，减到 0 就整条
删除。

| 界面 | 怎么用 |
|------|--------|
| 网页 | 核销记录 → 「取消核销」→ 弹窗填金额（填全额或留空 = 整条撤销） |
| 桌面 | 核销记录上方「撤销金额」输入框，先填金额再点「取消」 |

守卫两条：`0 < 撤销额 ≤ 这条记录的金额`（超了报「撤销金额 X 超过这条核销记录本身的
金额 Y」）、**记录所在期间未结账**（下一条）。

## 二、撤销不看结账线 → 已结账的期间不许动

账龄、未核销额都是「截至某期」的数。结账之后把它改掉，等于让**已经出过、签过字的
报表对不上账**。

现在：

```
这条核销记在 2026-08，该期间已结账（已结至 2026-09）——已结账期间的核销不能撤销。
确需更正请先反结账，再改动。
```

反结账那条路有日志、有明确意图，走它是对的。

## 三、顺手改对的一件事：核销记录记在「核销发生的期间」

`settle_record.period` 原来写的是被核销分录的期间。于是 11 月收到客户还 8 月的货款，
台账里那笔核销记在 `202608`：

- 账面看不出「钱是哪个月收的」——这正是对账时最常问的一句；
- 8 月可能已经结账，却还能往里面塞核销记录。

改成「最后一个已结账期间的下一期」（`periods::current_period_of(&tx)`，事务内读，
避免「刚判完没结账、期间被别人结了」的窗口）。

这一步让上面那条规则自洽了：**新增核销永远落在未结账的当前期**，所以「已结账不许
撤销」不会把正常业务卡死——今天做的核销，今天所在的期间一定没结账。

| 项 | 结果 |
|----|------|
| `cargo test --workspace` | **993** 全绿（findb 422：新增 4 条核销期间/撤销；新增 `settle_unsettle_api` 3 条） |

| 变异验证 | 5 条全部拦下（撤销不看结账线 / 部分撤销不夹记录金额 / 记录仍按单据期间 / 撤到零不删 / 空串当非法金额），下限 67→**72** |
| 自检 | check-ci / check-js / check-portable / check-design-doc / check-simple-nav 全过 |

HTTP 这一层单独守了三条，因为它们是「静默错」的高发区：

- 只传 `{id}`（老前端）→ 行为不变；
- `amount: "5万"` → 400 且**带上原值**（「撤销金额「5万」不是合法金额」比 500 有用）；
- `amount: "   "` → 当成没填（整条撤销），不是非法金额。

## 打 tag 那天 CI 红了一次：mingw 又卡在 apt 上

`Check (Windows x64 target)` 的 mingw 安装连续三次卡在 mirror 上，12 分钟整被
step timeout 掐断，日志里只剩一句 `cancelled` —— 又一次「慢到看不出是哪儿的问题」。

两条加固（`ci.yml` 与 `release.yml` 必须同改）：

- **第一次先 `apt-get install`，不 `update`**。runner 镜像自带 apt 索引，装得上就
  省掉整条 mirror 往返；这是唯一一条完全不依赖 mirror 的路。以前是先 `update`，
  而 update 卡住时 `install` 根本没机会跑。
- **整个 step 一个总预算** `deadline=$((SECONDS + 600))`，超了就停并打印原因。
  被 step timeout 掐成 `cancelled` 是最差的结局：不是失败也不是成功，还查不出是谁。

`tools/check-ci.js` 这一项从「查三条字符串」改成**两个文件各查六条**，把
「改一处要改两处」变成机器守的事。
