# v1.8.58 —— dev 的调试信息从 `debug = 2` 降到 `debug = 1`

没有功能改动，改的是一行 `Cargo.toml`。起因是一个好问题：**Rust 的 debug 构建为什么
这么占磁盘，能不能小一点。**

## 先量，再说

同一个仓库、同一份代码，每次 `cargo clean --profile dev` 之后重新
`cargo test --workspace --no-run`（36 个测试二进制，每个都链接一份 `finweb`）：

| `debug` | `target/debug/deps` | `target/debug` 合计 | 最大的测试二进制 |
|---------|---------------------|--------------------|------------------|
| `2`（Rust 默认） | 9.1 GB | **13 GB** | 283 MB |
| `1`（本版起） | 6.2 GB | **8.4 GB** | 188 MB |
| `0` | 2.9 GB | **4.0 GB** | 75 MB |

单看一个 crate 的 rlib（`libfinweb`，259 MB → 158 MB → 98 MB）：`debug = 1` 省 39%，
`debug = 0` 省 62%。

## 为什么大：不是「符号没删」，是「每份实例都带一份」

`debug = 2` 生成完整 DWARF：变量、类型、内联信息、泛型**每个实例化**都存一份。这个
仓库泛型用得多（`Money`、`ReportTable`、axum 的 handler `Future`、`serde` 的每个
`Serialize` 组合），同一个结构的调试信息在几十个实例里各存一遍。

再叠上三件事：

1. **36 个测试二进制**，每个静态链接一整套 crate —— 同一份调试信息在磁盘上出现 36 次；
2. **增量编译的中间态**（`target/debug/incremental`）与 `deps/` 里的旧 rlib 都不删，
   改一天代码能堆到 45 GB；
3. **`--release` 默认没有这些**（`incremental = false` + `strip = true`），所以
   `target/release` 只 543 MB —— 同代码差 20 倍以上。

## 为什么选 `debug = 1` 而不是 `0`

`debug = 1` 是「行号表」：panic 的 backtrace 依然打印 `文件:行`、函数名、模块路径 ——
日常排查那个崩溃点在哪一行，够了。`debug = 0` 连行号都没有，backtrace 只剩地址，
得先对符号表才能看，日常反而更慢。

丢掉的只有「在 gdb/lldb 里单步看变量值」。需要时临时覆盖，不改文件：

```bash
CARGO_PROFILE_DEV_DEBUG=2 cargo build -p finweb
```

## 顺手记下的两条

- **积攒比选项更可怕**：干净状态 debug=1 是 8.4 GB，连跑一周测试能到 45 GB。定期
  `cargo clean --profile dev` 是常规维护，不是出事了才做。
- **不要为了省磁盘用 `cargo test --release`**：那会再生成一整套 release 测试产物，
  两份加起来更大，而且反馈从十几秒变几分钟。

## 验证

- `cargo test --workspace` **1081** 条全绿（`debug = 1` 不影响任何行为）。
- 五个自检全过。
