# v1.8.27 —— 打印预览设置：把「纸面版式」和「参数校验」各自收敛到一处

这一版做的是用户提的两件事：**优化系统设置、优化打印预览设置**。两件事看着不搭，
其实是同一个毛病：**同一件事写在两个地方，迟早会分叉**。

## 一、打印版式从「写死在代码里」变成「账套参数」

改之前，纸张方向、字号、页边距、页码、落款**全都没有设置项**：

- 网页端 `report_html.rs` 直接生成一份固定样式的 HTML；
- 桌面端 `finui::views::export::sheet_to_html` 把 CSS 硬编码在 `format!` 里。

两边各写各的。这种分叉不会报编译错误，只会表现为「网页打印有页码、桌面打印没有」
「网页横向、桌面竖向」——而**没有人会同时打开两处源码比对**，用户只会说
「打印出来怪怪的」，然后没人能复现。

现在规则只有一份，放在新模块 `fincore::print`：

```rust
pub struct PrintOptions {
    pub orientation: String,   // auto | portrait | landscape
    pub font_pt: u8,           // 9–14
    pub margin_mm: u8,         // 5–30
    pub show_company: bool,    // 编制单位
    pub show_printed_at: bool, // 打印时间
    pub show_page_no: bool,    // 页码
    pub show_signatures: bool, // 落款
    pub sign_line: String,     // 制表 / 审核 / 负责人（可改）
}
```

它存在 `BookOptions.print` 里，也就是**跟随账套**而不是跟随某台电脑。理由很朴素：
小工厂常常「办公室打报表、宿舍看电脑」，同一份报表在两台机器上打出两种版式是没
道理的；而「这套账的打印口径」本来就属于账套。旧账套没有这个字段时按 `serde(default)`
取默认值，不追溯改存量行为。

几处具体做法：

- **自动横向**：列数 > 8 转横向。A4 纵向扣掉页边距约 186mm，一列内容平均要占 20mm
  以上，8 列就已经挤到折行。显式选了纵向/横向则听用户的。
- **页码**：`@page { @bottom-right { content: "第 " counter(page) " 页 / 共 " counter(pages) " 页" } }`。
  这是浏览器里唯一能拿到页数的地方。旧内核（Chrome 131 之前等）不认识页边距盒子，
  会**整块忽略而不报错**——表现为「勾了页码但纸上没有」。所以设置页的说明文字直接
  写清这个前提，别让人以为是功能没做。
- **跨页**：`tr,td,th { break-inside: avoid }` + `thead { display: table-header-group }`，
  行不会被切成两半，表头每页重复。

## 二、对齐方式按「列内容」判断，不再「最后一列右对齐」

老的 `sheet_to_html` 里有这么一条：

```css
td:last-child, th:last-child { text-align: right; }
```

这是个把**报表结构**硬编码进**样式**的假设：利润表最后一列是金额，所以右对齐「看起来
对」。可凭证清单、明细账、会计科目、辅助档案的最后一列都是备注或摘要，硬性右对齐会把
整列文字顶到右边，看着像排版坏了。

改成看内容：非空单元格里九成以上能解析成金额（认千分位、会计括号负数 `(1,000.00)`、
货币符号），才算金额列 → 右对齐 + `font-variant-numeric: tabular-nums`（数字等宽，
上下对得齐）。

## 三、零值印 `0.00`，不再留空

财务惯例「零不印」只在纸面上成立。到了屏幕上，一片空白会被当成「金额列没取到数 /
接口返回缺列」——用户实际就是这么报障的。而接口（`table_json`）和网页端一直印 `0.00`，
只有打印页单独留空，属于同一张表两套口径。统一成 `0.00`。

## 四、账套参数保存前统一校验

写账套参数的路径有三条：桌面「账套参数」页、网页 `PUT /api/options`、建账向导。校验
写在界面里，就等于「哪条路径忘了调，哪条路径就能写进脏数据」。实际情况是：网页端自己
手写了一遍「级长 / 凭证字号」检查，桌面端只校了「期间能解析」「级长能解析成数字」，
同一个字段两套规则。这类分叉最后都表现为「网页存得进、桌面存不进」或者反过来，而使用者
只会认为「保存按钮有时候不灵」。

现在收敛成两处：

- `BookOptions::validate()`（`fincore`，不查库）：级长非空且每级 1–12 位、最多 8 级；
  凭证字号不能有空白项；本位币非空；业务默认科目六项非空且是科目编码；打印设置的范围
  与落款非空。
- `findb::accounts::check_biz_accounts()`（查库）：六个业务默认科目**必须存在、必须是
  末级科目**。

第二道特别值得说：`biz_accounts` 被收付款单、发货收入、暂估入库、盘点等十几条自动生成
凭证的路径直接拿去当分录科目。填错了（比如把应收科目填成一级科目 `1122`）不会有任何
提示——平时看不出来，等到某天点「发货」才报「科目 1122 不能直接记账」，而那时候单据
已经开出去了。人只会觉得「系统坏了」，不会想到是半年前账套参数里填错一位。

`Db::set_options` 是唯一的落库入口，所以校验放在这里：三条路径一起受保护。

## 五、两端接线

- 网页：四个打印 handler 读 `db.options().print`；设置页新增「打印预览」面板，保存时
  把 `print` 原样合并回去（`PUT /api/options` 是**整个对象覆盖**，不带回去就会把用户
  刚调好的版式重置成默认）。
- 「试打一张」用 `?po_orient=&po_font=&po_margin=&po_company=…` 覆盖**本次**渲染，
  不写库——不然用户只能「改 → 存 → 去报表 → 打印 → 发现不对 → 回来再改」。非法值一律
  忽略并沿用账套设置：宁可打不出新样式，也不要打个 500。
- 桌面：`sheet_to_html(sheet, title, opts)` 收 `&BookOptions`（既拿版式也拿企业名称），
  19 处 `run_export` 调用点改传 `&ctx.db().options()`；参数页新增「打印预览」区块。

## 一处坦白

这一版中途出过一次事故：给 `BookOptions` 字面量批量补 `print` 字段时，脚本按行匹配
`BookOptions {` 没排除 `pub struct BookOptions {` / `impl BookOptions {`，把定义也插坏了；
随后我为了回退错误插入执行了 `git checkout -- crates/`，**把当时所有未提交的改动全抹掉了**
（仓库没有 stash、也没有中间提交）。

教训记在这里：批量改代码之前先打一个 WIP 提交或 `git stash`；`git checkout -- <目录>`
在未提交的工作区里不是「撤销一行」，是**销毁**。全部改动后来按清单重建，测试与变异都重跑过，
但那次返工是可以避免的。
