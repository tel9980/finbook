# v1.8.60 —— 看不见的部门，会骗人的页码

这一版修一个「数据其实过滤对了、页码却骗人」的问题，另把全仓格式统一到一把尺子上。

## 一、部门范围：只判「打了标签」的分录

`DataScope.depts` 早就存着了，也早就随登录态发下去了，但 `can_see_voucher` 只按科目区间
过滤 —— 于是设了部门范围的会计，照样看得见全公司的凭证。

补的时候最先要定的是**没打部门标签的分录算谁的**：

- 按「每一张凭证的分录都必须落在范围内」—— 没填部门的凭证一条也看不见；
- 按「有标签才判，没标签放行」（`allows_dept("")` 恒真）—— 只收窄真正标注过的那部分。

选后者。本厂绝大多数凭证不填部门（只有费用类才拆部门），前一种口径会让部门会计凭空
丢掉一大半账 —— 这比越权更常见，也更容易被当成「软件坏了」。科目与部门两个范围是
**AND**：都是「限制」，不是「任选其一」。

## 二、光过滤不够：还得下推到 SQL

`list_vouchers_page` 先取一页、再按 `can_see_voucher` 逐张过滤，同时用 `COUNT(*)` 算总数。
两者不同源就会出事，所以那里本来就蹲着一句断言：

```rust
debug_assert_eq!(before, rows.len(), "SQL 下推的数据范围与 can_see_voucher 不一致，total 会算错页码");
```

部门范围只加在 Rust 侧的那一半里，这句在 debug 下直接 panic；release 下更阴：total 比
实际能翻到的张数大，**页码是假的** —— 点第 3 页空白，人只会以为账没了。

做法：`VoucherQuery` 加 `scope_depts`，`build_where` 用 `NOT EXISTS` 整段匹配：

```sql
AND NOT EXISTS(SELECT 1 FROM voucher_entry e WHERE e.voucher_id=v.id
    AND (char(31)||e.aux_key||char(31)) LIKE '%\x1fdept=%'      -- 这张凭证带部门标签吗
    AND NOT ( (char(31)||e.aux_key||char(31)) LIKE '%\x1fdept=D01\x1f%' OR … ))
```

两个细节是故意的：

1. **不用裸子串**。`aux_key` 里还挤着职员、项目、存货，`dept=D01` 裸着找会撞进别人的值里。
2. **`depts` 原样拷贝**，不 trim、不过滤空串。Rust 侧对分录值做 trim，SQL 按原值整段比；
   归一化只会让两侧判定分叉 —— 而分叉的后果就是上面那个假页码。

顺带把 `with_account_scope` 改名 `with_range_scope`：它现在管的不止科目区间了。

## 三、三条用例，一层比一层难糊弄

| 层 | 用例 | 钉住什么 |
|----|------|----------|
| fincore | `can_see_voucher_dept_scope_only_judges_tagged_entries` | 空部门放行 / 一条越界整张不可见 / 科目与部门 AND / 空白等同未标注 |
| findb | `list_page_dept_scope_matches_can_see_voucher` | SQL 下推集合 == `can_see_voucher` 集合 == **显式期望**（5 张凭证 × 5 组部门） |
| finweb | `voucher_page_total_respects_dept_scope` | 部门会计 `total=6`、别部门那批不出现、合计金额跟着变 |

findb 那条特意写成三方比对：只比「SQL == Rust」的话，两边一起错就查不出来 —— 而这正是
「下推写漏了一维」的典型形态。

真跑一遍才有底气：把 `if !q.scope_depts.is_empty()` 改成 `if false && …`，
findb 那条立刻红（`left: [1,2,3,4,5] right: [1,3,4]`），还原后复绿。

## 四、全仓 fmt：一把尺子，和一条教训

`cargo fmt --all`：**94 个文件、+2582/−1398**。CI 里没有 fmt 门禁，漂移就只增不减
（`handlers.rs` 一个文件 120 处、`advanced.rs` 22 处、`reports.rs` 20 处）。

顺手踩到一条值得记的：**变异清单里的 `from` 字面量也是代码**。fmt 一跑，6 条变异的
`from` 串跟源码对不上；`check-ci.js` 立刻报红（它专门查这件事），于是逐条重锚。

重锚后先跑了 6 条，**2 条照样通过**。原因是我把 `from` 锚到了长得一模一样的另一处：
`aux_kind_of_dim` 而不是 `aux_kind_of`、辅助档案导出的闭包而不是存货导出的列向量。
改坏点找错，等于这条变异从此测别的东西。**字面量对得上 ≠ 锚对了位置，只有真跑一遍
看它红不红才算数。**

反过来也说明这道自检值钱：没有它，这 6 条会在下一次跑变异时静悄悄退化成「永远通过」。
