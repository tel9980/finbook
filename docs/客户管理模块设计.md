# 客户管理模块 · 设计

> 定位：**给已有的客户主数据加一个「以客户为主体」的视图层**，不新增第二份客户主数据。
> 状态：**已实现**（列表 / 详情·往来明细 / 账龄 / 交易历史 / 催款）。实现顺序见文末。

## 0. 先说为什么不是「新建客户管理模块」

系统里客户主数据**已经存在**，而且是全系统唯一的一份：

```
aux_entity(kind='customer')   code / name / parent_code / disabled / props_json / memo
```

它已经被这些地方引用：凭证辅助核算、销售订单、发货通知、收款单、往来核销、账龄、
催款、对账单、期初挂账导入。

再新建一张客户表，等于两份主数据 + 一个同步问题，且必然出现
「销售单据里认的客户」与「客户管理里看到的客户」对不上。所以本模块
**一个字节的新数据都不加**，全部从既有表派生。

## 2. 缺口 —— 这才是模块该做的

> 本节记录**立项时的缺口**（为什么值得做）。现已按下方设计逐一落地：
> 客户 360 视图、余额汇总、未核销明细、交易历史、客户维度报表均已有页面入口。

| 缺口 | 现状 |
|------|------|
| **客户 360 视图** | 没有任何页面能「打开一个客户，看他全部往来」。账龄以**科目**为主体、催款以**单据**为主体，都不是以客户为主体 |
| 客户余额汇总 | 「这个客户现在欠我多少」要自己去科目余额表翻 1122 再按辅助核算拆 |
| 未核销明细 | 「这个客户还有哪些单没核销」没有按客户维度的入口 |
| 交易历史 | 「这个客户买过什么」要从 so / shipment / payment 三张表自己拼 |
| 客户维度报表 | 现有报表都是科目/辅助维度，没有客户维度 |

## 3. 设计

### 3.1 一个入口，两个视图

侧栏新增 `customers`（分组「销售」，`perm: "report"`）。
挂 `report` 而不是 `aux_edit`：出纳要看（催款要看客户欠多少），但不该能改客户档案。
沿用既有权限位，**不新增 permission**。

```
客户管理（customers）
├─ 列表视图（默认）：一行一个客户
│    编码 / 名称 / 层级 / 应收余额 / 未核销笔数 / 最长账龄 / 本年销售额 / 本年回款
└─ 详情视图（点行进入，一个客户一页）
     ├─ 顶部：应收余额、已核销、未核销、本年销售额、本年回款、信用额度占用
     ├─ Tab 1 往来明细：期初挂账 + 已记账分录（未核销/已核销），可直接点「核销」
     ├─ Tab 2 账龄：复用 settle::aging 的桶，**同一套口径**
     ├─ Tab 3 交易历史：报价 / 销售订单 / 发货 / 收款，按日期倒序
     └─ Tab 4 催款记录：dunning + ar_statement 状态
```

### 3.2 三个必须守住的规则

**① 余额只有一处算法**
所有余额走 `settle::open_entries`，**不许新写一份 SQL**。
理由：H-3 口径（只认已记账分录）是全仓共识，新模块自己算一遍就出现两套数字，
而「为什么这个客户欠款和往来核销页不一样」是最难查的一类问题。

**② `include_all=false`**
往来明细默认只显示已记账。**未记账的往来行不参与任何余额计算**。
如果要显示，必须像 `open_entries_with(posted_only=false)` 那样显式标注「仅供查看」
—— 前端已有这个约定（`OpenEntry.posted` 字段），照做。

**③ 不新增信用管理**
信用额度字段已存在、拦截已生效，本模块**只读展示**占用情况，
不加授信审批、额度调整日志、超额白名单。理由是你明确说了不做信用管理；
而且在没有审批流的前提下，加了额度调整日志也只是在给一个不需要审批的动作做记录。

### 3.3 接口

```
GET /api/customers?period=&q=&only_open=      列表（一行一客户，含聚合）
GET /api/customers/:code?period=              顶部汇总 + 往来明细
GET /api/customers/:code/aging?period=&as_of= 账龄（复用 aging 的桶定义）
GET /api/customers/:code/trade?from=&to=      交易历史（报价/订单/发货/收款）
GET /api/customers/:code/dunning              催款 + 对账单状态
```

全部 `user.require(Perm::Report)`。**只读**，没有 POST/PUT/DELETE ——
改档案仍然只有 `aux` 那一个入口。

### 3.4 数据来源对照（每个数字都要能说出出处）

| 界面字段 | 来源 | 口径 |
|---------|------|------|
| 应收余额 | `settle::open_entries("1122")` 按 `aux_key` 汇总 | 已记账，含负数（预收）；**1122 自动含子科目**，见 §5.1 |
| 未核销笔数 / 金额 | 同上，`settled < amount` | 同上 |
| 最长账龄 | `settle::aging` 的最早未清账龄 | 同上 |
| 本年销售额 | `sales_order` 已确认/已发货 × 不含税 | 单据口径，**不是**收入科目口径 |
| 本年回款 | `receipt_doc`（**只取 `audited`**），按 `party` 汇总 | 见下方「为什么是 receipt_doc」 |
| 信用占用 | `sales::credit_check` | 已确认非作废订单减已收 |

### 为什么回款取 `receipt_doc` 而不是 `so_payment`

设计初稿把这条列为「实现前必须先解决的问题」，现已查清（2026-10-01）：

`add_so_payment`（`handlers.rs:8095-8096`）**一次调用同时写两张表** ——

```rust
so_payment_add(...)   → so_payment   （挂在 so_id 上）
receipt_create(...)   → receipt_doc  （挂在 party 上，status='draft'）
```

同一笔钱，两处记录。而两表之间**没有指向彼此的外键**：`so_payment` 没有 `doc_id`，
`receipt_doc` 没有 `so_id`，勾稽靠 `doc_link` 单独建边。

所以同时 SUM 两张表**必然每笔钱数两次** —— 上面那个函数就是同时写的。
选 `receipt_doc` 且只取 `audited`，三个理由：

1. **会计口径**：收付款单审核时才出凭证并自动核销，草稿单的钱还没进账，
   不该算「已回款」。这与全仓 H-3（只认已记账）一致。
2. **完整性**：`receipt_create` 有三个独立入口（资金管理、采购付款、销售收款），
   不走销售订单的收款只进 `receipt_doc`。反过来按订单汇总 `so_payment` 会**漏掉**它们。
3. `receipt_doc` 带 `voucher_id`，能直接回答「这笔回款对应哪张凭证」。

> 对 `so_payment` 的正确用法是**订单维度**（「这张单收了多少钱」），
> 不是客户维度。两者不冲突，只是不能相加。

## 5. 实现前必须先解决的 2 件事

> 三个原问题已全部查清（2026-10-01）。结论见下。

### 5.1 ✅ 已解决：应收口径 = `1122` 及其子科目，**不需要改代码**

初稿以为「1122 是不是唯一应收科目」是个待决策项。查清后：

`settle::open_entries_with` 的 SQL 已经是

```sql
WHERE (e.account_code = ?1 OR e.account_code LIKE ?1||'%')
```

**传一级科目就自动匹配全部子科目**。而科目表里 `1122` 下预置了
`112201 应收货款` / `112202 应收其他`，`2202` 下有 `220201` / `220202`。

所以「按客户汇总应收」直接传 `'1122'` 即可，**不需要逐个子科目相加，
也不需要新写 SQL**。若账套自定义了 `1122xx`，同样自动被包含。

范围界定：应收类共 8 个一级科目（1121/1122/1123/1131/1132/1221/1231/1531），
但**本模块只统计 1122 系**（与全系统现有口径一致 —— 前端 `settle/aging`、
工作台的应收/应付都是传 1122 / 2202）。理由：1121 应收票据、1123 预付账款、
1221 其他应收、1231 坏账准备各有各的性质，混进「客户欠款」会让数字没法解释。
若将来要扩，扩的是**科目清单**，不是算法。

### 5.2 ✅ 已解决：`parent_code` 环校验已补上（2026-10-01，`cbd3bf3`）

原问题：编辑 `parent_code` 时没有环校验，按层级汇总会死循环。

已修（`auxs.rs:225` 的 `check_parent` 加 `find_parent_cycle` / `children_of`，
`insert` 与 `update` 都过校验），覆盖自环、多级环、上级不存在三种情况，
并有 5 条测试 + 3 个变异探针钉住。

层级汇总是**可选展示**：平铺（只看自己）不需要它，加「按上级分组」才需要。
既然环已不可能出现，递归是安全的。

### 5.3 ✅ 已定（2026-10-01）：列表**默认平铺，不做树视图**

调查了三个事实，结论一致：

| 事实 | 证据 |
|---|---|
| **没有任何数据有层级** | 建库种子里**没有任何** `aux_entity` 行（那条 SQL 只是 `insert` 函数的语句）；全仓库 `parent_code: Some(...)` **0 处** |
| **业务表不存层级路径** | `sales_order` / `receipt_doc` / `settle_record` / `voucher_entry` 四张表都只有平级 `customer_code` / `party`，无任何 parent 字段 |
| **前端从未做过层级聚合** | `app.js` 里 `parent_code` 只出现在编辑弹窗的读写（10346/10370）与列表的一列（10306），没有任何分组或递归 |

所以「默认按层级树展开」是**为一个不存在的数据形态做界面**：多一层点击、
每行递归、界面上一层分组表头，换来一堆空分组。

决定：**默认平铺**，按未核销余额倒序（`customers::list` 已这样实现）。
若将来真有人用层级，做成**筛选器**（「只看某上级下的客户」，一层、不递归）
而不是树视图 —— 层级是 `aux_entity` 的**通用字段**（存货、项目、部门都有），
客户页不该承担这个语义。
