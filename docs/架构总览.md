# FinBook 架构总览

> 这份文档回答三个问题：**东西都在哪**（模块地图）、**谁能调谁**（依赖方向）、
> **加一个新功能要动哪些地方**（扩展路径）。
> 需要「怎么用」看 [功能参考.md](功能参考.md)，需要「记账怎么记」看 [日常记账手册.md](日常记账手册.md)。

## 一、四层结构与依赖方向

```
                 ┌──────────────────────────────────────────┐
                 │  finbook   （桌面二进制入口 main.rs）      │
                 │  finui     （egui 桌面界面，45 个视图）    │
                 │  finweb    （axum Web 服务 + 前端 app*.js）│
                 └───────────────┬──────────────────────────┘
                                 │ 只往下调
                 ┌───────────────▼──────────────────────────┐
                 │  findb   （SQLite 持久化 + 业务闭环 + 导入导出）│
                 │  60 个顶层模块，69k 行                     │
                 └───────────────┬──────────────────────────┘
                                 │ 只往下调
                 ┌───────────────▼──────────────────────────┐
                 │  fincore （纯计算：科目/凭证模型/引擎/报表模板）│
                 │  无 IO、无 SQL、无 UI，可单独单测           │
                 └──────────────────────────────────────────┘
```

**三条铁律**（越线就要在评审里说明理由）：

1. **`fincore` 不做 IO**。它只接受「已经取出来的数据」（`BalanceRow`、`Voucher`、`Account`），
   算出结果。所以报表口径、凭证校验、个税、折旧、成本、账龄全在这里，测试不需要建库。
2. **业务规则只写一遍，写在 `findb`/`fincore`**。桌面端（37.6k 行）和 Web 端（27.1k 行 + 前端 910KB）
   各有界面，**但同一件事不能各写一遍**——历史上「打印版式」和「参数校验」就各写了两份，
   结果是同一张报表在两端打出两种样子（见功能参考 §4.79）。
   界面的职责是「收集参数 → 调 findb → 展示结果」，不允许自己算钱。
3. **账套是单文件 SQLite**（`.fbk`）。所有持久化都经 `findb`，任何模块都不许自己 `open` 数据库。

## 四、`finui`（桌面，45 个视图）与 `finweb`（Web，22 个 handler）

| 侧 | 结构 |
|---|---|
| `crates/finui/src/views/` | 45 个视图：dashboard / voucher_list / voucher_edit / ledger / balance_table / reports / period_end / settle_view / bank_rec / funds / payroll / invoice_view / assets / inventory / inventory_deep / scm_deep / advanced / automation / budget / custom_report / dim_profit / profit_sheet / process / month_brief / begin* / users / security / backup / options … |
| `crates/finweb/src/handlers/` | 21 个子模块：auth / books / platform / voucher / reports / settle / funds / hr / inventory / procure / sales / prod / consign / fixture / piecepay / processfee / rework / profit_sheet / assets / export / misc |
| `crates/finweb/static/` | 16 份 `app*.js`（经典 script，按业务切；加载顺序见 `index.html`）+ `util.js` / `icons.js` / `style.css` |

**两端共享的只有 `fincore` + `findb`。** 一端的界面改动不该让另一端的行为变化；
如果发现某条规则只有一端实现了，那就是 bug（B3 那组表驱动测试专门钉这件事）。

## 五、一次取数的完整路径

```
界面（finui 视图 / finweb handler / app*.js）
   │  ① 收集查询参数（期间、科目、辅助维度、是否含未记账）
   ▼
findb::balances::BalanceQuery + BalanceSnapshot::load
   │  ② 查 voucher_entry 汇总（缓存在快照里，key 含 prepared_by 与写入计数）
   ▼
findb 把「借正贷负」的原始余额交给 fincore
   │  ③ fincore::report::* 按模板组织成行（资产负债表/利润表/现金流量表/自定义）
   ▼
界面渲染 / 打印（print.rs 版式）/ 导出（exports）
```

三条必须记住的口径：

- **报表只认已记账凭证**。草稿不参与，所以「首页净利润 ≠ 利润表」十次有九次是有凭证没记账。
- **余额符号约定只有一个地方**：`fincore::balance::signed_to_dir_amount`（正=借、负=贷）。
  想在别处「顺手取反」= 埋一个只有月结那天才炸的雷。
- **利润表口径要用 `with_exclude_carry(true)`**：结转损益凭证自己会把损益类科目冲平，
  不排除它，本月收入费用会变成 0。

## 六、加一个新功能要动哪些地方

以「新增一张业务单据（比如委托加工结算单）」为例，标准路径是七步：

1. **表结构**：`crates/findb/src/schema.rs` 加表 + 索引（并写迁移；老账套打开要能自动升级）。
2. **模型与仓储**：在合适域的模块里（如 `findb/src/scm2.rs` 或新建模块）加 `struct` + `insert/update/list/get`。
   编号、日期、金额一律走公共工具，不要自己拼。
3. **业务规则**：能纯计算的（金额拆分、校验、结转、账龄）放 `fincore::engine::*`，配单测；
   需要读库的放 `findb`，配 `crates/findb/tests/*.rs` 集成测试。
4. **出凭证**：一律调 `vouchers::save` + `post`，草稿由用户点记账；凭证来源用
   `VoucherSource::Business`，摘要写清「哪张单、哪个往来单位」。
5. **两端界面**：`finui/src/views/` 加视图 + `finweb/src/handlers/` 加 handler +
   `static/app-*.js` 加页面（**新脚本要同步 `index.html` 与它引用顺序**，`asset_version()` 会自动扫）。
6. **检查与变异**：给关键行为加一条静态检查（`tools/check-*.js`）或 Rust 测试，并**同时加一条变异**
   （`tools/mutate-rust.js` / `mutate-check.js`）证明这条检查真的会红。
7. **文档**：`docs/功能参考.md` 加一节；用户可见的改动写进 `docs/releases/v1.8.xx.md`。

> 第 6 步最容易省，也最不该省。这个仓库最贵的教训是：**检查写成永远通过的样子，
> 比没有检查更危险**——它让人以为有网。

## 七、已知的命名债（不是 bug，是历史）

同一域里模块名靠猜的地方，动之前先看这里，别新加第四个：

| 现状 | 实际关系 | 建议 |
|---|---|---|
| `stock` / `stocktake` / `warehouse` | 三处都碰存货：前者「盘点+批次」、中者「盘点单流程」、后者「仓库档案」 | 新功能进 `stocktake`（流程）或 `inventory2`（深度），别再开新模块 |
| `inventory2` / `scm` / `scm2` | `scm` 是订单与 BOM，`scm2` 是暂估对账等深化，`inventory2` 是库存深度 | 采购销售相关的进 `scm2`，库存形态的进 `inventory2` |
| `advanced` / `business` / `mgmt` / `workflow` | 四个「什么都装」的筐：高级功能 / 业务闭环 / 管理会计 / 审批流 | 新代码优先进具体域模块；确实无处可放才进这四个，并在模块头写一句归属理由 |

## 八、规模与自检

| 项 | 数值 |
|---|---|
| `fincore` / `findb` / `finui` / `finweb` | 约 12.7k / 68k / 37.6k / 27.1k 行 |
| 前端脚本 | 16 份 `app*.js`，拼合约 910KB（gzip 后约 240KB，另有未拼入的 `util.js`/`icons.js`） |
| 账套表结构 | 127 张表 / 134 个索引 |
| 测试 | `cargo test --workspace` 1199 个用例（0 failed）；`crates/findb/tests` 8 个集成文件 |
| 静态检查 | `tools/check-*.js`（CI 配置/编码/前端行为/设计文档引用）+ 191 条 Rust 变异 + 22 条前端变异 |
| lint 闸门 | `cargo clippy -- -D warnings`（只 `-A` 五类既定设计风格） |

改完代码在本地跑这四行就够了：

```bash
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings -A clippy::too_many_arguments \
  -A clippy::type_complexity -A clippy::large_enum_variant \
  -A clippy::should_implement_trait -A clippy::field_reassign_with_default
node tools/check-ci.js
node tools/check-js.js && node tools/check-app-render.js && node tools/check-simple-nav.js
```
