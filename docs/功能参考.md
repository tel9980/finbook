## 4. 业务三件套 + 管理会计三件套

### 4.1 存货核算（业务 → 存货）

- **出入库单**：采购入库 / 销售出库 / 其他出入库；出库行数量为负，成本由引擎计算
- **存货盘点**：盘点单按仓库**快照账面** → 录实盘 → 应用生成 其他入库/其他出库 流水 + **盘盈盘亏凭证**（借/贷 1901 待处理财产损溢，金额 = 差异 × 标准价；未配标准价只调流水）；草稿可删、已应用不可删（冲回做反向盘点），仓储作业权限（仓管员专属）
- **批次与库位**：存货档案配「保质期天数」→ 批号自动生成 `BT+日期+序号`（或手工指定）；**批次余额 = 库存流水按 (存货,批号) 汇总——与普通库存同一本账**；批次登记（其他入库/出库带批号、仓库、初始库位）；**FEFO 近效期先出推荐**（无效期批次按生产日期）；**临期预警**（默认30天窗口）；库位主数据（存储/拣货/隔离）；仓储作业权限
- **收发存汇总**：期初 / 本期入库 / 本期出库 / 期末，按存货 + 仓库汇总
- **成本核算**：**移动加权平均 / FIFO** 两种计价引擎，结转销售成本一键生成凭证

### 4.2 工资与个税（业务 → 工资）

- **工资表**：按部门/职员录入应发、三险一金、专项附加扣除
- **个税计算**：累计预扣法（计税基数 = 应发 − 三险一金 − 专项附加 − 5000×月数，首月 3% 起档），自动算出本期应扣个税
- **凭证生成**：计提工资 / 发放 / 扣个税 / 扣社保四组分录一键生成

### 4.3 费用报销（业务 → 报销）

- 状态机：**提交 → 审批 → 付款 → 完结**（可驳回），全程留痕（申请人 / 审批人 / 付款人）
- 审批通过后自动生成报销凭证（借：管理费用等 / 贷：其他应收款或银行）

### 4.4 安全中心（系统 → 用户权限）

| 页签 | 功能 |
|------|------|
| 用户管理 | 管理员**新增 / 停用 / 改密 / 重置绑定设备**普通账号，设定角色与细粒度权限；**强制改密**横幅（口令过期提示） |
| 我的口令 | 任意登录用户可在此**修改自己的口令**（验证旧口令 + 策略校验），被强制改密的用户在此完成首次改密 |
| 口令策略 | 最小长度、复杂度（字母+数字）、有效期天数、**连续错 N 次锁定 M 分钟**、会话空闲超时分钟 |
| 登录审计 | 每次登录 / 失败 / 锁定 / 超时登出全部留痕，可按用户/时间筛选 |
| 数据范围 | 按用户配置可见辅助对象（部份/全部）。**部门范围**已接入凭证列表/导出与明细类账簿（明细账、总账、日记账、日报表）；余额表与财务报表固定公司口径（按部门切分录会切不平，见 §4.104） |

> **默认口令策略**：≥8 位且含字母+数字、有效期 90 天、错 5 次锁 15 分钟、闲置 30 分钟自动登出。
> **默认管理员**：账套内只有 `admin` 一个内置账号（默认口令 `admin123`，首次登录强制改密）；其余账号由管理员在「用户管理」开通。

### 4.5 账号设备绑定（一人一设备）

为防止同一账号在多处同时登录，FinBook 在每次登录时采集**设备指纹**并绑定账号：

- **首次登录自动绑定**当前设备；之后**换设备登录会被拒绝**（提示"该账号已绑定设备 XXX"）。
- **管理员不受此限制**，可在任意设备登录，也不绑定设备。
- 员工换电脑时，由**管理员在「用户管理」点击「重置绑定」**解除原绑定，该账号即可在新设备重新登录。
- 设备指纹来源：Windows 读 `MachineGuid`、Linux 读 `/etc/machine-id`、macOS 读 `IOPlatformUUID`，
  兜底用「主机名 + 用户名」哈希；绑定的设备名显示在用户列表「绑定设备」列，方便管理员辨认。

### 4.6 导出管控（普通账户只能打印，不能导出）

报表与账簿的"导出 Excel / 导出 CSV"按钮**需要 `Export` 权限**，仅**系统管理员与财务主管**拥有：

- **普通账户（会计 / 出纳 / 审计 / 只读）看不到"导出"按钮**，界面显示灰字提示"无导出权限，仅可打印预览"。
- 所有能看报表的账号都有**「打印预览」按钮**：把数据生成一份带打印样式的 HTML，用系统默认浏览器打开并自动弹出打印对话框。
  打印走的是 HTML，**不会以文件形式落地**，满足"只能打印、不能把整表数据带出"的管控。
- 凭证的 Excel 导出同样仅管理员 / 财务主管可用；屏幕内的凭证打印预览人人可看。

### 4.7 管理会计三件套

| 模块 | 说明 |
|------|------|
| **预算**（管理会计 → 预算） | 按科目 + 期间编制预算额；执行分析：实际发生 vs 预算、执行率、超支标红 |
| **多维损益**（管理会计 → 多维损益） | 按部门 / 项目 / 客户任意维度切分收入成本费用，输出多口径利润表 |

### 4.8 凭证模板 + 常用摘要（凭证 → 模板）

- **凭证模板**：把常做的分录组合存成模板（含借贷方向、金额公式、辅助核算），到期（月/季/年）提醒，一键生成草稿凭证
- **常用摘要**：与凭证录入联动，热度自动排序（见 §2.5）

### 4.9 出纳作业台（出纳 → 资金管理）

出纳岗位的完整闭环（出纳角色默认 `填制凭证 + 出纳签字 + 账簿报表` 即可上岗，记账/审核仍归会计）：

| 能力 | 说明 |
|------|------|
| **出纳日记账** | 资金管理 → 日记账：现金/银行科目逐笔（仅已记账 H-3）+ 滚动余额；**日清标记**按科目按日核对封账；**收款/付款登记**一键跳转凭证录入并预填科目 |
| **现金盘点** | 账面按当日资金日报口径快照 → 实盘录入 → 差异一键生成盘盈盘亏凭证（对方科目 1901 待处理财产损溢）；账实相符记录可直接删除 |
| **支票登记簿** | 票号/类型/付款科目/收款人/金额，开出 ↔ 作废流转；纯备查簿不入账，删除无凭证联动 |
| **员工借支** | 建单 → 支付（借 其他应收款-员工 / 贷 资金，同事务出凭证）→ 核销（冲账费用 + 退回现金 / 贷 其他应收款），超额与状态机守卫、幂等 |
| **票据 / 融资台账** | 贴现、背书、兑付、融资到账与结清**同事务自动生成台账凭证**（存量台账可「生成凭证」回填），资金台账与总账不再脱节 |
| **资金日报（按日）** | 上日结余 / 本日收支 / 日末结存，按日翻页（仅已记账） |
| **资金预算** | 现金/银行科目的预算 vs 已记账实际执行（预算行在预算管理维护） |
| **出纳签字** | 账套参数开启后，涉现金/银行的凭证记账前必须出纳签字（凭证弹窗按钮 + 账套参数开关），日记账带签字列 |
| **报销支付落账** | 报销单支付即自动生成付款凭证草稿（默认贷 100201），手动「生成凭证」幂等返回同一张 |
| **收付款单** | 资金管理 → 收付款（Web + 桌面）：保存即出凭证并按往来单位对未清挂账 **FIFO 自动核销**（见 §4.10） |

### 4.10 供应链全流程（对标金蝶：订单 → 出入库 → 收付款 → 会计记账）

从「创建订单」到「出纳收付」再到「会计记账」的完整链路，关键节点**同事务自动生成凭证**：

| 环节 | 动作与卡控 | 自动生成凭证 |
|------|-----------|--------------|
| **订单创建** | 销售/采购单据页「新建订单」：明细行编辑器，行金额=数量×单价、税额=金额×税率（服务端计算），草稿自由改删 | — |
| **订单确认** | 草稿 → 已确认（可作废）；**客户信用控制**：客户档案「信用额度」（0=不限），确认时校验「已确认订单占用（总额−已收款）」≤ 额度，超限拒绝；草稿不占额度 | — |
| **发货执行** | 已确认才能发货/退货（草稿/作废拦截）；**按比例确认收入**：收入与税额 × 本次数量÷订购总量（发货封顶未发量、退货封顶已发量不超额冲回）；订单状态随发货进度自动推进 部分发货/已完成 | **借 应收账款(客户辅助) / 贷 主营收入 / 贷 销项税**；退货出反向冲回 |
| **入库暂估** | 采购到货登记执行进度；入库未票在「采购暂估」登记（须挂真实订单）→ 同事务出凭证；到票「冲回」出反向凭证（UPDATE 条件化幂等，重复/并发冲回不出票） | **借 存货材料科目 / 贷 应付账款(订单供应商辅助)**；冲回反向 |
| **收付款** | 收付款单：选类型/资金账户/往来单位/金额 → **保存为草稿（仅台账）→ 审核时**同事务出凭证 + 对该往来单位**未清挂账按日期 FIFO 自动核销**（超出留预收/预付腿，无挂账全额预收）；审核权 = 审核人/主管（出纳录单、审核人把关），撤审删凭证回草稿；执行坞「收款/付款」落待审核单，审核后出凭证 | **收款：借 资金 / 贷 应收；付款：借 应付 / 贷 资金** |
| **核销账龄** | 自动核销进往来核销（手工/自动/账龄同口径）；**删除凭证自动清理其核销配对**，收付款单须先删凭证才可删单 | — |
| **会计记账** | 以上均为**草稿凭证**（H-3 草稿不入余额），会计审核记账后进余额与报表；涉现金银行凭证按出纳签字开关（§4.9）把关 | — |

生成科目集中在**账套参数 → 业务凭证默认科目**：应收 / 应付 / 收入 / 销项税 / 暂估材料 / 默认资金账户（须为末级科目，Web 与桌面两端可改）。

暂不覆盖（业务边界）：信用催收与账龄预警、税务发票对接、单据→凭证**可配置规则引擎**（当前为固定生成器 + 科目可配）。

### 4.11 单据套打（订单 / 收付款单）与批量打印

- **字段可选 + 一键预设**：列表里点「打印设置」勾选要打印的字段与明细列（单号 / 日期 / 状态·类型 / 客户·供应商·往来单位 / 备注 / 制单人 / 存货编码 / 名称 / 数量 / 单价 / 税率 / 金额 / 税额 / 行备注 / 合计行 / 签章栏 / 资金账户 / 关联凭证号），服务端按 `fields=` 白名单裁剪，未勾选的列头与内容都不出现；**预设**：「默认全单」一键还原 /「送货单（随车·留数量藏价格）」**保留数量供收货清点**，自动去掉 单价·税率·金额·税额·合计·状态（跟车联不带价格）；
- **多尺寸纸张**：打印设置选 `A4` / `A5 二等分(210×148)` / `三等分(99×210)` / 自定义「宽x高 mm」；`@page` 尺寸、页边距与**分页预算随纸张重算**（A4≈42 行 / A5≈20 / 三等分≈28），窄纸（<120mm）自动压缩字号行高；字段与纸张选择保存在本机浏览器（localStorage，兼容旧存储）；
- **批量 + 充分利用纸张**：列表勾选「打印所选 / 批量打印」（未勾选 = 当前期间 / 全部单据），多张单据按**行单位预算**（单据固定开销 6 行）紧凑排进同页——放不下才换页、整单不劈开（`break-inside:avoid`）；「紧凑分页」可关，改一单一页。可见列宽归一化到 100%；
- **覆盖范围**：销售订单、采购订单、收付款单（Web 三处列表勾选批量 + 打印设置；桌面收付款页签「打印全部」走同一模板）、出纳日记账「打印日记账」；凭证套打（整期间批量）、账簿套打、报表打印沿用既有通道；
- **报价单转订单**：报价单审批后一键「转订单」→ 生成草稿销售订单（税率 0 可再改）并把报价单标记 `converted`（重复转换拒绝）——订单部从 报价 → 确认 → 执行 → 打印 全程闭环。

### 4.12 工作流可视化（对标金蝶审批流设计器）

- **节点-动作模型**：开始 / 审批 / 条件 / 消息节点 + 普通 / 驳回连线；**无出边的审批节点即流程终点**；驳回走 Shift+拖拽 画出的驳回连线或节点「驳回至」；参与人 = 角色多选（留空 = 需审核权限者可批）；**会签**：strategy=all 且参与人非空时每个参与角色各需一票（同人不可重复批，未满票停留当前节点并显示「会签 x/y」）；**条件分支**：连线条件审批时求值（`amount > 5000` 等字段比较，多条出线按序匹配、空条件兜底，配置错误立即报批）。
- **SVG 画布（原生 JS，不依赖框架）**：拖拽节点（20px 钉吸）、节点蓝点拖出连线、滚轮缩放、空白拖拽平移、Delete 删除、Ctrl+Z/Y 撤销重做、小地图、适配视图、右侧属性抽屉。
- **运行时**：对已发布流程的业务单据（报价 / 请购 / 报销 / 收付款）执行审批时**自动创建实例并逐节点推进**，到终态才执行原有业务批准（收付款 = 出凭证 + 自动核销）；「运行实例」页回放轨迹（谁在何时通过/驳回哪个节点）并可就地通过/驳回（服务端校验参与人与审核权限）。
- **向后兼容**：未配置发布流程 = 走原固定审批（默认流），既有行为完全不变；设计/发布需账套管理员（`SysOption`）。桌面端设计器为后续迭代（运行审批不受限）。

### 4.13 工厂生产链：下达 → 开工 → 领料 → 完工（业务单据同步凭证）

- **下达**：`POST /api/prod` 新建生产订单（状态=已下达）——补齐此前全系统无生产订单创建入口的缺口；「MRP」结果页每行「下达」按钮按计划量一键下达。
- **开工**：已下达 → 生产中（`prod_start` 条件更新防并发），完工入库的前置状态。
- **领料**：按 **BOM × 计划量 × (1+损耗)** 展开，同事务「扣库存 + 归集生产成本 + 出领料凭证」——借 500101 生产成本-直接材料 / 贷各物料科目（数量核算）；单价取最近采购价，**无采购价回退计价配置标准价**（与盘点/暂估同口径，错误文案不变）。
- **完工入库**：仅生产中订单（条件更新防重复）；同事务「入库 + 订单推进 completed + 完工结转凭证」——借 140501 库存商品（数量核算）/ 贷 500101~03 各要素（只出非零要素）。
- **BOM Web 化**：`GET/POST /api/bom`（ProductionOps 权限）+ 报工页「维护BOM」编辑器（子件/用量/损耗率），此前 BOM 仅 findb 内部可用。
- **工序报工页 = 生产作业台**：同一订单下拉内完成 开工 / 领料出库 / 完工数量（自动带未完工数）/ 完工入库，动作后状态即时刷新；全链测试 `production_issue_complete_flow`。

- **到货即入库（采购链闭环）**：Web 采购到货此前**只做执行跟踪、不写库存流水**（`kind=purchase` 仅桌面手工单产生）——现 `po_receipt_with_stock` 同事务「执行行 + 采购入库流水」，价格=订单行单价、金额=qty×价——**这也是「最近采购价」（领料成本回退链）的真实数据源**；防呆：订单无行拒、**单价 0 拒**（0 价入库污染移动平均，下推后先补价）；退货 `po_return_with_stock` 同事务负流水 + **超退防呆**（本次 ≤ 累计净收货）；多行订单按首行品/价入库。

- **形态转换单**：`form_convert` 源物料出库 → 目标物料入库（同数量一减一增，**金额按源存货移动加权成本平移**——等值转换，源无成本价拒绝；原数量口径会给目标存货留 0 价首入污染计价，已修）；组装拆卸页新增「形态转换」工具条；同物料/非正数拒绝；无总账凭证（存货内部结构调整）。
- **低库存预警**：`below_safety`（`item_plan` 安全库存 > 0 且现有库存 < 安全量）→ `GET /api/inventory/below-safety` + **工作台仓管域新卡片「低于安全库存」与待办**（点击直达仓库库存页）。
- **测试**：web `inventory_qc_convert_flow`（到货 +20 → 质检不合格 5 自动退货 → 15 → 超退 400 → 转换 5/10 → 同物料 400 → 端点 200）+ `doc_push_chain` 增补 0 价防呆与补价序列；README §9 质检条目同步收窄。

### 4.22 销售成本结转（Web 化 + 口径修正，对标金蝶存货核算-凭证生成）

- **口径修复**：`stock_summary` 的"出库"原为**全部负流水**（含领料/形态转换）——制造业账下结转会虚增主营业务成本 → 收敛为**仅 kind=sale 的销售出库**（移动加权与全月一次两分支同步；计价引擎仍跑全部行保证成本序列正确，非销售出库只消耗库存、不计入结转与回写）。
- **Web 入口**：`POST /api/cost/sales-cost {period, method, date?}`（CostOps）——借 6401 主营业务成本 / 贷 140501 库存商品（数量 + 存货辅助 + **显式发出单价 amount÷qty**：0 价入账过的存货缺 price 会触发计价引擎「首次入库必须指定单价」）；期末结价页新增「结转销售成本」按钮（口径下拉：移动加权/先进先出/全月一次），缺省日期 = 期间末日。

### 4.33 Web 平台安全中心（口令策略可配 + 登录审计 + 持久锁定）

- **背景**：Web 登录是**平台层**（认账号库 realm）——此前口令策略硬编码默认值（不可配）、登录只走内存限流（重启即忘、不留审计），与桌面端账套级策略/锁定语义不一致。
- **策略可配**：`GET/POST /api/security/policy`（仅平台管理员；值域校验：长度 1-64、失败次数 1-20、锁定时长 1-1440 分、空闲登出 0-1440 分、有效期 0-3650 天）→ 存 realm `realm_option`；**改密校验 / 空闲登出 / 登录锁定统一走该策略**（`WebState::policy()`，读取失败回退默认，不因策略库异常阻断登录）。
- **登录审计**：realm 新表 `realm_login_attempt`（只留最近 500 条）+ `GET /api/security/login-attempts?username=&limit=`；成功登录亦留一条（先 `unlock` 清失败再记成功，成功记录不被清理）。
- **持久锁定**：`realm_user.locked_until`（老库启动自动补列）+ `GET /api/security/locked-users` + `POST /api/security/unlock`——连续失败达策略阈值写锁，**跨进程/重启生效**；锁定期间口令正确也 429（不再做昂贵 argon2 校验）；解锁同时清空失败计数。
- **UI**：「系统 → 安全中心」新增两块（仅平台管理员可见）——**口令策略表单** + **平台登录审计**（锁定账号 🔒 红标 + 一键解锁）；账号管理/账套成员锁定解锁保持原样。
- **测试**：web `web_security_center`——默认策略 → 保存 max_fail=3 → 非法值 400 → 3 次错锁定 → 正确口令也 429 → 审计含失败记录 → 锁定名单可见 → 解锁后登录成功 + 审计含成功记录 → 非管理员 403 → 解锁陌生账号 404。

### 4.54 桌面端精简模式（侧栏只留日常财务的 12 项）

面向个人/小微记账人：完整侧栏有 **56 项**，其中生产制造、供应链、成本、预算、多维损益等重模块与日常记账无关，把菜单撑得很长、新手一眼望不到该点哪里。

- **开关位置**：侧栏底部「精简模式」勾选框（不在深层设置里——这是个高频微调的界面偏好，藏起来等于没有）。
- **勾上后侧栏只剩 12 项**：工作台 / 填制凭证 / 凭证查询 / 账簿查询 / 科目余额表 / 会计报表 / 期末处理 / 银行对账 / 往来核销 / 会计科目 / 期初建账 / 备份恢复 —— 覆盖建账 → 录凭证 → 查账 → 出表 → 月末结账 → 备份的完整链路。
- **不是删功能**：被过滤的项一项没少，取消勾选立刻全部回到侧栏。
- **临时看全部**：顶栏只有「填制凭证/凭证查询」两个快捷入口，勾上精简模式后其余页面在侧栏就没有入口了。所以底部另给「临时看全部功能…」——只展开当前这一屏、不改开关本身，旁边变成「← 回到精简模式」。
- **停在隐藏页时的兜底**：勾选瞬间若当前正停在被藏起来的页面，该页继续显示但侧栏没有高亮项（看着像界面坏了），此时自动跳回工作台。
- **存哪儿**：`Persist`（eframe 本地配置）而**不是**账套的 `BookOptions`——它是「这台设备上我的界面偏好」不是账套属性，存进 `.fbk` 会跟着备份走，换台电脑打开别人的账套也会被套上。默认值策略见 §4.56（未决定的一律默认精简）。
- **测试**：`finui` 4 条 —— 恰好 12 项 / 覆盖日常全链路 / 确实藏起了重模块 / 至少保留工作台。

### 4.55 新手建账向导去术语墙 + 发布包带示例账套

面向零基础用户，把「下载 → 双击 → 用起来」这条链路上的两个坎拆掉。

- **建账向导**：「科目级长 `4-2-2-2`」原来和「企业名称」平级摆着，但系统已预置 199 个标准科目、级长保持默认就够用。折进**默认收起的「进阶设置（一般不用改）」**，并把说明改成人话（「会计科目的编码位数规则…保持默认即可，建账后不可更改」）。同时给「纳税识别号」补「选填，打印报表时会用到」、给「启用期间」补「填你要开始记账的那个月，格式 2026-01 / 这个月之前的账进软件后在『期初建账』录余额」。
- **发布包从 1 个裸 exe 变成 3 个文件**：`finbook.exe` + `新手使用说明.txt`（4 步走通的大白话，含备份提醒与常见问题）+ `示例账套.fbk`。
- **`demo` 示例工具**（新增）：`create` 建空壳、`seed` 灌基础档案但**一张凭证都没有**、`demo` 再灌一整月**已记账**业务 —— 采购付货款 / 赊销收货款 / 发工资 / 付房租 / 结转成本 / 缴税共 9 张，借贷平衡、凭证状态 `posted`，打开就能在余额表和三大报表上看到数。演示数据刻意只含商贸业务，不含生产制造（个人记账用不上，也少一层理解成本）。
- **一个必须注意的坑**：`create` 用的是 `Db::create_no_admin`（Web 端「首个登录者即管理员」的初始化流程），建出来的账套**用户表是空的**。所以 `demo` 必须自己补一个 `admin/admin123`（且不设 `must_change_pwd`），否则发布包说明里的登录信息就是假的 —— 照着做直接 401。
- **Linux 与 Windows 各自生成一份示例账套**（不用交叉编译跑 example），打包时保持一层目录（不用 `zip -j`），避免中文文件名在 Windows 下乱码。

### 4.56 新手上手：精简模式默认开 + 「先看示例账套」入口

§4.54/§4.55 把菜单和建账页改到位了，但还有两处「东西在那儿，小白够不着」：

- **精简模式默认是关的** —— 小白第一次打开看到的是完整侧栏（47 项），
  要自己在侧栏最底部找到那个勾选框才会变精简。大概率找不到，
  于是第一印象就是「菜单好多，看不懂」，而这恰是精简模式要解决的问题。
- **示例账套也要先登录** —— 他还不知道 `admin/admin123` 是什么，
  点完「打开已有账套」被弹到登录页，第一步就卡住。

改法：

- **A 精简模式默认开（不分新老用户）**：`Persist::simple_nav` 从裸 `bool` 改成
  `Option<bool>`。`Some(b)` = 用户明确选择，永远优先；`None` = 还没决定 →
  一律默认精简。退出时 `save()` 把推断值固化成 `Some(b)`。
  - 为什么不用 `#[serde(default = "true")]`：那样「没这字段」和「明确关了」
    无法区分，老用户某次取消勾选后会被默认值顶回来。
    用 `Option` 才能区分两者。
  - 为什么**不再**按新老用户分流：最初有历史的老用户默认完整菜单（怕他们
    不适应），但个人/小白财务用户打开看到 47 项正是要解决的问题 —— 分流等于
    把最需要精简的那批老用户挡在门外。开关与「临时看全部功能」一键即回，
    不存在功能损失，所以未决定的统一精简；明确关过（`Some(false)`）的仍然保持。
- **C 账套选择页给三个入口**：原来只有「新建账套」「打开已有账套」两个小按钮，
  两个词都要先理解才知道选哪个。新增「👀 先看示例账套」—— 按文件名
  （与 exe 同目录，兼容 macOS `.app`）直接定位，不弹文件选择框，点完直接进主界面。
  「新建账套」同时改名为「建自己的账」。
- **示例账套免登录但只读**：文件名命中 `示例账套.fbk` 时直接注入
  `Role::Viewer` 身份跳过登录页。**必须给只读身份** —— 否则新手随手一改就把
  发布包里的示例数据弄乱，别人下载到的包也跟着变。用文件名而非账套内标记，
  免去一次 schema 迁移；代价是用户若把自己的账套改名成这个名字会拿到免登录
  只读（只影响自己这台机器，顶栏「退出登录」仍可返回选择页，不构成越权）。

- **测试**：`finui` 4 条 —— 未决定默认精简（新老用户都验）/ 明确选择优先
  （开、关两个方向都验）/ 老版本配置缺字段仍能读 / 存取往返不丢选择。

### 4.57 辅助档案批量粘贴（把 100 次点击变成 1 次粘贴）

「基础资料」分组里最耗时的是辅助档案：一家公司 50 个客户 + 30 个供应商 + 20 个员工，
按原来「新增」按钮一个个敲是 100 次点开、填编码、填名称、保存。而财务手上几乎
一定已经有一份 Excel/WPS 名单 —— 让他们重打一遍是最没必要的重复劳动。

- **入口**：辅助档案页工具栏新增「批量新增」，打开一个多行文本框。
- **两种写法都收**：
  - `编码,名称` 两列 —— 有自己编码体系时用
  - 只写名称 —— **编码自动编号**（C01、C02…），小白多半不知道怎么给档案编编码，
    让他自己填反而是个坎；编号从「库里该前缀的最大号 +1」接着排，不会撞上已有档案
- **分隔符容忍**：Tab（Excel 复制的真实分隔符）、中英文逗号、顿号、连续空格；
  第一行像「编码 / 名称」的表头自动跳过；空行与首尾空格清理掉。
- **必须先「预览」再导入**：预览表格逐行列出编码/名称/状态（将导入 / 跳过：已存在 /
  跳过：本批内重复）。直接点确认就把一坨文本当数据写库，粘贴错位（多带表头、
  带上合计行）会静默变成脏档案。
- **不覆盖已有档案**：新增 `auxs::insert_many_skip_existing`，与既有 `import_many`
  的区别就在那句 `INSERT OR REPLACE` —— 后者会**静默覆盖**同名档案。用户粘一份
  旧 Excel 进来，其中一条编码和库里重了，客户名就被悄悄改掉，而凭证上的历史金额
  对不上任何东西，之后极难排查。这里宁可少导一条、并在返回值和提示里报告跳过了
  哪些，也不替用户做决定。
- **测试**：`finui` 10 条解析（制表符/中文逗号/表头/自动编号接最大号/各类型前缀/
  库内冲突/批内冲突/空行/空输入）+ `findb` 2 条写入语义（不覆盖、空列表）。

### 4.58 期初余额批量粘贴 + 方向自动归位

期初建账页已有「按科目表补全」和「按期末余额倒推」，但前者只是把 199 个
末级科目列出来（数还是要一个个填），后者只在**本账套已有发生额**时有用 ——
而小白的新账套是空的。他的期初数在另一份 Excel（上期余额表）里，
需要的是**从外面贴进来**。

- **入口**：期初页工具栏新增「批量粘贴」。
- **三种写法都收**：
  - `编码,金额` —— 从余额表复制两列，最常用
  - `编码,借/贷,金额` —— 金额恒为正，自己声明方向
  - `编码,借方金额,贷方金额` —— 和 UI 表格同一布局
- **方向自动归位（核心）**：只给金额时，方向从**科目的余额方向**来 ——
  资产记借、负债/权益/收入记贷。小白从余额表抄来的数天然只有一列，
  不区分借贷符号，而「资产=借方、负债=贷方」恰是他最容易错的一步。
  负数/红字和会计报表的括号 `(5000)` 都自动转反方向。
- **抄错码给提示**：编码不在科目表里时标出，并用编辑距离找最接近的
  （`10011` → 「像不像 1001？」），而不是直接吞掉。
- **和辅助档案同样的纪律**：必须先「预览」再导入；库里/草稿里已有的跳过
  （不覆盖）；预览里带本次的借贷合计与差额，粘完先看平不平。
  批量粘贴只是把草稿填好，最终仍由工具栏「保存」统一落库+校验。
- **新建行方向预填**：「添加科目」和「按科目表补全」建出来的行，方向按科目
  预填。以前一律借方 —— 资产确实是借，但负债/权益/收入默认也是借，
  新手照着填完试算必不平，而他还不知道错在哪（方向错了，金额看着都对）。
- **测试**：`finui` 11 条解析（含 `is_header` 从 `any` 改 `all` 的回归 ——
  真实数据行 `1001,贷,5000` 里有个「贷」，`any` 会把它整行吞掉）。

### 4.59 试算不平时标出「嫌疑人」

试算区原来只给三个数：借方合计 / 贷方合计 / 差额。用户看到「差额 5000」
时，面对 199 行不知道从哪查 —— 只能逐行对，这是期初最耗时的环节。

- **只标方向异常**：金额方向与科目余额方向不一致的行（负债放借方、
  资产放贷方）。这是新手期初不平最常见的原因。
- **只在不平时标**：备抵科目、红字余额等合法反方向会被误标 ——
  所以试算平了就不标；标出来的是「嫌疑人」不是「罪犯」，提示条里明说
  「备抵科目、红字余额等合法反方向也会被列出，请自行确认」。
- **两种呈现**：试算区下方列出嫌疑人编码（可点击，点完搜索框自动填该编码、
  列表过滤到那一行）；表格里嫌疑行的编码框标红，200 行里一眼找到。
- **三类不标**：金额为 0（刚补全的空行不能满屏红）、有累计借贷
  （期初数是三项合成，不能简单按方向判）、未知科目（那一列已有红字提示）。
- **测试**：`finui` 5 条，对应上面三类不标 + 两类标出。

### 4.60 会计科目：层级缩进 + 三档排序 + 只看在用

科目页原来是 199 个平铺列表。`1001` 和 `100101` 看不出父子关系，
新手不知道点哪个；199 个里大部分是 0，打开满屏 0 会以为软件没装好。

- **层级缩进**：名称按 `Chart::level` 缩进（最多 3 格，窄屏不吃列），
  下级前面带 `├`/`└`。父级用主题色、末级用深灰，本来就是这么区分的，
  现在加上缩进一眼看出树。
- **排序三档循环**：编码（默认，层级天然有序）→ 名称（找名字快）→ 类别
  （资产/负债/权益分组看）。按钮上直接显示当前档，点一下换一档。
- **只看在用**：有分录、有期初余额的科目；子在用则父也留着（不然树断了）。
  过滤是纯内存操作，不重查库。
- **测试**：`finui` 3 条 —— 三档循环不断 / 每档有中文标签 / 缩进有上限。

### 4.61 常用档案一键预置

**根因**：`validate_entry` 强制要求启用了辅助核算的科目**必须**填辅助核算。
而默认科目表里 `100201~100207` 全部 `aux=Bank`、`6601/6602/6603` 全部
`aux=Dept`。新账套一条档案都没有，于是用户在凭证窗口看到下拉框里只剩
「（不核算）」，只能选它 —— 保存时被拒：
「第 N 行科目 100201 核算银行账户，必须填写银行账户」。
他此刻正站在凭证里，不知道档案页在导航栏哪一层，只能把整张凭证丢掉去翻菜单。

**修法**（三层入口，逻辑共用 `AuxPreset`）：

- **fincore `preset_aux(kind)`**：纯数据清单。
- **findb `insert_presets` / `insert_all_presets`**：沿用
  `insert_many_skip_existing` 的约定 —— **跳过已存在，不覆盖**，返回跳过清单。

  - 建账页勾选项「预置常用档案（推荐）」，**默认开**，旁边直接列出条目名。
  - 辅助档案页工具栏「预置常用档案」按钮；库为空走普通确认，已有档案走
    危险确认（明确说「编码相同的不会被覆盖」）。
  - 凭证的辅助核算窗口：该类别一条档案都没有时，红字说明「这张凭证保存不了」
    + 一键预置按钮 + 指出档案页在哪。这条是最关键的 —— 用户正卡在那里。

预置的每一条都带 `memo` 写清「预置的通用部门，可改名或删除后填自己的」。

**测试**：`fincore` 3 + `findb` 5 + `finui` 3 = 11 条。

### 4.62 试算不平：算解，而不是猜

§4.59 的检查是**语义猜**：拿科目表的方向去比，负债放借方就标出来。它命中不了
三种真实情况 ——

1. 科目表本身标错了方向（把「其他应付款」建成借方），检查反过来指认正确的行；
2. 行上有**累计借贷**时，`年初余额` 是三项合成，代码为避免误判一律放弃检查；
3. 差额压根不是方向问题，而是**只填了一边**（对方科目漏了）。

**解法**：把差额当方程解。一行参与借贷合计的金额是 `s = ±年初余额 + 累计借 − 累计贷`，
试算差额 `diff = Σs`。能改动一行让它归零的改法只有三种，各有充要条件：

| 改法 | 条件 | 一键修复 |
|---|---|---|
| 方向取反 | `diff == 2 × ±年初余额` | 有 |
| 累计借/贷对调 | `diff == 2 × (累计借 − 累计贷)` | 有 |
| 这一行就是差额（其余全平） | `diff == s` | 无（缺的是另一行） |

三个条件都**充要** —— 满足就一定平，不满足就一定不平。所以报出去的每一条
都是**解**，不是「嫌疑人」，用户改完当场验证，不用再猜。只收充要解是有意的：
宁可少报也不要报「大概可能」，新手分不清两者，试一次发现没用，第二次就不信了。

- 前两种给一键按钮（改完立刻重算试算）。
- 第三种只提示「其余行都平了，多半是这笔的对方科目漏填」。
- **兜底**：不管解不解得出来，都给「新增一行 {对方方向} {差额}」—— 金额和方向
  由差额直接算出，用户只需选科目，不用自己算该填多少。
- §4.59 的语义检查**保留**并降级为弱提示：解法不看科目表，语义检查不看算术，
  两者互补（比如数字解说「翻 1002 能平」，语义提示「1002 是资产不该在贷方」）。

**测试**：`finui` 11 条 —— 每条解代回去必归零（充要性）/ 有累计数的行也能定位
（并断言旧检查在这行上会放弃）/ 平了不给解 / 零金额行被跳过 / 补对方方向金额 /
排序稳定 / 不提供无用的修复按钮。

### 4.64 check-design-doc：行号锚点改成「窗口 + 容差」

CI 挂在 `CI 配置与变异清单自检` —— 这次不是工具坏了，是**它在正常工作**：
`handlers.rs` 的两条锚点从 7310/7311 漂到 7313/7314（我在文件头加了两行注释）。

但暴露了一个真实的设计摩擦：**14000 行的文件里维护精确行号，成本高到会让人
习惯性无视检查**。每新增一个 handler，后面所有锚点都要回来改一遍。一个天天
误报的检查等于没有检查。

**根因**是第一版的容差写错了对象。第一版给了 ±3，注释里写着「容忍漂移等于
没有校验力」—— 那次真正的坑是判据用了**没转义的裸名字**，注释里提到函数名
也被算成命中。现在判据全是 `^\s+` 起头的完整调用式，注释匹配不上。

**改法**：TOLERANCE=20，窗口内命中即过；命中时把实际行号和漂移量一并打出来
（OK 行的信息，不是只在失败时说）。窗口外仍能找到时，报错明确区分两种成因：
「只是无关改动 → 改 REFS.line 即可」/「代码被挪走 → 先确认文档的语义还成不成立」。

**自检同步扩到 4 条**（原来 3 条）：

| 探针 | 证明什么 |
|---|---|
| 锚点内容被改坏 | 窗口不是「随便一行都算过」 |
| 锚点被插 30 行推出窗口 | **容差有界**，不是无限大 |
| 锚点只漂 3 行 | **反向断言**：容差真的有用，否则前两条可能只是「对任何改动都报错」 |
| 文档约束被删 / 未登记引用 | 原有两条不变 |

第三条是新增的关键一条：没有它，前两条变红可能只是因为检查对任何改动都报错
—— 那是噪声不是校验。两条一起才说明「该红的时候红，该绿的时候绿」。

行数漂移的探针数字（30）故意与 TOLERANCE（20）不同步：有人调大容差时这里会
立刻失败，那才是该有的反应。

### 4.65 Web 精简模式：藏起来 ≠ 拿掉

69 个功能平铺 16 组，新用户建完账第一眼看到的是 MRP、工艺路线、预算预警这类
跟他完全无关的东西 —— 他要找「期初建账」得在一屏文字里翻。桌面端已经这么做了
（`NavItem::daily_core`），这里对齐。

**三条不变量**，少一条这个模式就变成了「功能被删了」：

1. **搜索框永远搜全量**。69 项里挑 16 项靠的是「藏起来，不是拿掉」——
   任何人打任意功能名都能搜到并跳过去。搜索的数据源是 `all`（权限过滤后），
   不看这个开关。
2. **路由完全不受影响**。`goView(hash)` 该去哪去哪，精简只决定侧栏画不画出来。
3. **开关随时可切，且按账号分区**（`acctKey`，与收藏/最近一致）—— 一个会计用
   精简，不该影响同一台电脑上出纳看到的菜单。

**默认开，但区分「没设置过」和「显式关掉」**：localStorage 读 `null` → 默认开，
读到 `false` → 尊重用户的关闭。用 `false` 当默认值的话，用户关掉刷新后又被
自己开回来，会以为是坏了。

侧栏铺开列表用 `listed = all.filter(n => SIMPLE_NAV.includes(n.id))`，
即**权限过滤之后**再精简 —— 不能反过来，否则精简会把无权访问的项短暂放出来。

**为什么是 16 项而不是桌面端的 12 项**：Web 把报表拆成了
`balance-sheet` / `income-statement` / `cash-flow` / `reports` 四个导航项，
只留「报表中心」的话新手进利润表得点两次。两边覆盖的功能集合等价，只是切分
粒度不同 —— 别为了凑数字把报表藏起来。

**E2E 3 条**（`e2e/tests/simple-nav.spec.js`）：

- 默认只铺日常功能（生产/预算/库存那一片必须不在）、**搜「MRP」「批次」仍搜得到**、
  开关来回切且**刷新后保持**
- **精简不拦路由**：直接敲 `#/mrp` 仍能进去，且进到页面后侧栏里
  `vouchers` 仍标 `.active`

第二条独立于第一条 —— 万一以后有人在 `goView` 里也加了精简判断，只有它能抓住。

**90 条老 E2E 怎么办**：`newBook` / `loginAs` 里 `addInitScript` 先把
`nav_simple@<账号>` 置 false。这不是在「把测试改成配合实现」—— 精简只决定侧栏
画不画出，不碰路由、权限、页面逻辑；且 `addInitScript` 必须**先于 `goto`**，
否则首屏侧栏已经按默认「精简」渲染了。`loginAs` 要按**登录账号**写 key
（`nav_simple@出纳`），不是 admin 的 —— 账号分区正是为了这个。

### 4.66 check-js：`rest` 的判据从字面改成语义

精简模式给 `rest` 加了一层 `all` → `listed` 的包装，`check-js.js` 就报了
「rest 不再是只排收藏」。但**我的改法完全符合本意**（`listed` 是 `all` 的子集，
谓词没变），报红的是字面匹配：

```js
/const rest = all\.filter\(\(n\) => !favs\.includes\(n\)\);/
```

这类判据的坏处：字面量一变，正确重构就被判成「行为变了」，逼着改动者要么
放弃改进、要么去改检查 —— 越改越僵。改成语义判据：

- `rest` 的谓词里**出现 `recents`** → 报红（本意：最近必须是追加不是搬家）
- `rest` 的谓词里**没有 `favs`** → 报红（否则「常用」会在原分组出现第二份）

`mutate-check` 的 ⑳ 号变异 `from` 串也跟着改成 `listed.filter(…)`。变异清单的
`from` 串必须对齐源码实际写法，否则它「匹配 0 次」会静默失效 ——
`mutate-check` 自己会报「变异已失效」，但没人会因为一条变异失效去看它护着什么。

**这不是放宽检查，是把判据对准它真正要守的不变量。** 变异测试仍然是
「排掉 recents 必须报红」，且变异串已同步更新，验证力没减。

### 4.67 Query 少字段会 422 —— 一整条链路静默消失

**事故**：`GET /api/aux-presets?kind=dept` 返回 **422**，
因为 `KindQuery.kind` 没写 `#[serde(default)]`。

axum 对查询串反序列化失败直接 422，**根本不会进 handler** —— 处理函数里那行
`AuxKind::from_code(&q.kind).unwrap_or(AuxKind::Dept)` 是够不到的。结果前端
`loadAuxPreset` catch 到错误直接 `return`：按钮保持 hidden、提示区空白，
整条预置链路**静默消失**，而且编译期和 Rust 单元测试都发现不了
（Rust 侧那只 handler 逻辑是对的，错的是「框架在进 handler 之前就拒了」）。

body 少字段会 422 这件事本身不新鲜，新鲜的是它发生在 **query** 上：
body 是我们自己在 JS 里拼的，query 是从 URL 拼的，两处都很难在本地顺手测到。

**修法**：给 `kind` 加 `#[serde(default)]`。

**更重要的修法是补上回归网**：`crates/finweb/tests/aux_preset.rs` 4 条，
每一条都发**真的带查询串的 HTTP 请求**（`oneshot(authed_get(uri))`）。
已做变异验证：去掉 `#[serde(default)]` → 立刻变红；还原 → 恢复绿。

顺带说明为什么这类 bug 必须有 HTTP 层测试而不是单元测试：单元测 handler 函数
签名时，`Query<T>` 只是一个类型参数，反序列化发生在框架里。**必须真的发请求。**

**另一个教训（我自己踩的）**：验证时用 Python `urllib` 发「GET」却带了
`data=b"{}"` —— 有 body 就必须是 POST，于是 urllib 悄悄发成了 POST，
测的是 `KindReq` 缺 `kind` → 422。工具用错会得出「产品有 bug」的错误结论，
而且结论看起来完全合理。我差点据此去改本来正确的代码。
以后验证 HTTP 行为优先用现成的集成测试（`oneshot`），别拿手写脚本凑。

### 4.68 本机 E2E 跑不动 → 给侧栏逻辑补一道 Node 检查

CI 的 E2E 挂了，但我拿不到日志（只读 token 无 Actions 写权限）。本机按 CI 的
方式起 finweb + `npx playwright install chromium` 居然真的跑起来了，但：

```

checkValidity() === false

```

于是连**没被我碰过**的 `smoke.spec.js` 都卡在「等不到 `#new-book`」。
结论：本机浏览器输入注入失效，E2E 在本地**完全无法验证**——看到失败也
分不清是产品坏了还是环境不行。CI 上那次 E2E 失败就是这样卡住的：
我一度以为是产品 bug。

**所以给侧栏逻辑补了一道能在本地跑的检查**：`tools/check-simple-nav.js`。

关键设计是**抽 app.js 的真实源码片段执行**，而不是抄一份到检查里：

```js
function grab(re, what) {
  const m = SRC.match(re);
  if (!m) throw new Error(`抽不到 ${what}，源码形状变了？`);
  return m[0];
}
const LISTED_SRC = grab(/const listed = [\s\S]*?;/, "listed");
const listed = eval(LISTED_SRC.replace("const listed = ", ""));
```

抄一份的话，产品改了检查还在跑，报「全绿」，而实际行为早变了 —— 那才是
真正危险的检查。抽不到就抛错，至少不会**假装通过**。

验证三条不变量：默认只铺 16 项（生产/预算/库存那一片必须不在）、**搜索数据
源是全量 70 项**（藏起来≠拿掉的根据）、账号分区互不污染、`rest` 只排 favs
不排 recents。已接进 `check-ci.js`。

**还有个教训**：这条检查第一版报了个假失败「cashier 的 false 没生效」。
原因是我 `lsSet("nav_simple@cashier", false)` 之后**没切 session** ——
`acctKey` 拼的是当前登录账号，session 还在 admin 上，等于在测 admin 的 key。
探针自己也会有 bug，报红不等于产品有问题，得先确认探针测的是它声称的东西。

### 4.69 `addInitScript` 不能注销 —— 一个会伪装成产品 bug 的测试写法

CI 的 E2E 挂了，证据从 **`playwright-trace` artifact** 里拿到（`trace:
"retain-on-failure"` + `upload-artifact`；只有失败用例才有，所以 artifact 很小）。
读法要注意一个坑：artifact 下载是 302 到 S3，带上 `Authorization` 会被 S3
拒 401 —— 必须先拿到 `Location` 再用**不带 auth** 的请求去取。

报错只有一条：

```
Error: expect(locator).not.toBeChecked() failed
  Locator:  locator('#nav-simple')
  Expected: not checked
  Received: checked
```

**症状极像产品 bug**（开关没存住），实际是我的探针写错了：

```js
await newBook(page, name, { simpleNav: true });   // 注册了写 "true" 的 addInitScript
...
await page.uncheck("#nav-simple");                // 用户关掉，写 false
await setSimpleNav(page, null);                   // ← 只是「不再新增」
await page.reload();                              // 旧脚本照样执行，写回 "true"
```

**`page.addInitScript` 没有对应的 unregister。** `setSimpleNav(page, null)`
只保证「这一次不新增注册」，已注册的那个会**在每次导航前执行**。所以
「null 之后 reload 看值还在不在」测到的根本不是持久化，是脚本又写了一遍。

**正确写法**：`newBook(page, name, { simpleNav: null })` 起步，全程不注入任何
脚本，只靠用户真实的点击改变状态，reload 后看值还在不在。这才是持久化该有
的测法 —— 而且顺带把 `uncheck → check` 的完整用户路径也覆盖了。

**加了两条静态检查**（都在 `check-ci.js`）：

1. 绕过 `newBook` 自己 `page.goto("/")` 的 spec，必须用 `newBook` 或
   `setSimpleNav`。本次就漏了 `smoke.spec.js` 和 `aux-attach-reports.spec.js`
   两个文件，症状是 E2E 跑了 50 分钟才挂（正常 16-20）。
2. 同一用例里既用 `setSimpleNav(null)` 又在 `newBook` 传 `simpleNav: true/false`
   的，报红。

**第 2 条的判据按 test 块切分，不按文件**：同一个 spec 里不同 test 用不同模式
是正常的（「精简不拦路由」用 `simpleNav: true` 完全合理，它不测持久化）。第一版
按文件判，立刻把 `simple-nav.spec.js` 误报了 —— **一个在真实代码上就误报的新
检查，会很快被人注释掉，那还不如不写**。

两条都做了变异验证：坏写法报红、正确写法不误报。

### 4.70 批量粘贴解析下沉到 fincore（Web 端复用的前置）

辅助档案与期初余额的「把 Excel 名单粘进来」解析，原本住在 `finui`

|---|---|
| `finweb` 依赖 `finui` | 把 egui/eframe 整个拖进服务端，只为调几个不碰 GUI 的函数 |
| Web 端自己写一份 JS 解析 | **两端必然分叉** —— 桌面端支持了「名称,编码」倒序而 Web 没支持，用户会得出「这软件有的地方能用有的不能用」，而桌面的 20 条测试保护不到 Web 的实现 |
| **下沉到 `fincore`** | 两端共用一份，桌面端那 20 条测试继续有效，Web 免费继承 |

选第三条。解析本来就是纯计算（切列、认表头、算自动编号、判方向），本来就属于
`fincore` 的职责范围，只是当初写的时候只考虑了一个调用方。

**新结构**：

```
crates/fincore/src/batch/mod.rs    共享切列 split_cols（tab > 逗号类 > 空白）
              /aux.rs             辅助档案：编码 + 名称，42 条测试里 21 条
              /begin.rs           期初余额：编码 + 金额（方向自动归位），21 条
crates/finui/src/views/*_batch.rs 只剩窗口与两步流程，转发到 fincore
```

两个子模块**故意不合并行模型**：跳过原因集合不同（期初多「无此科目」「金额
看不懂」），强行合并会得到一堆两边都不适用的枚举变体。

**顺带修掉 3 个真缺陷**（都是搬的过程中发现的）：

1. **自动编码撞码**。`next_num` 和 `auto_taken` 是两个要手动同步的变量，
   而「两列都不像编码」的兜底分支只用了 `next_num`，**没登记也没递增**。
   于是紧接着的单列行会发出**完全相同**的编码 —— 两条档案撞码，
   `insert_many_skip_existing` 认编码不认名，第二条被**静默跳过**：
   用户粘 10 行进来只进了 9 条，界面上看不出哪条没进。
   现在把计数器收成 `CodeGen` 结构体，让「每次发号必须记账」成为类型上的要求。
   回归测试：`兜底发号不与后续撞码`。
2. **显式编码不推进自动编号**。`C09,甲` 后面接单列名，应该发 `C10`，旧代码
   会再发 `C09` 然后靠 `auto_taken` 跳过 —— 结论对但逻辑绕，且 `reserve` 缺失
   时若批次里恰好没有同名行就会撞。回归测试：`显式编码推进自动编号`。
3. **多余列混进名称**。`C01,杭州明远,备注列` 旧代码走 `cols.join(" ")`，
   生成「C01 杭州明远 备注列」这种没人会要的档案。现在名称只取前两列。
   回归测试：`多余列不混进名称`。

**新增的能力**（桌面端原先没有，Web 端需要）：

- `SkipReason::label()` —— 两个端点共用一份中文文案。此前两端各写一份
  match，桌面的改了 Web 的没改就会漂移。
- `Parsed::trial()` —— 试算（借方合计 / 贷方合计 / 差额）。Web 端是「粘贴后
  立刻提交」，没有草稿区可看，不给试算用户就没有任何反馈。
- `Parsed::is_empty()` 取代 `empty` 字段（后者是每次现算的冗余）。

**测试**：42 条（比原来多 7 条，都是上面那些回归）。

### 4.71 Web 批量粘贴端点：三条接口约定

`POST /api/aux-batch`（解析）、`PUT /api/aux-batch`（导入）；
`POST`/`PUT` `/api/begin-batch` 同构。用 **PUT 而非 POST** 导入是为了在同一个
路径上区分「不写库」和「写库」—— 出错时看方法名就知道有没有落库。

**三条约定，都是「看着多余」但少一条就出事**：

1. **导入只认前端回传的行**，请求体里没有文本。
   若后端重新解析一遍，用户在预览之后改过文本（比如取消勾了一行），
   实际写入的就不是他确认过的那批 —— 「确认了 A、写进去 B」是最难查的一类错。
2. **科目方向不接受前端传**，每次从科目表现取。
   方向是期初「自动归位」的依据；让前端传等于让前端决定借贷，
   而那正是期初不平的头号原因（见 §4.59 / §4.62）。
3. **越权科目在预览里就不出现**，导入时再拒一次。
   否则用户会看到一条他无权写、点了才报错的行。

**期初导入复用 `upsert_begin`**，与手工「保存」同一条校验路径 ——
批量导入并不比手工一行行填更特殊，特殊的只是**一次能错几百行**。

**为什么必须有 HTTP 层测试**（10 条）：`fincore::batch` 那 42 条验的是解析对不对，
这里验的是**端点有没有把解析结果正确送到前端/落进库**。中间这段最容易出
「解析全对、前端表格少一列」的低级错 —— 比如 `json!()` 里漏了个字段，
单测和解析测试都发现不了。

**两个我自己踩的坑，都写进注释了**：

- `Money` 序列化成的是**字符串** `"50000.00"`，不是 JSON 数字。
  测试用 `as_f64()` 取会静默拿到 0，报出来是「贷方余额应存成负数，实际 0」——
  看起来像产品 bug，其实是取值方式错了。
- 用 Python `urllib` 验证接口时，「GET」不能带 body：有 body 就必须是 POST，
  urllib 会悄悄发成 POST，于是我测的其实是 `save_begin`。
  **同一个坑我踩了两次**，第二次还差点据此去改本来正确的路由。

### 4.72 Web 批量粘贴界面：两个页面共用一个弹窗

`batchPasteDialog(opts)` 一个组件同时服务辅助档案与期初余额。两者流程完全一样
（粘 → **预览** → 导入），差异只在列定义和是否显示试算 —— 与其复制两遍然后
各自腐化，不如抽出来。

**三处「看着多余」的处理**：

1. **文本一改，预览立刻作废**（`input` 事件里 `preview = null` 并禁用导入）。
   否则用户预览完改了文本再点导入，导入的是**他已经删掉的那几行** ——
   而「预览 → 导入」这个两步流程存在的全部意义就是防这个。
2. **⌘/Ctrl+Enter 直接导入**：预览之后不用移开手去点按钮。
3. **解析为空时给的是「怎么写」的提示**，不是「解析失败」——
   「没解析出内容。每行一条，列之间用逗号或 Tab 隔开就行」比一句「失败」有用。

**期初页的 `existing` 来自 `state.beginDraft`**，不是库里的期初数。
解析时后端看到的是库里的行，看不到用户**正在编辑还没保存**的那些 ——
不把草稿编码传过去，就会把用户刚填好还没保存的科目重复导入一遍。

**顺带修一个真缺陷**（`import_aux_batch`）：`skipped` 报数把「本批已处理过」
（用来防重复的集合）也算进去了，于是用户看到「已导入 2 条，跳过 2 条」——
2 + 2 ≠ 2。数字对不上时第一反应是「这软件出 bug 了」，而真正的错只在
一个返回字段里，肉眼几乎不可能发现。

修完加了一条**盯恒等式而不是盯具体值**的回归测试：

```
inserted + skipped == 请求的行数
```

第一版只断言 `inserted == 2`，把 bug 放过去了 —— 恒等式才是不变的东西。
已做变异验证：把 `seen` 又塞回 skipped → 测试立刻变红；还原 → 绿。

**E2E 4 条**（`e2e/tests/batch-paste.spec.js`）—— 解析本身有 42 条单测 + 11 条
集成测试，这里只补「浏览器里点得动、看得见」那一段（端到端验的其实是接线：
按钮 → 弹窗 → 预览表格 → 导入 → 列表刷新）：

1. 未预览前「导入」**必须禁用**（两步流程的第一道闸），预览后**未写库**，
   导入后已存在的那条**没被改名**
2. 预览之后改文本 → 预览作废、导入禁用
3. 期初方向按科目自动归位；预览带试算，且**不平的差额看得见**
4. 未知科目给「像不像 1001」的提示，且**不静默丢行**、不进试算

粘贴文本一律用 **Tab** 分隔（模拟 Excel 的真实输出）。用逗号的话，金额里的
千分位会被当分隔符切坏 —— `fincore::batch::begin` 的 `千分位逗号会切坏行`
那条测试已经把这个坑钉住了，E2E 不能自己踩一遍。

### 4.73 账套额度满 → 65 个假失败（本轮最隐蔽的一个）

首次跑这 98 条时 **65 条一起挂**，包括 `smoke` 和所有与本次改动无关的老用例，
每条都报「等不到 `.nav-item[data-view=vouchers]`」。真因在第一条失败的
`yaml` 快照里：

```
- status:
  - text: 每个账号最多创建 10 个账套（当前已创建 10 个）
```

**账套上限是每账号 10 个**（见 `helpers.js` 顶部注释 —— 这个坑已经踩过一次，
「1 个真实失败被放大成 18-31 个用例」）。`purgeOwnBooks` 按 `E2Ew<worker>///`
前缀清理，漏了两类书：

1. `smoke.spec.js` 与 `aux-attach-reports.spec.js` **绕过 `newBook`** 自己手写
   建账，名字是 `E2E公司1757…` / `E2E辅1757…`，**没有 worker 段**，永远清不掉；
2. worker 索引全局递增（`w0`…`w9`），每个前缀下各攒一本，一次清理只清得掉 1 本。

修法三处：

- **`purgeOwnBooks` 改按公共前缀 `E2E`**。串行跑（`workers: 1`）时不存在
  「别人的书」，按公共前缀全清是安全的；账套名仍带 worker 段，只为出问题时
  能一眼看出是哪条用例漏了。
- **两个 spec 改用 `newBook`** —— 它们的手写建账逻辑与 `newBook` 本来一模一样，
  绕过它没有好处，只有漏清理的风险。
- **加检查**：spec 里出现 `#cb-save`（自己点创建）就报红。建账的全部知识
  （命名、清理、精简开关、默认期间、出厂配置回读）都在 `newBook` 里。
  同时用了两者的会 WARN 而不是报红，留个口子给有意的例外。

已做变异验证：注入 `#cb-save` → 两条相关检查都报红。

**这次为什么值得单独一节**：它没有出现在任何一条失败的错误信息里 ——
每条都说「等不到某个元素」，只有第一条的页面快照里有真相，而且被夹在
几十行不相干的堆栈中间。**失败信息指向的症状和真正的原因之间隔了三层**。

### 4.74 导入导出闭环：为什么必须「导出的表能原样导回去」

v1.8.21 之前，Web 端的数据进出是不对称的：**进**的路很宽（`/api/import/analyze`
认 xlsx/xls/ods，带科目映射与幂等跳过），**出**的路很窄 —— 只有凭证、明细账、
工资、报销、催款、派工六张 CSV，基础资料（客户/供应商/存货/科目/期初）一个导出
按钮都没有，全站零 xlsx。用户想把客户列表拿去改一遍再导回来，只能手抄。

这一节记的是「为什么不是加几个下载按钮那么简单」。

#### 一、列头就是接口，不是文案

`findb::imports` 的解析器按**列下标**取值（`import_aux_rows` c0=类型 c1=编码
c2=名称 c3=备注；`import_accounts_rows` c0..c4）。所以导出的列头必须与导入模板
逐字对应，顺序也不能动 —— 一旦顺序变化，导入侧不会报错，它会**把名称读进备注**，
数据错位但看起来成功。`crates/finweb/src/sheets.rs` 里每张表都在注释里写明了
它对齐的是哪个解析器。

这条约束还有一个反例：`begin`（期初余额）的「通用」模板是 6 列
（`科目编码,科目名称,方向,期初余额,累计借方,累计贷方`），而 `ImportTemplate::Generic`
分支原本按 3 列（`科目编码,方向,金额`）解析。两边对不上时后果不是报错，是
**整批丢行**：方向列读到「库存现金」、金额列读到「借」，`MoneyWarn` 判定「借」
不是金额，每一行都进 warnings 被跳过 —— 用户下载官方模板照着填、一条也进不去，
而提示是「期初余额「借」无法识别为金额」，看不出是列错位。

修法是不改模板（模板已经发出去了），让解析器认两种布局：第 2 列是不是
借/贷/平 就能判别。判据安全，因为布局 B 的第 2 列是科目名称，不可能只有一个
「借」字。

#### 二、金额必须是数字，不能是文本

CSV 里的 `1,234.56` 在 Excel 里是**文本**：左对齐、不能求和、不能透视，用户
每次都要手动「分列」。所以报表类必须走真 xlsx。`crates/finweb/src/xlsxout.rs`
把它收敛成「若干张 `Sheet` → 一份文件」：

- `ColFmt::{Text, Money, Int}` 决定数字格式（`#,##0.00;[Red]-#,##0.00`），
  **空金额写 `write_blank` 而不是 0** —— 写 0 会让合计对不上，而且用户无法
  分辨「真的是 0」和「这行没有数」；
- `to_f64` 剥千分位、货币符号、全角空格，并认会计括号负数 `(1,234.56)`；
- `emphasis` 只做一件事：把「小计/合计/净增加额」行加粗。会计表不加粗，
  打印出来一堆同权重的数字，读表的人找不到重点。

#### 三、三大报表不能另起一套取数

报表导出最容易犯的错是「导出模块自己算一遍」。`export_statement_xlsx` 直接复用
`statement_table` / `cash_flow_statement` / `equity_statement` —— 与打印页
**同一条取数路径**。另起一套的后果是：两张表看起来都"挺对"，但数字不一样，
而且没人说得清哪个对。

现金流量表与权益变动表不是 `ReportTable`（结构特殊：一类活动一个分组、
权益表是三个金额列），所以 `sheets.rs` 里单独拼。现金流表末尾**把勾稽结论写进
表里**（`ties()` 的结果 + 未标注现金流量项目的金额）—— 导出的表是拿来发的，
收表的人看不到页面上的那行绿字。

#### 四、账套上传：先校验，再落盘，最后才注册

Web 端原来完全不能上传 `.fbk`：`restore_backup` 只认 `books_dir/backups/` 下、
经 `backup_belongs_to` 校验属于当前账套的文件，所以桌面版建的账套一个字都上不来。

`import_book` 的顺序是刻意的：**写临时文件 → 校验 → `Db::open` 迁移 → rename →
注册**。三步校验缺一步都会出问题：

1. `PRAGMA integrity_check` —— 传一半断线的文件仍然能被 SQLite 打开；
2. 有没有 `account` 表 —— 任意 Sqlite 文件都能被 `Db::open` 迁成一个科目全空的
   账套，不先认出来就会把「随便一个库」变成账套；
3. schema 版本不能比本二进制新 —— 新版本的列旧代码不认识，放进来之后第一次用到
   就 `no such column`，而且没有任何线索指向「版本太新」。

另外支持本系统「下载备份」得到的 `.zip`（`.fbk` + `.attachments/`），因为那是
**唯一能带走附件的格式**。zip 里只收「根目录下的 .fbk」和「`.attachments/<扁平名>`」，
任何含 `..` 或额外目录层的条目一律丢弃。

#### 五、三份证据，缺一不可

| 测试 | 证明什么 |
|------|----------|
| `roundtrip.rs` | 导出的**字节**喂回 `imports`，数据能还原（含方向、辅助维度） |
| `export_xlsx.rs` | 路由真的挂着、权限真的生效、附件头正确、坏文件真的被拒 |
| `mutate-rust.js` 4 条变异 | 上面两条测试在代码被改坏时**真的会红** |

第三条是这次必须补的：v1.8.19 出过「测试用 `include_str!` 断言源码含某字符串」
的假绿 —— 断言的字符串本身就在测试里，永远 contains 为真。所以这 6 条变异
（期初 6 列布局、现金流量项目类型、科目表存在性、科目方向列、表头被当数据、
停用状态丢失）都是**手工跑过、确认 FAILED** 才写进清单的。

#### 六、粘回去这条路：表头不是「长得像表头」，而是按列名取值

上面五节说的都是「文件」这条路。「从 Excel 里复制几行粘进来」是另一条路，
而且更容易出错 —— 因为它没有列定义，只有肉眼可见的列。

桌面端「辅助核算档案」的导出表是五列（`编码,名称,上级编码,状态,备注`），
而批量粘贴的解析器原本是**按位置**取前两列、表头判定要求「整行都是表头词」。
把导出的表原样粘回去：

1. 表头行（含「上级编码」「状态」「备注」）不算表头 → 被当成数据，
   凭空多出一条名为「编码 名称」的垃圾档案；
2. 停用状态、备注、上级编码全丢。数据没丢，**结构丢了**：搬完账套之后
   停掉的客户又冒出来，层级的部门塌成一级，而界面上看不出任何异常。

修法是「有表头就按列名取值」：先认表头，从表头建立「列名 → 下标」的映射，
再按 `编码/名称/上级编码/状态/备注` 取值 —— 列的顺序可以变、可以有额外列。
没有表头的老写法（两列、只写名称）完全不变。

**安全判据**：整行不能有任何一格长得像编码（`looks_like_code`）。
否则 `C01,编码` 这种真实数据（客户名恰好叫「编码」）会被当成表头整行吞掉 ——
丢一行数据，而且用户只会觉得「我明明粘了 10 行」。

这条改动同步到了两端：`fincore::batch::auxiliary::parse` 是桌面端与网页端共用的
**同一份代码**，所以改一处两端都受益。网页端另外把 `parent_code/memo/disabled`
透传进 `/api/aux-batch` 的预览与导入（前端只做透传不渲染），并给 `/api/aux`
加了 `include_disabled=1` + 档案页的「显示停用」勾选框 —— 原来网页端根本
看不到停用档案，「停用」等于单向操作，停掉就找不回来了。

### 4.75 列名就是接口：为什么解析器要先认列名，再谈「列顺序不能动」

§4.74 立的规矩是「导出的列头必须与导入模板逐字一致」。这条规矩只对了一半：
它守住了**字面**，却没有守住**顺序**。用户拿到导出的表，第一件想做的事往往是
「把备注拖到最右边好看一点」「删掉用不上的上级编码列」—— 表还是那张表，列头
一个字都没改，但位置全变了。按列下标取值的解析器不会报错，它会把名称读进备注、
把编码读进上级编码，然后「导入成功」。这比报错糟糕得多。

v1.8.22 把这条规定升级成：**有表头就以列名为准，没有表头才按位置猜。**

#### 一、一个 HeadMap 收掉三处重复

`crates/findb/src/imports.rs` 里档案、存货、科目、期初四个导入器原本各写一遍
「跳过表头行、按位置取值」。现在统一成：

- `normalize_header`：去掉空白/全角空格/`*`/`：`，英文转小写 —— 用户从别处
  粘来的表头常带 `编码*`、`名称：`；
- `is_header_code`：`编码|科目编码|存货编码|代码|编号` 或 `code`；
- `row_is_header`：**整行任一格**是表头词就算表头。不能只看某一列，因为
  「哪一列是编码」正是用户要改的东西；
- `HeadMap::cell(&aliases, pos)`：按别名查列名，查不到时 —— **有表头就返回空，
  没表头才退回 `pos`**。

最后这一条不是洁癖。真出过一次错：一张「备注挪到第一列、上级编码被删掉」的表，
退回按位置取值时第 4 列正好是编码，于是「上级编码 = 自己」，导进去报
`上级编码不能是自己（C001）—— 会形成环，层级汇总无法收敛`。报错信息看着像
档案数据有环，其实是解析器在猜。所以 `HeadMap` 里那个 `has_header` 字段是必需的：
**缺列在有表头的表里意味着「用户删了它」，不意味着「大概是这一列」。**

同理，期初表原来靠「第 2 列是不是借/贷」判别是 6 列布局还是 3 列布局 —— 这件事
只对没有表头的老文件有意义。文件里明明写着列名还要靠位置猜，等于把用户能改的
东西当成了不能改的。

#### 二、页面上能改的，导出表里必须有

判定一张导出表够不够用，标准不是「字段全不全」，而是：**这个字段在哪个界面上
能改？能改的地方，表里有没有？** 按这条挨个查，v1.8.21 的四张表都有漏：

| 表 | 界面上能改、表里没有的 |
|----|----------------------|
| 客户/供应商 | 税点%、开票情况、信用额度、开户行、银行账号 |
| 存货 | 计量单位、备注、停用 |
| 科目 | 辅助核算维度、数量单位、币种、现金/银行标志、停用 |
| 期初 | 数量、分户（客户/供应商/存货/项目/部门/职员/银行账户） |

税点那一栏尤其要命：小厂 59 个客户每个税点都不一样（13% 专票 / 3% 代开 /
不要票）。原来只能点开档案一个个改 —— 想核对一遍税点，得点开 59 次；想搬账套，
税点全丢，之后每张凭证的销项税都要重算。

改法是把新列**一律追加在末尾**，老列位置一位不动：已经发出去的模板、用户手上
的旧文件、别处抄来的表格，全都还是按位置能被认出来。

#### 三、空单元格是「不动」，不是「清空」

导入器对扩展属性（税点、信用额度、开户行……）的规则是：**空单元格 = 保留原值**。
反过来做（空就是清空）会让「导一张只有编码和名称的表来改名字」变成一次
批量清零事故。这条与 §4.74 里「空金额写 `write_blank` 而不是 0」是同一个道理：
表里没有数，不等于数是零。

#### 四、这一节能被验证，靠的是三样东西

1. **往返测试**（`crates/finweb/tests/roundtrip.rs`，8 条）：真把导出的 xlsx 字节
   喂回 `findb::imports`，断言数据回到库里 —— 不是断言「表里有这一列」，而是
   断言「导回去之后客户的税点还是 13」。
2. **变异测试**：把「缺列时返回空」改成「退回位置」、把税点列的值改成空串，
   对应测试必须失败。变异测试守的不是代码，是「这条测试真的在守它该守的东西」。
3. **README 的测试基线表**：这几行的数字不允许下降。

### 4.76 网页版首页首屏：把「赚没赚钱、钱在谁手上」搬到浏览器

桌面版首页有两张卡：左边「本期经营结果」（净利润当主角，带利润率、环比、
成本 Top3、未记账提示），右边「钱在哪」（别人欠我 / 我欠别人 / 手头现金 /
净头寸，外加欠我最多的客户和我欠最多的供应商，带账龄）。网页版一直没有，
登录进去只有功能菜单 —— 而老板真正想在手机上瞄一眼的恰恰是这两张卡。

#### 一、数字由后端给，前端不算

`/api/dashboard` 的 `brief` 字段直接把**格式化好的字符串**和**已算好的比例**
交给前端：

```json
{
  "period": "2026-11", "revenue": "50,000.00", "cost": "12,000.00",
  "net_profit": "38,000.00", "margin": 76.0, "unposted": 1,
  "money": { "receivable": "230,000.00", "net": "222,000.00", "top_customers": [...] }
}
```

为什么不把原始数字丢给前端自己算？因为同一件事一旦在两端各写一遍，就会
各错一遍：

- 桌面版用 `Money::fmt_money()` 出千分位，网页端若自己 `toLocaleString`，
  小数位、负数括号、货币符号各有各的写法；
- 利润率的四舍五入（这里保留 1 位）、净利润的环比基准（上月净利润）、
  成本的取数口径（含 `5101 制造费用` 这类**未结转的 Cost 类科目**，
  见 §4.62 附近 v1.8.12 那次修复）—— 每一条都是踩过坑才定下来的。

后端取数一律复用桌面版同一条路径：`findb::advanced::financial_totals`、
`financial_analysis`、`money_position`、`vouchers::status_summary`。网页版
只做版式，不参与计算。

#### 二、收入为零时，利润率是 `null` 不是 0%

```rust
let margin = if t.revenue.is_zero() { None } else { Some(...) };
```

`0%` 会让人以为「这月白干」，而事实是「这月还没开张」——两件事完全不同。
JSON 里显式给 `null`，前端就不显示那一行，而不是显示一个刺眼的 0%。

#### 三、没记账的凭证：数字对，但必须当面说清

`unposted = draft + audited`（草稿 + 已审核未记账）。它们**不算进**收入/成本/
净利润，这是对的 —— 但老板看到「这个月只赚这么点」根本不会想到是自己录完
凭证忘了记账。所以首页直接摆一行：`⚠ 1 张凭证还没记账，未计入上面的数字`。

`crates/finweb/tests/home_brief.rs` 里 `draft_vouchers_warn_but_do_not_count`
同时盯住两件事：`unposted == 1`（提示了）且 `revenue == "0.00"`（没混进利润）。

#### 四、同一家既是客户又是供应商：标出来，并给净额

宏源那种厂（既是外发加工商，又偶尔拿货来做成客户）会有两条档案。首页两列
里各出现一次，每行带 `both: true` 和轧出来的 `net`：

- 客户行：他欠我 15,000、我欠他 28,000 → **净我欠他 13,000**（方向翻过来）；
- 供应商行：同一笔账，方向仍是我欠他。

`net_is_receivable` 给的是**这一行**的净额方向，不是「客户就一定是应收」。
第一版按行种类直接定方向，于是同一家在两列里显示了相反的结论。

#### 五、守它的是四条 HTTP 级回归

`crates/finweb/tests/home_brief.rs` 从**录凭证**开始，一路断言到 JSON：

1. `home_brief_is_derived_from_vouchers` —— 100,000 收入 + 15,000 房租
   （510105）+ 8,000 外发加工（510105）→ 成本 23,000、净利 77,000、
   利润率 77.0、应收 100,000、应付 8,000、净头寸 92,000；
2. `margin_is_null_when_revenue_is_zero`；
3. `draft_vouchers_warn_but_do_not_count`；
4. `party_with_two_identities_shows_net`。

配套 4 条变异（`tools/mutate-rust.js` 的 ⑰ 系列）：成本口径退回只算
6401/6402、利润率写死 0%、不提示未记账、不标同一家两种身份 —— 每条都必须
让上面的测试变红，否则就是「测试没在守它该守的东西」。

一个坑记在这里：测试里粘档案必须**两步**（`POST /api/aux-batch` 只解析预览，
`PUT` 才写库）。第一版只发了 POST，结果客户名字全变成编码、`both` 全是
false —— 看着像产品 bug，实际是夹具少发了一次请求。

### 4.77 性能：先量，再改，最后拿数字说话

「性能优化」最容易变成一场自我感动：凭直觉加缓存、把循环拆开、把函数改短，
看起来快了，实际瓶颈在别处，还顺手埋了「缓存不失效」的新 bug。这一轮把顺序
反过来 —— **先量出六个热点，逐个改，再量一次**。

#### 一、量出来的六个热点（6000 张凭证 / 12,000 条分录的真实规模）

| 位置 | 改前 | 改后 | 问题 |
|------|------|------|------|
| 网页首页 `/api/dashboard` | 233ms | 64ms | 见下 1、2 |
| `financial_analysis`（利润表整年趋势） | 168ms | 144ms | 逐月调 `financial_totals`，每调一次两次全表扫 |
| `money_position`（钱在哪） | 18.6ms | 10.3ms | 同上，多扫了一遍快照 |
| 单期内所有页面 | 每次重复扫 | 命中缓存 | 同一个请求里同一份快照被取 5 次 |
| `app.js` 传输 | 780KB | 211KB | 全站没有任何压缩 |
| 首页三个接口 | 串行 | 并行 | 浏览器可以并发，代码在排队 |

#### 二、五个改动，和每个改动「为什么必须这么写」

1. **成本构成不再为了 Top3 算一整年。**
   首页只要「钱花哪了」的前三条，却调用了给利润表画趋势用的
   `financial_analysis` —— 它为 10 个月各跑一次 `financial_totals`。
   新增 `advanced::cost_drivers_of(db, period, from, scope)`：一个区间、一份快照、
   只算成本类。**关键是它和 `financial_analysis` 必须同口径** ——
   两边都从同一个 `cost_driver_accounts(db)` 取科目清单，包括
   `5101 制造费用`（这是 v1.8.12 修过的老 bug：漏了成本类，净利润虚高）。
   测试 `cost_drivers_of_matches_financial_analysis` 就是拿两边的结果对表，
   对不上就红。变异 ⑱ 把成本清单改成空，这条测试立刻拦下。

2. **余额快照加了一层连接级缓存，键里带写入计数。**
   `BalanceSnapshot::load` 改为 `load_shared` → 内部走
   `db.snap_cache_get/snap_cache_put`。缓存键是把查询条件全部序列化
   （期间、起止、科目区间、辅助维度、各种开关），**外加
   `db.conn().total_changes()`** —— SQLite 连接级的累计写行数。
   任何一次插入/更新/删除都会让它变大，旧键自然不再被命中，
   所以不需要在任何写入口埋失效钩子（那条路必然漏掉某个写入口）。
   桌面版一个 `Db` 活很久，跨帧收益最大；网页版每个请求一个 `Db`，
   收益是「同一请求里不重复扫」。

3. **科目表也缓存，同样用写入计数做键。**
   科目表在一次请求里会被取几十次（每条分录补辅助核算、每次余额查询、
   每张报表），而它只在「改科目」时才变。变异 ⑱ 把校验改成不看计数，
   `chart_cache_sees_new_account` 立刻报「新建的科目取不到」。

4. **首页三个接口并行。** `viewDashboard` 里原本三个 `await` 串着写，
   总耗时是三者相加。改 `Promise.allSettled` —— 用 `allSettled` 而不是 `all`，
   是因为一块失败不该让整页空白：利润取不到也照样显示「钱在哪」。

5. **全链路 gzip，但 xlsx 不压。** `tower-http` 的 `CompressionLayer`，
   门槛 1KB，并且显式排除 `xlsx` —— 它本身就是 zip，再压一遍只烧 CPU，
   还会把 `Content-Length` 变成未知（下载进度条没了）。测试同时断言
   「该压的压了」和「不该压的没压」，只测前者的话，哪天全量压缩也照样绿。

#### 三、顺手修的一个真 bug：进账套停在「建账首月」

`select_book` 里取的是 `db.options().start_period`，而桌面版一直是
`periods::current_period`（最后一个已结账期间的下一期）。后果：账套结到
2026-09，网页一登录仍停在 2026-01，首页整块「本期经营结果」「钱在哪」
显示的是建账首月的数，**而且不会自己动** —— 老板只会得出一个结论：系统算错了。

这类 bug 属于「口子开在别处」：桌面版对的、网页版错的，两边各写一遍就必然有一天
对不上。测试 `selecting_a_book_lands_on_current_period_not_start_period`
从「录凭证 → 记账 → 结账 → 重新进账套 → 看 `/api/dashboard`」整条走完。

#### 四、量不出来的就别改

「导入 2000 张凭证要 11 秒」是**误判**：那是 2000 次单张 `save`（一张一个事务，
每张都在等 fsync）。真实的导入路径 `import_vouchers` 整批共用一个事务，
实测 2000 张 **1.7 秒（0.85ms/张）**。数字不对的时候先看自己量的是哪条路，
不要急着动代码 —— 这一轮唯一的「优化」是删掉两处多余的全表读。

### 4.78 第二轮性能：省掉的每一次全表扫都要有等价性证明

§4.77 收尾时留了三项「量过但没动」，这一轮把能动的两项做掉，第三项做的是
**判它不值得做**——并写清理由。

#### 一、首页的「本年累计」不该再扫一遍账

首页要显示两个数：这个月赚多少、今年累计赚多少。改之前后者是再调一次
`financial_totals(db, cur, 年初, ..)`。看起来只是多调一个函数，实际是
**一组全新的查询键**：余额快照的缓存按「期间区间」作键，`cur..cur` 与
`年初..cur` 是两份独立的快照，等于把整本账又扫了一遍（6000 张凭证规模下约 8ms）。

其实不用扫。余额快照里 `ytd_debit / ytd_credit` 本来就是「1 月至本期」的累计
发生额，`BalanceSnapshot::load_raw` 早就把它算好了；资产、负债又都是**时点数**，
与区间无关。于是新增：

```rust
pub fn financial_ytd(db: &Db, period: Period, scope: Option<&User>) -> DbResult<FinTotals>
```

它把 `from` 传成 `period`（查询键与 `financial_totals` 完全一致，必然命中同一份
缓存），只把损益读成 `ytd_*` 列。代价是一次缓存查找，收益是省掉一次全表扫。

**这里必须有一条等价性测试。** 两个数字各自都「看着对」，一旦分叉，症状是
首页的年累计与利润表的年累计对不上——而这条分叉几乎必然发生在
`load_raw` 里 `ytd_from` 的算法被人改动时（比如跨年该不该含建账前的
`debit_accum`）。`financial_ytd_matches_scanning_from_january` 同时断言三件事：
本年累计收入/成本/净利润与「从 1 月再扫一遍」逐项相等、数值本身对（收入 70000、
净利 56000）、时点数与本期那份相同（资产/负债/权益相等）而本期净利只有当月那两笔。

#### 二、快照扫描里最贵的一步，被九成行浪费掉了

用一次性剖析工具（临时插桩，量完即删）把 7ms 的冷快照拆开：

```
期初 38µs ｜ 凭证扫描 6.6ms ｜ 科目表 0.4ms ｜ 前缀预聚合 7µs
```

凭证扫描是全部成本，而 SQL 侧只占 2.1ms（把 3960 行的全列拉出来、不解析）。
也就是说**瓶颈不在数据库，在这层循环的每行工作**。再往下量单步：

| 每行动作 | 3960 行合计 |
|---|---|
| `serde_json::from_str::<AuxRef>(aux_json)` | **1.33ms** |
| `AuxRef::from_key(aux_key)`（等价替代） | 0.56ms |
| `Money::parse` × 3 列 | ~1.0ms |

关键洞察在另一组数字：3960 条分录只落到 **44 个**（科目, 辅助键）组合上。
而解析 `aux_json` 写在 `or_insert_with` 之前——**每一行都解析一次，然后九成九
的结果被丢掉**。把解析挪进「这个键第一次出现」的分支，一次快照省 1.3ms。

没有改用更快的 `AuxRef::from_key`：`aux_key` 由 `AuxRef::key_parts` 生成，
只含 `BALANCE_DIMS`（不含现金流量），而 `aux_json` 是全量。快照读的是余额口径，
眼下用不到现金流量维度，但这是**语义差异**而不是性能差异——为了 0.7ms
把「以后可能有人依赖的字段」悄悄丢掉，不划算。

#### 三、静态资源：真正的大头不在服务器，在手机流量

服务器上省 5ms，用户感知不到；但 `app.js` 211KB（gzip 后）原来是**每次打开都回源
验证**，在移动网络上那是一到两秒。而 `index.html` 里每个资源都带 `?v={{V}}`，
版本号由静态文件 mtime 推出——**内容一变 URL 就变**，所以让浏览器一年内不再回源
是安全的：

| 请求 | `Cache-Control` | 理由 |
|---|---|---|
| `/app.js?v=1730…` | `public, max-age=31536000, immutable` | URL 随内容变化 |
| `/app.js`（手输直达） | `no-cache` | 没有版本号兜底，必须回源 |
| `/`（首页） | `no-cache` | 它负责注入 `{{V}}`，缓存住等于把旧版本号钉死 |

顺带修掉一个**只有开了长缓存才会致命**的漏洞：`asset_version()` 算版本号时
漏了 `icons.js`。以前漏项只是「下次回源就对了」，现在漏项意味着「一直错到别的
文件也被改」。**清单必须与 `index.html` 里带 `?v=` 的文件逐个对齐**——
这条没办法靠类型系统保证，只能写在注释里并在改动时对照。

三个用例分别盯住三种请求的响应头（`tests/static_cache.rs`）。变异 ⑲ 把版本化
分支改成 `if false`、把首页的 `no-cache` 删掉，两条测试各自立刻变红。

#### 四、明确判定「不值得做」的一件

`/api/workbench` 的 23ms 里，与期间数无关的固定成本约 20ms：`collect()` 自己
只有 3.7ms，其余是「当期卡片」用的两张完整报表各取一次快照。而趋势部分
（3 期 → 12 期 → 24 期：24.7 / 27.3 / 32.9ms）每期只加约 0.4ms，因为快照缓存
已经把重复取数吃掉了。**再优化只能去打「快照本身」，而那是另一个量级的事**
（把期间余额做成写时维护的汇总表），风险与收益都不成比例。

`app.js` 拆包同理：开了长缓存之后，211KB 一个版本只下一次，拆包换来的是
构建复杂度与「少一次请求」之间不划算的交换。

### 4.79 打印版式与账套参数：同一件事写在两个地方，迟早会分叉

这一节讲两件看起来无关、实际是同一个病的事：**打印版式**和**参数校验**，
原来都「各端各写一遍」，于是同一份报表在两个端上打出两种样子，同一个字段
在两个端上有两套规则。

#### 一、打印版式原来是硬编码在样式里的

桌面端 `finui::views::export::sheet_to_html` 和网页端 `finweb::report_html`
各有自己的 HTML 模板，纸型、字号、页边距、页码、落款全是写在字符串里的常量：
A4 纵向、13px、默认边距、没有页码、没有落款。想改就得改代码发版——
而「我们厂的报表要横向、要素齐」是**每个厂不一样**的正常需求。

更隐蔽的是对齐方式：两端都是 `td:last-child { text-align:right }`。
那是个把报表结构硬编码进样式的假设——财务报表最后一列确实是金额，
但**凭证清单、明细账、档案列表的最后一列是备注或摘要**，结果整列文字
被顶到右边，看着像排版坏了。现在按内容判断：

```rust
// 非空单元格里有九成以上能解析成金额，才把这列当金额列（右对齐 + 等宽数字）
pub fn is_money_column<S: AsRef<str>>(cells: impl Iterator<Item = S>) -> bool
```

规则放在 `fincore::print`，两端都调它。**不是**「顺便统一一下」，而是因为
不统一的后果没人会发现：没有人会同时打开两处源码比对，用户只会说
「打印出来怪怪的」。

#### 二、校验写在界面里，等于漏一条路径就漏一个口子

`BookOptions` 有三个写入口：桌面「账套参数」页、网页 `PUT /api/options`、
建账向导。原来三处各校各的：

| 字段 | 桌面端 | 网页端 |
|---|---|---|
| 启用期间 | 能解析成 `YYYYMM` | 同左 |
| 科目级长 | 能解析成数字 | 每级 1–12 位、最多 8 级 |
| 凭证字 | 不查 | 查空项 |
| 业务默认科目 | **不查** | **不查** |

第 2 行的差异就是分叉的样本：同一个字段，网页存不进、桌面存得进。
第 4 行是真正的坑：`biz_accounts` 的六个编码被收付款单、发货收入、暂估入库
等十几条自动生成凭证的路径直接拿去当科目用。填了一级科目 `1122`，保存时
不会有任何提示，直到某天点「发货」才报「科目不能直接记账」——而那时候
**单据已经开出去了**，人只会认为系统坏了，不会想到是半年前账套参数里错一位。

所以校验收敛到两处，各自只做自己能做的事：

- `BookOptions::validate()`（fincore，不查库）：级长范围、凭证字空项、
  本位币非空、六个科目编码非空且形如编码、打印设置越界。
- `findb::accounts::check_biz_accounts(chart, biz)`（要查库）：科目存在、
  且是**末级**。科目表为空时直接放行——建账向导允许「先设参数、后建科目」。

两者都在 `Db::set_options` 里兜住：

```rust
pub fn set_options(&self, o: &BookOptions) -> DbResult<()> {
    let mut problems = o.validate();
    if let Ok(chart) = crate::accounts::chart(self) {
        problems.extend(crate::accounts::check_biz_accounts(&chart, &o.biz_accounts));
    }
    if !problems.is_empty() {
        return Err(fincore::FinError::Validate(problems.join("；")).into());
    }
    ...
}
```

`set_options` 是唯一落库口，所以桌面端和网页端自动获得同一道闸。
网页端 `put_options` 里那段手写的级长检查因此删掉了。

#### 三、打印设置为什么放账套参数，而不是本机配置

小工厂的典型场景是「办公室打报表、宿舍看电脑」。跟着机器走，同一份报表
在两台机器上打出两种版式，谁也说不清哪个对；而「这套账的打印口径」本来
就属于账套，跟公司名、级长、凭证字是同一类东西。旧账套没有该字段时
`#[serde(default)]` 给默认值（自动 / 11pt / 12mm / 全显示），不追溯改存量行为。

代价必须写清楚：`PUT /api/options` 收的是**整个** `BookOptions` 并整体覆盖。
前端保存时少带 `print` 字段，`serde(default)` 会把它悄悄重置成默认——
症状是「刚调好的版式，一保存又回原样」，而接口返回 200。
所以设置页的保存是「拿到的对象原样保留 + 只覆盖改过的键」，并有
`print_settings_survive_save_and_reload` 这条用例专门盯住它。

#### 四、「自动」的方向判定：按列数，不按报表种类

A4 纵向扣掉页边距约 186mm，一列内容（日期 / 摘要 / 数量金额）平均要占 20mm
以上，8 列就已经挤到折行。所以判定是 `cols > 8 → 横向`，列数超过这个数
自然转横向。没按「这是明细账所以横向」写死，是因为同一张报表在启用数量核算
或外币之后列数会变，而**报表种类清单没人会同步维护**。

#### 五、页码：勾了却没出现，不是功能没做

页码用 `@page` 的页边距盒子实现（`@bottom-right { content: "第 " counter(page) … }`），
这是浏览器里唯一能拿到 `counter(page)` 的地方。旧内核（Chrome < 131 等）
不认识页边距盒子，会**整块忽略且不报错**，症状正是「设置里勾了页码，
纸上没有」。这种「分不清是我们的代码没生成、还是浏览器不支持」的情况，
只有测试能分辨：`page_number_can_be_turned_off` 断言关掉后 HTML 里不出现
`counter(page)`，变异 ⑳ 把该分支改成 `if false` 立刻变红。

同理，界面上要写明这个前提，别让人以为是功能没做。

#### 六、顺便修掉的一处旧口径

打印页原来按「财务惯例」把零值打成空白。纸面上没错，但屏幕上整列空白会被
当成「金额列没取到数 / 接口缺列」——用户就是这么报障的。网页端与接口
（`table_json`）一直是 `0.00`，只有打印页单独留空，属于**同一张表两套口径**。
现在统一成 `0.00`，`print_zero_normal_row_shows_money` 盯着它。

#### 证据

四个变异（⑳）各自盯住一条：
`勾了页码却不生成页边距盒子` / `选横向也不横向` /
`打印设置不进账套参数校验` / `业务默认科目不查末级`。
新增用例：`fincore::print` 8 条、`report_html` 4 条、
`tests/options_print.rs` 5 条（往返、越界被拒且原值不动、一级科目被拒、
不存在科目被拒、GET→PUT 幂等）。

### 4.80 套打与薄壳：把「第三种写法」收干净

§4.79 把报表打印和账套参数各收敛到一处。这一节收尾剩下的三种分叉——它们都是
同一类：**同一件事有三个地方在写，改一个忘两个**。

#### 一、套打三种纸各有自己的一句 `@page`

凭证套打（`VOUCHER_CSS`）、账簿套打（`LEDGER_CSS`）、单据套打（`page_setup`）
原来都把纸张尺寸和边距写死：

```css
@page{size:A4 landscape;margin:12mm 10mm;}   /* 凭证，写死 */
@page{size:A4 landscape;margin:10mm 10mm;}   /* 账簿，写死 */
@page{size:A5;margin:8mm;}                   /* 单据，按纸型算 */
```

于是「账套里设了页码/横向/偏移」，报表跟着变了，套打一点不动——而套打恰恰是
**最需要对位**的地方：针式打印机走纸偏 2–3mm 是常态，以前只能改打印机驱动或者
忍着，压线压到金额上看不清。

改法：纸张规则统一从 `PrintOptions::page_box_css(size, base_margin_mm)` 出。

```rust
// 偏移是「内容整体往右下推」，等价于左/上边距变大、右/下变小
let l = (base + self.offset_x_mm as i32).max(0);
let r = (base - self.offset_x_mm as i32).max(0);
```

`page_setup` 拆成 `page_spec`（返回 size 片段 / 行单位预算 / 基础边距 / 窄纸附加
CSS）+ 一个兼容旧调用的 `page_setup` 包装。四个套打入口（凭证、账簿、订单、
收付款单）都多收一个 `po: &PrintOptions`。

**两个细节，缺一个就白做**：

1. **套打不接字号**。`page_css` 会把 `font-size:Npt` 一起写出去，而套打纸的格子
   是按 px 固定的（`.form`、`tr.l{height:21px}`），被 pt 一冲就溢格。所以纸张规则
   和字号规则拆成两个方法：`page_box_css`（只有 `@page`）与 `page_css`（报表用，
   两者都要）。
2. **负边距要夹到 0**。`margin:-8mm` 不是「负边距」，是**非法值**——浏览器会把整条
   `margin` 声明丢掉，纸张回到默认边距，比不设还乱。

#### 二、科目余额表打印是第四份 `<style>`

`trial_balance_html` 自己写了一整套 `<!doctype html>…<style>body{…} .pbar{…}`。
后果和 §4.79 一模一样：账套里设了页码、横向、偏移，这张表全都不跟着变。

改法：`report_html::shell` 提升成公开的 `page_shell(title, company, subtitle,
unit, table_html, cols, po)`——**表体各不相同，壳只留一个**。科目余额表自己只拼
`<table>`，其余交给 `page_shell`。

#### 三、桌面端少了三个设置项

网页端早就有「预算控制 / 单据前缀 / 启用生产制造」，桌面端的账套参数页一直没有。
这不是「少个功能」，是**同一套账在两处看到不同的设置项**：在网页上把预算强控打开，
回到桌面端根本找不到开关，也不知道它开着。

补上之后两端一致。这一类的检查办法不是看代码，是**把两边的字段清单并排比一遍**：
字段名对不上的，就是漏的。

#### 四、结构校验补齐了四类「填错不报错」

| 填错 | 原来会怎样 | 现在 |
|------|------------|------|
| `budget_control = "warning"` | 只有 `warn`/`strong` 生效，其余按关闭 → 超预算一路放行 | 报错并带出原值 |
| `doc_prefixes` 键写成 `purchase` | 只有 `po/so/req/quo/prod` 被读 → 永远用默认 CG | 报错并指出拼错的键 |
| 单据前缀填 `C G`（带空格） | 单据号里带空格，搜索/对账都难对 | 只允许字母数字，≤8 字符 |
| 凭证字重复（`记,记`） | 两张凭证同号，谁也说不清 | 报错 |
| 本位币填「人民币」 | 外币折算按 `CNY` 硬编码走，填什么都一样 | 必须三位字母代码 |
| 企业名称留空 | 报表抬头、套打单据全空 | 报错（并把 `Default` 改成「未命名单位」，让默认值自洽） |

一行 `validate()` 顶掉的是一类「静默不生效」——这类 bug 的特征是**没有任何报错**，
只能靠人某天发现「怎么设置了没用」。

### 4.81 期初收集表：一本工作簿四张纸，一次导完且先算平

工厂把《期初收集表.xlsx》填回来后，要落三样东西：往来台账（算账龄、出对账单）、
`112201`/`220201` 的科目期初（资产负债表的应收应付数）、各账户与实收资本的期初。
入口在「期初建账 → 导入期初收集表」。

#### 一、台账与科目余额是两本账，必须一起写

`arap_opening` 是**台账**：一张一单，用来算账龄、出对账单、催款。
资产负债表的应收数是 `112201` 的**科目余额**。两者互不推导。

只导台账不导科目，症状是「账龄表上明摆着欠 7 万，资产负债表应收是 0」；
只导科目不导台账，症状是「报表对了，但查不出是哪家欠的、欠了几天」。
两个都写，才有得对。

代码上这两步在同一个函数里紧挨着（`opening_book::import_collection_sheet`），
中间由一条测试守着：把 `112201` 那句删掉，`collection_sheet_lands_in_ledger_and_opening_balances`
立刻红。

#### 二、先算平再落库

期初借贷不平，试算平衡开账就是不平的，之后每个月每张报表都歪 —— 而且很难倒推
是哪一步错的。所以这里**先算完再写**：

```
借方 = 应收合计 + 资产类账户（1 开头）
贷方 = 应付合计 + 负债类账户（2 开头）+ 实收资本 4001 + 本年利润 4103
```

不等就整批拒绝，错误信息里带三个数：借方合计、贷方合计、差额，并提示
「把差额补到 ④ 基本资料 → 本年利润 4103」。拒绝时不写任何一条 —— 报错但留下
半个账套，比不导更难收拾。

一个刻意的便利：只填了实收资本、**没填**本年利润时，用差额自动补 `4103` 并在
结果里给出提示。这不是猜，收集表④「所有者权益（轧差）」本身就是这么算的；
但如果用户**明确填了** 4103，就绝不再动它，让不平直接暴露。

#### 三、缺纸要明说缺哪张

文件名、纸张顺序都可能被改。匹配按表名关键字（`客户应收`/`供应商应付`/`账户余额`），
名字被人改了就退回按顺序取（第 1 张是「怎么填」，数据纸从索引 1 起）。
三张数据纸缺任何一张都直接拒绝，并列出应有的三张 —— 不玩「导成功但什么都没导」。

列头也是按名字认的（`col(head, &["欠款金额","金额","余额"], 2)`）：工厂把「单据号」
和「备注」调了顺序，按位置取就会把备注当单据号写进台账。

#### 四、账龄表要能导出，而且必须与界面同一份取数

账龄表以前只能截图。老板发给客户、存档给会计，截图既不能改也不能算。

`/api/settle/aging/xlsx` 与 `/api/settle/aging` 走同一个
`findb::settle::aging`，只是最后一步换成文件。这样界面上的数字与文件里的数字
不可能分叉 —— 如果各自写一套取数，早晚有一天两边的账龄不一样，而谁也说不清
该信哪个。

文件名带科目（`往来账龄_2202_20261027.xlsx`）：导出应收与应付两个文件时，
文件名不带科目就分不清哪个是给客户的、哪个是给供应商的。这条也有测试守着
（导出 2202 却写死 1122 会被拦下）。

#### 五、三份证据

| 守什么 | 测试 |
|--------|------|
| 台账与科目期初都写、期初就是平的 | `crates/findb/tests/opening_book.rs::collection_sheet_lands_in_ledger_and_opening_balances` |
| 不平整批拒绝、一笔不留 | `opening_book.rs::unbalanced_sheet_is_rejected_and_nothing_is_written` |
| 不是收集表要拒绝且说人话 | `opening_book.rs::non_collection_workbook_is_rejected_with_a_readable_reason` |
| 接口层同样行为（不只库层） | `crates/finweb/tests/opening_sheet.rs`（3 条） |
| 账龄导出跟科目走 | `crates/finweb/tests/export_xlsx.rs::settle_aging_export_as_xlsx` |

### 4.82 数据外带的边界按岗位划，不按「安全感」划

v1.8.29 加了「账龄导出」之后马上撞上一个问题：后端要 `Perm::Export`，而这个权限
只有管理员与财务主管有。可是**催款前导账龄的正是应收会计**——他们的日常活就是
「把账龄表发给客户」「把应付清单发给老板」。不给导出，真实行为不是「他们就不导了」，
而是**改用截图**：截图不进操作日志、不能对账、改一个数字也没人知道，比开权限更糟。

所以这一版的边界改成：

| 岗位 | 导出（`Export`） | 理由 |
|------|------------------|------|
| 系统管理员 / 财务主管 | ✅ | 一直有 |
| **应收会计 / 应付会计** | ✅（本版新增） | 发账龄、发应付清单是本职，且已在报表权限内 |
| 会计 / 出纳 / 审核 / 仓管 / 订单专员 / 成本会计 / 只读 | ❌ | 只能打印预览：纸面留痕可控 |

`Backup`（账套文件副本）**仍然只有系统管理员**——能导出报表 ≠ 能拿走整个账套。

#### 开了权限就必须留痕

导出等于把数据带出门，所以账龄导出补了操作日志：

```
导出 · 导出往来账龄 · 2026-10 至 2026-10-27 · 科目 1122 · 24 行
```

谁在什么时候把多少家的往来余额带出去，事后查得到。这条也有测试守着
（`export_xlsx.rs::settle_aging_export_as_xlsx` 里读 `/api/logs` 断言）。

#### 顺手修的三个「看着在守，其实没守」

1. **按钮没按权限显示**：账龄导出按钮原来对所有角色都渲染，会计点了得到 403 ——
   死按钮。现在 `can("export")` 才显示，与其它导出按钮一致。
2. **变异助手 `CORE` 丢参数**：`const CORE = (name) => [..., "user::tests::"]` 里 `name`
   没被用上，实际效果是「跑所有 user 测试」。于是某条变异被**别的**用例顺手拦住，
   也显示 PASS，看不出目标用例到底守没守住。改成 `user::tests::${name}` 后重跑，
   两条旧变异仍然 PASS（说明它们本来就被正确守住，只是判断方式不精确）。
3. **变异插了重复 match arm**：想验证「导出权限顺手开给会计」，第一版插了一条
   `Role::Accountant => &[Report, Export],` —— 但 match 取第一条，原分支在前，
   变异等于没生效，测试照过、被误读成「放过了」。改成直接在真分支里加 `Export` 才
   拦得住。这类「改了源码但语义没变」的变异，是这个工具最容易骗过自己的地方。

### 4.83 变异测试要分片，但分片会带来一个新的静默失效

变异测试（把代码改坏、要求测试报红）是这个仓库最贵的一道门禁：58 条变异串行跑一遍
要 **35–40 分钟**，`timeout` 已经贴到 60 分钟边缘。发一次版等一次，代价是实实在在的。

所以切成 4 片并行：`node tools/mutate-rust.js --shard 2/4`，按**下标取模**切。

#### 为什么用取模而不是按前缀分组

`--shard i/N` 取 `MUT.filter((_, k) => k % N === i - 1)`。这样

- 交集为空（每个下标只落一片）
- 并集为全（每个下标必落一片）
- 变异增减时不用重新分组，性质自动保持

按「⑤ 开头归第 1 片、⑩ 开头归第 2 片」那种分法，一改名字就漏。

#### 分片引入的三个新坑，都做了防护

1. **空分片会静默通过**。分片参数写错（`--shard 5/4`）或分母大于条数时，取模结果为空，
   `for` 循环一次不跑，脚本会打印「全部 0 个变异都被拦下」然后 exit 0 —— 看上去一片绿，
   实际一条没跑。现在 `RUN.length === 0` 直接 `exit(2)`。
2. **片数与分母写在两个地方**。`matrix.shard: [1,2,3,4]` 与 `--shard ${{ matrix.shard }}/4`
   是两行，只改一处就会让某些下标**永远不被取到**（分母改大）或**被取不到**（分母改小），
   而 CI 依旧绿。`tools/check-ci.js` 现在核对这两处一致，并且验证过：
   - 把 `/4` 改成 `/5` → `FAIL 分片数不一致：matrix.shard 有 4 片（1,2,3,4），但 run 里写的是 /5`
   - 把 `[1,2,3,4]` 改成 `[1,2,3]` → `FAIL 分片数不一致：matrix.shard 有 3 片，但 run 里写的是 /4`
3. **`--list` 的输出必须保持纯 JSON**。分片时脚本会打印一行「分片 2/4：本次跑 15 条」，
   而 `check-ci.js` 用 `--list` 去 `JSON.parse` 清单 —— 那行标题混进标准输出会让解析失败。
   现在 `--list` 时不打标题，并且 `--list --shard i/N` 输出的是**该分片的清单**，
   于是「分片是否覆盖全、是否互斥」可以机械验证：

   ```
   shard 1/4: 15 条   shard 2/4: 15 条   shard 3/4: 14 条   shard 4/4: 14 条
   覆盖完整: True  总数: 58
   ```

   （15+15+14+14 = 58；不是均分，因为取模对 58/4 本来就会余 2。）

#### `fail-fast: false` 是有意的

一片红就取消其它三片，会掩盖「到底哪几条变异没守住」——而变异测试的价值恰恰是
**看全貌**。宁可多花几分钟，也要一次拿到完整清单。

### 4.84 催款单的金额：绝对值不是「欠多少」，方向才是

`OpenEntry::open()` 返回的是 `abs(signed) - settled` —— 一个**没有方向**的绝对值。
它回答的是「这笔单据还剩多少没核销」，不是「对方欠我多少」。

`settle::dunning_create` 一开始就栽在这里：它把每个未核销单据的 `open()` 直接累加
成催收金额。客户预存 3 万（贷方，走 112201）时，`signed` 是负数、`open()` 是 3 万，
于是催款单上写着「应向我方支付 30,000.00」，还附上那笔预收的明细。客户收到会直接
翻脸，而这笔钱本来就是他自己先给的。

更麻烦的是**同一份数据在账龄页上是对的**：`engine::aging::analyze` 把负数的那部分
单列到 `credit_total`（即「其中预收/预付」）。两个页面、两个口径，代码里没有任何
一处报错。

改法：

1. 用 `aging()` 同一套方向归一 —— 贷方性质科目（2202 等）先翻号，让「正数 = 对方
   欠我方/我方欠对方」在全系统是同一个方向。不翻的话，供应商一张正常的发票
   （贷方记 220201）会被判成「预付」，对账函上一条应付都不显示。
2. 明细行带 `direction`（应收/应付/预收/预付）。催收金额只累加「应收/应付」那一侧；
   预收/预付单独汇总展示 —— 客户看得懂「你给 5 万、我先收了 3 万、实际还欠 2 万」。
3. 一分钱不欠时**直接拒绝生成**。以前会出一张 0.00 元的催款单，比不发更糟。
4. 老单据的 `direction` 是空串（`serde(default)`）。**空串一律按应收/应付处理** ——
   那些单据生成时还没有方向概念，把它们改成预收等于篡改历史。

导出同理：`/api/export/dunning` 那份 CSV 只有一行汇总，客户问「是哪几张单凑的 5 万」
答不上来。新的 xlsx 导出出两个 Sheet（汇总 + 逐单明细），明细带方向列。

### 4.85 「查哪个月的账龄」不该由今天的日期决定

`/api/settle/aging` 的基准日 `as_of` 缺省值曾是 `chrono::Local::now().date_naive()`
（今天），而桌面端一直是 `upto.last_day()`（查询期间的最后一天）。

后果：查 2026-03 的账龄，一笔 3 月 5 日的单据被算成 200 多天，全部落在最老的那一档；
桌面端同一份数据显示 26 天。两个答案，导出的 Excel 跟网页一致、跟桌面不一致 ——
谁也不敢拿去给老板看。

改法：服务端缺省 `upto.last_day()`。基准日是**查询参数的一部分**，不该由今天决定；
用户真要「按今天算」，显式传 `as_of` 就行。

这条也进了变异清单：把缺省改回「今天」，`settle_aging_defaults_to_period_end` 必须变红。

### 4.86 三条「看着能用、其实没接上」的地方：建账校验、未核销清单、套打纸型

这一节记三处**代码都在、开关都有、就是没生效**的缺陷。它们的共同点不是写得差，
而是「写在了只有一半路径会走的地方」——所以修法都不是加功能，而是**把两条路径并成一条**。

#### 一、建账和导入账套不过参数校验

v1.8.27 把账套参数的校验收敛进 `Db::set_options`（`crates/findb/src/lib.rs`），
理由是「写参数的路径有三条，校验写在界面里就等于哪条忘了调哪条能写脏数据」。
但**写参数还有第四条路：建账本身**。`create_with` 当时没调校验，于是：

| 填错 | 建账时 | 第一次在参数页点保存 |
|------|--------|----------------------|
| 应收科目写成 `1122`（非末级） | 账套建出来了 | 才报「必须是末级」 |
| 预算控制写成 `warning`（该是 `warn`） | 账套建出来了 | 才报「只能是 off/warn/strong」 |

中间的每一天，自动生成凭证的那条路都在用 `1122` 去找科目 —— 找到的是汇总科目，
分录记上去就等于记在一个不该记账的科目上。而用户会认为是「新版本把保存按钮弄坏了」。

修法：新增 `Db::validate_options_for_new_book(opts)`，结构校验走 `opts.validate()`，
科目校验用 `fincore::chart::default_accounts()` 建一张**临时科目表** —— 建账这一刻
账套里还什么都没有，但 `seed_builtin` 紧接着就会灌这套内置科目，所以能提前判。
`create_with` 与 `in_memory_with` 都调它，报错信息里带上具体是哪一项。

这条也说明一件事：**校验放在「落库入口」还不够，要放在「所有能产生一个库的入口」**。

#### 二、未核销清单一次返回全部

`/api/settle/open` 原来把该科目所有未核销分录一次给完。1980 张凭证的账套实测
**222.9 KB**，按 6000 张推算会到近 700 KB —— 手机上看一眼核销页要下半个兆。
核销页与账龄下钻都吃这个包，是这一块唯一会随账套规模变差的地方。

改成分页（默认 200 笔、上限 2000、`limit=0` 保留全量给导出与脚本），同时把
**合计与笔数算在分页之前**。这一条不是性能问题，是**口径问题**：

> 第一页说「共 792 笔、合计 848 万」，翻到第二页变成「共 200 笔、合计 214 万」，
> 会计会以为钱少了。

所以 `total` / `sum_debit` / `sum_credit` 一律按**全部**未核销算，只有 `rows` 分页；
`truncated` 明说「还有没给的」。悄悄少给几行比慢十倍更坏 —— 表现是「这单明明还欠着，
核销页里找不到」。实测同一账套：**222.9 KB → 56.2 KB**，三页的合计都是 8,482,200.00。

#### 三、套打纸型：三种纸不能共用一个设置

凭证套打原来写死 `A4 landscape`（`crates/findb/src/printform.rs`），单据走
`page_spec(size)` 已经可配，而**账簿把 `PrintOptions` 收进来了却一行没用** ——
所以凭证能调偏移、账簿不能，同一个针式打印机上两种纸表现不同。

小厂的实际用纸是三种同时在用：凭证 A5 或 241×140 连续纸、账簿 A4、
收付款单 A5 或三等分联。一个全局纸型必然有一头打歪，于是加了三档：

```rust
pub enum PaperUse { Voucher, Ledger, Doc }

fn paper_choices() -> [(&'static str, &'static str); 5]   // 两端的下拉都从这里取
fn paper_size_css(value: &str, landscape: bool) -> Option<String>
```

认不出来的值（`B5`）**保存时报错**、打印时兜底 A4 —— 两边都要有兜底：
只在保存时报错，老账套里的脏值会让人打不出纸；只在打印时兜底，用户会以为设置生效了。

#### 四、账龄下钻：天数要跟账龄表同一个基准

账龄表只给「最老 148 天」，答不了催款第一句要问的「这 5 万是哪几张单、各挂多久」。
`/api/settle/open` 加了 `party=` 过滤与 `days` 字段后，账龄行点一下就能看到明细。

`days` 必须按 **`upto` 期间最后一天** 算，不能按今天：账龄表的 `max_days` 是期末口径，
两处一个按今天一个按期末，就会出现「账龄说 148 天、下钻说 160 天」，而差的那 12 天
正好是会计对账时最想问的。这一条在测试里钉死了（`2026-01-10` 的单在 `upto=202601`
下必须是 21 天）。

### 4.87 核销记录记在哪一期，以及为什么「已结账」要拦住撤销

**一、记录期间 = 核销发生的期间，不是单据的期间**

`settle_record.period` 原来写的是 `f.period`（被核销分录的期间）。于是 11 月收到
客户还 8 月的货款，台账里那笔核销记在 `202608`。两个后果：

- 账面看不出「钱是哪个月收的」——而这正是对账时最常问的一句；
- 8 月可能已经结账，却还能往里面塞核销记录。

改成 `periods::current_period_of(&tx)`（最后一个已结账期间的下一期）之后，规则自洽了：
**新增核销永远落在未结账的当前期**，所以下面那条「已结账不许撤销」不会把正常业务
卡死 —— 今天做的核销，今天所在的期间一定没结账。

一个坑：`current_period_of` 只吃 `&Connection`，不是 `&Db`。核销要在同一个写事务里
「读结账线 → 写记录」，两步之间不能有窗口（刚判完没结账，别人把期间结了）。

**二、已结账期间的核销不许撤销**

账龄、未核销额都是「截至某期」的数。结账之后把它改掉，等于让已经出过、签过字的
报表对不上账。所以 `unsettle` / `unsettle_part` 都会先看记录所在期间：

```
这条核销记在 2026-08，该期间已结账（已结至 2026-09）——已结账期间的核销不能撤销。
确需更正请先反结账，再改动。
```

反结账那条路有日志、有明确意图，走它是对的。

**三、部分撤销：三张单核销了 5 万，事后发现其中一张该是 3 万**

以前只能整条撤销再重录。撤销的瞬间三张单全变「未核销」，账龄立刻虚高——而这段
时间里别人（老板、客户）看到的数就是错的。

现在 `unsettle_part(db, id, amount)`：减掉 `amount`，减到 0 就整条删除。守卫两条：
`0 < amount <= 记录金额`（超了报「撤销金额 X 超过这条核销记录本身的金额 Y」）、
期间未结账。

界面上：网页核销记录里点「取消核销」弹窗填金额（填全额或留空 = 整条撤销）；
桌面版核销记录上方有「撤销金额」输入框。两者都清楚写着「先填金额再点取消，可只撤
一部分」——这句话不能省，否则没人会想到能填。

**四、测试与防呆**

| 断言 | 守的是什么 |
|------|-----------|
| 记录期间 = 核销发生期 | 记成单据期间就等于往已结账期间塞记录 |
| 已结账拒绝撤销 | 结账后改数 = 报表对不上账 |
| 部分撤销后未核销额回来 | 撤了钱却还显示已核销，比不能撤更糟 |
| 超记录金额被拒 | 撤出负数等于凭空造账 |
| 空串 = 整条撤销、`5万` = 400 带原值 | 老前端只传 `{id}`；写错必须当场说清 |

变异 5 条（撤销不看结账线 / 部分撤销不夹记录金额 / 记录仍按单据期间 / 撤到零不删 /
空串当非法金额）全部被拦下。

### 4.88 期初收集表：模板必须能自己长出来，而且要能"先试后做"

#### 一、模板不该是"下载一份空白 xlsx"

期初那四张纸（客户应收 / 供应商应付 / 账户余额 / 基本资料）以前只能靠
`examples/opening_sheet.rs` 跑出来，工厂实际拿到的是**一份示例账套的模板**——
里面填着别人的 59 个客户、27 个供应商。

后果是：工厂要么照着改成自己的（改错编码就整批导不进去），要么回去抄科目编码。
而编码恰恰是最容易抄错、错了最难查的东西（`112201` 抄成 `112021` 会得到
"科目不存在"，但用户不知道是抄错还是系统没有）。

所以模板改成**按当前账套现场生成**：

| 那张纸 | 预填什么 | 为什么 |
|--------|----------|--------|
| ① 客户应收 | 账套里每个启用客户一行，编码+名称已填 | 工厂只需要填"欠多少" |
| ② 供应商应付 | 同上 | 同上 |
| ③ 账户余额 | 所有 1xxx / 2xxx 末级科目，编码+名称已填 | 不用背编码 |
| ④ 基本资料 | 实收资本、本年利润两行 | 差额自动轧 |

**③ 刻意剔掉两类科目**：

- `1122 / 2202`：余额由 ①② 两张纸的往来合计自动生成，在 ③ 里再填一遍就是双计；
- `4xxx` 权益类：由 ④ 生成，同样会双计。

双计的可怕之处不是"多一行"，而是**借贷两边各多一份、看起来还是平的**——
试算平衡表会通过，错在别处才爆发。

#### 二、模板里还要有"怎么填"

四张纸之外多一张「怎么填」：

- 预收 / 预付填**负数**（正数=他欠我，负数=我欠他）；
- 编码和名称填一个就行，另一个留空会自动补；
- `1122 / 2202` 的科目余额**不用填**；
- 权益类只填在 ④，③ 里再填一遍会双计；
- 金额一律填正数，借贷方向按类性质自动判断。

这张纸不参与导入（解析器按表名找那四张），但它是"用户第一次用"时唯一能读到的说明。

#### 三、先预检，再导入

`/api/books/opening-sheet/preview` 与导入走**同一段代码**，只差最后一件事：不写库。

响应里给全四张纸的行数、金额合计、逐条问题，外加 `dry_run: true` 与
`debit_total / credit_total`。不平就 400，并且第一句就说清是不平：

```
期初借贷不平：借方合计 50000.00，贷方合计 0.00，差 50000.00。
```

这一步的价值：期初是最容易出错、又最不该出错的一次性操作。用户填错了，
**预检告诉他哪一行不对**，而不是让他先导入、发现试算不平、再猜是哪张纸。

#### 四、闭环保卫：从 HTTP 下载模板 → 填数 → 传回去

新增 `crates/finweb/tests/opening_sheet_loop.rs`，三条：

1. `template_carries_the_current_books_account_codes` —— 模板里必须有当前账套的
   `1001`，且**不许**出现 `1122 / 2202`；
2. `preview_does_not_write_then_import_does` —— 同一份填好的表先预检（此时
   `/api/begin` 必须还是 `[]`），再导入（此时必须有 `1001`）；
3. `preview_rejects_an_unbalanced_sheet` —— 只填资产不填权益，预检必须 400 且说"不平"。

前两条合起来才叫闭环：只测"能导入"测不到"导出的模板能导回去"，而后者才是用户
真正走的那条路。

#### 五、三条变异守着它

- 预检其实也落库（`dry_run` 分支失效）→ 第 2 条红；
- 模板不预填科目清单（①③ 变空表）→ 第 1 条红；
- 不平也预检通过 → 第 3 条红。

### 4.89 期初对账：导入成功不等于账对了

`import_collection_sheet` 返回 `ok: true` 只能证明三件事：文件格式对、借贷平了、数据进了库。
它证明不了一件事——**库里的数和表里的数，是不是同一套东西**。

#### 一、为什么必须回读库

期初的往来有两条独立写入路径：

| 路径 | 谁在用 | 漏了会怎样 |
|------|--------|------------|
| `arap_opening` 台账 | 账龄、对账单、催款单 | 报表里有应收、账龄表里没有 |
| `112201 / 220201` 科目期初 | 资产负债表、试算平衡 | 账龄表里有欠款、报表里一分没有 |

两条都写对了才算对。任何一条漏掉，两边各说各话，而**试算平衡仍然报「平衡」**——
因为它只看科目余额，不知道台账上还挂着东西。这种「两处都对、合起来不对」是最难查的一类。

所以 `crates/findb/src/opening_check.rs` 的 `reconcile_begin` 六个校验里，头两条就是把
这两条路径的数摆在一起比。它们不是「再算一遍」，是两条路径的对撞。

#### 二、负债/权益要按余额方向取反

`BalanceRow` 里的金额是**带符号**的（借正贷负）。资产类「借正贷负」直接累加就对；
负债和权益的余额方向是贷，所以库里是负数，必须 `-amt` 才是「会计看到的那个数」。

第一版为了好读写成绝对值累加：

```rust
let signed = if amt >= Money::ZERO { amt } else { -amt };   // ← 错
```

后果：`4103 本年利润` 有借方余额（亏损 67,000）时权益算成 `87,000 + 67,000`，
资产只有 20,000——**差得离谱，可「资产 = 负债 + 权益」那条校验照样通过**，
因为等式两边都用的是同一个错数。

性质：**符号错不会让校验变红，只会让校验变成废话。** 所以必须有一条专门造亏损场景的
测试钉住它，而不是指望结构校验自己发现。

#### 三、编码校验为什么不能放在导入里

导入那一刻，档案表里可能还没有客户（工厂常是先导期初再补档案）。把「编码必须存在」
做成导入的前置校验，等于强迫用户按某个顺序操作，而且报错会淹没在「跳过 N 行」里。

放在**对账**里就没有顺序问题：任何时候看，都对当前档案表复核一遍，并点名是哪个编码
（`档案里找不到：C999(鑫盛电器)`）。同一条原则见 §4.79：校验要放在「能一次覆盖所有
写入路径」的地方，而不是每条路各写一遍。

#### 四、金额给字符串，别给数字

对账页的金额一律 `fmt_plain()` 成字符串再返回。理由不是技术性的：**千分位错位会让人
怀疑数字算错了**，而它只是显示问题。对账页的读者正在核对数字，任何一次「0 和 . 看串」
都会让整页失去可信度。

#### 五、模拟数据先跑三遍

`crates/finweb/examples/chk_opening_reconcile.rs` 用真实路径造账（建账 → 建档案 → 生成
模板 → 填数 → 导入 → 对账），跑三个场景：填得对、删掉科目期初、编码笔误。再故意留着
它作为可重跑的证据——`cargo run --release -p finweb --example chk_opening_reconcile`。

"用模拟数据跑一遍"的价值不是证明代码能跑，是**看到错误场景下人能读到什么**。三个场景
的输出直接决定了文案怎么写（哪一句在前、要不要带编码、要不要给修改建议）。

### 4.90 期初四张纸收不到的东西：模板少一列，账就永久错一位

v1.8.42 之前，③ 账户余额这张纸只有「科目编码 / 科目名称 / 余额」三列。剩下四类期初
没有任何地方可以填：

| 收不到的东西 | 后果（都不报错） |
|---|---|
| 存货的**数量** | 数量核算科目的期初数量为 0，第一次出库结存就成负数，数量金额式明细全错 |
| 银行科目的**账户** | 期初挂在一个不存在的账户上，银行日记账从零开始，对不上银行对账单 |
| **预收**（客户预交的钱） | ①② 只收正数，负数被「已跳过」，于是应收虚增、预收彻底消失 |
| **预付**（先付给供应商的钱） | 同上，应付虚增、预付消失 |

四个洞其实是同一个洞：**模板生成器、导入解析器、对账校验三处各写一套「这张纸有什么列」**，
加列的时候只改了一处。

### 一、加列要三处一起改，缺一处就等于没加

这次把 ③ 扩成 7 列：`科目编码 / 科目名称 / 余额 / 数量 / 客户·供应商编码 / 存货编码 / 银行账户`。
三处必须同步：

1. `crates/finweb/src/sheets.rs` 的 `opening_collection_template` —— 生成模板；
2. `crates/findb/src/opening_book.rs` 的 `parse_balances` —— 读回来；
3. `crates/findb/src/opening_check.rs` 的「数量核算科目都填了数量」—— 复核。

只做第 1 步的症状最恶心：表里有这一列、用户也填了，导进去不报错、就是没有。

### 二、「客户/供应商编码」一列两用，不能按资产/负债判

2203 预收账款是负债，但它挂的**是客户**；1123 预付账款是资产，挂的**却是供应商**。
按「资产挂客户、负债挂供应商」判，会把 C002 挂成供应商编码，然后对账报「档案里找不到」——
看起来像用户填错，其实是程序认错。

按科目家族判：`1122 / 2203` 走客户，其余走供应商。

### 三、找不到的编码要跳整行，`continue` 跳不出去

校验「这个编码在档案里吗」时写在了一个内层 `for` 里，`continue` 只跳出内层循环，
**行照样写进库**：于是既报了「找不到」，又留下一个孤儿期初。改用一个 `bad` 标志，
查完再决定跳过整行。

### 四、合计不能「边走边加」

写完最后一行（轧差补的 4103 本年利润）之后，合计必须**按最终这批判行重算**。
之前的写法是补完 4103 只调了一边，于是回显「借方 65,000 = 贷方 65,000」——
一个**两边都错、还能对上**的合计，而库里实际是 71,000。

而分借贷不能看科目首位：4103 以「4」开头，但它完全可能是借方（亏了）。按符号判才对。

### 五、表头行：标题、说明、表头三行要分得开

模板每张纸上面有标题行和一行说明文字。原来找表头只看「这一行里有没有『编码』『科目』
『项目』」，说明文字里随口提一句「科目」就被认成表头 —— 真表头变成数据第一行被跳过，
数据行改用兜底列号解析：编码、余额恰好还在原位，**多出来的列全丢，一声不响**。

现在要求表头行**至少两个非空格**，并且只认「编码 / 项目」这类真正的列名。

### 4.91 打印预览：调完看不见效果，就等于没得调

打印版式一直是「去系统设置改 → 回来点打印 → 发现不对 → 再回去」的循环。版式调不调得
对，只有**看到那张纸**的时候才知道；来回三五趟之后，人就放弃了，最后就那么歪着打。

现在预览页本身就是编辑器：方向、字号、页边距、编制单位/打印时间/页码/落款，
点一下、拖一下，**当场看到效果，并且自动存进本账套**。

### 一、为什么是「局部更新」而不是「整份覆盖」

预览页只认识七个字段，但它改动的是一个 `BookOptions` 里的 `PrintOptions`。如果照着
「读出来 → 改 → 整个写回」做，也就是发一份完整的设置过去：

- 预览页不认识的字段（凭证纸型 `voucher_paper`、账簿纸型 `ledger_paper`、单据纸型、
  套打偏移）会被 `serde(default)` 悄悄重置成默认值；
- 而且**一声不响** —— 用户要等到下次打凭证，才发现纸型从「241×140 连续纸」变回 A4。

所以接口收的是 `PrintPatch`（字段全是 `Option`，`None` = 这次没动它），
`PrintOptions::apply_patch` 只覆盖请求里带来的那几项。测试里专门先设成非默认纸型，
再拖一次字号，然后断言三个「这次没带」的字段一个都没动。

### 二、越界值要报错，不能悄悄夹回去

滑块本身给不出 20pt，但接口不能假设调用方守规矩。保存路径走的是和「系统设置」同一条
校验（`BookOptions::validate()`），所以超出 9–14 会直接 400 并把原值带出来：

```
打印字号应在 9–14 之间，当前是 20
```

反过来，「悄悄夹到 14 并存住」看着更稳，实际更糟：用户明明填了 20，打出来是 14，
而且没有任何提示 —— 只会让人以为设置没生效。

### 三、两次防抖，别让状态栏撒谎

拖动滑块会连续触发 `input` 事件。等手停下来 400ms 再发一次请求；另外用一个递增的
`seq` **丢掉过期响应**：否则快速拖几下，先发的慢请求后到，会把状态栏刷成
「保存失败」，而其实早就存好了 —— 用户会以为没生效，再拖一遍。

### 四、没有「系统设置」权限的人怎么办

版式是**账套级**的：改一次，所有人打印都变。所以保存要 `Perm::SysOption`。

没有这个权限的账号打开预览页时，控制条会换成另一套：只有「横向 / 纵向 / 字大字小」
三个临时按钮，并明写一句

> 你的账号没有「系统设置」权限：这里的调整只对本次打印生效，不会保存

宁可少给一个功能，也不要给一个「点了以为存了、其实没存」的按钮。

### 五、隐藏，而不是删掉

以前「关掉编制单位」是把那段 HTML 整个删掉。现在这几个块留在 DOM 里、带
`display:none` —— 因为预览页的勾选框要能**当场打开看看**，删了节点就只能刷新。
打印时同样不显示（`@media print` 里没有它们的位置），观感没变。

### 4.92 成本类科目：利润表与首页必须是同一个净利润

小工厂的房租、水电、煤气、外发加工费，最常见的记法是直接借 `510105 厂租房租`，
月末一次「结转损益」到本年利润——这些支出**从不经过 6401 主营业务成本**。

于是「营业成本只取 6401/6402」的利润表会说这个月赚 100,000，而首页（口径含未结转
的成本类科目）说赚 85,000。同一套账、同一个月、两个净利润，谁也答不上来哪个对。

**改法：营业成本 = 6401 + 6402 + 5001 + 5101 + 5201 的净发生额**（借 − 贷），
而不是余额。用净发生额的好处是三种记法都对得上：

| 记法 | 5101 净发生额 | 6401 | 利润表成本 | 说明 |
|------|---------------|------|-----------|------|
| 只记 5101，没结转 | 15,000 | 0 | 15,000 | 成本当期进利润 |
| 做过「结转损益」 | 15,000（结转凭证被 `with_exclude_carry` 剔除） | 0 | 15,000 | 结转前后不跳变 |
| 手工 5101 → 5001 | 0 | 0 | 0（但 5001 净发生 15,000 计入营业成本）| 成本转到生产成本，仍在当期 |
| 完整链 5101→5001→1405→6401 | 0 | 15,000 | 15,000 | 每一环净发生额相抵，只算一次 |

**为什么不是「取余额」**：余额在完整链里会先在 5001 堆着、再进 1405（存货），
那时成本确实还没实现，取余额会把存货成本提前扣成费用。

**为什么不给 5001 单独开一行「在产品」**：小工厂不做在产品盘存，多一行就要多填一张
表；净发生额口径对他们就是对的。真要做存货成本核算的厂，走完整链时这张表也自动
正确（上表最后一行）。

守卫在 `crates/findb/tests/income_vs_dashboard.rs`：四条测试各守一种记法，断言
「利润表净利润 == 首页净利润 == 85,000」。变异 `㉗ 营业成本退回只算 6401/6402`
必须被拦下——它是这一版唯一能证明修复有效的证据。

### 4.93 现金流量表：没人标注时，靠对方科目把表填出来

现金流量表是直接法：一笔现金收支归到哪个项目（销售商品收到的现金 / 购买商品接受的
劳务支付的现金 / 支付的各项税费……），本该由录凭证的人标。但小厂没有这个人——老板娘
能照着教程把借贷写对，不会记得再给「100201 借方」点一个现金流量项目。

结果是：报表**勾稽得上**（净增加额 = 期末 − 期初货币资金），内容却是一片空白，全部落在
「未归集」里。老板看到的是一张等于没用的表，而且看不出是「没发生」还是「没标」。

#### 三级归集顺序

1. **凭证上标了就听凭证的**。人工标注永远优先，规则不许覆盖。
2. **按对方科目推断**（`fincore::report::cashflow_rules`）。
   「借 100201 / 贷 600102」里的 `600102` 就是对方科目，它天然说明了这笔钱是什么性质。
3. **推不出来就留在未归集**，并在界面上说清有哪几笔、多少钱。

#### 只在能确定时猜

一张凭证的对方科目指向**两个不同**的现金流量项目时，不猜：

```
借 100201  50,000          ← 收了一笔钱
贷 600102  30,000          ← 像收货款（0101）
贷 160101  20,000          ← 又像卖设备（0203）
```

这种情况记进 `ambiguous` 计数，金额留在未归集里，界面上写「1 笔对方科目指向不同项目、
未归集」。**猜错的现金流量表比空表更糟**——空表用户会去补标注，错表用户会拿去用。

#### 一个必要的例外：税额是伴生行

最常见的凭证形态是收入带销项税：

```
借 100201  113,000
贷 600102  100,000
贷 22210102  13,000     ← 销项税额
```

如果按「对方科目有两个、分不清」处理，**每一张带税的凭证都会变成未归集**，规则等于白做。
所以：对方科目里同时存在 `2221×` 和其它科目时，`2221×` 不参与投票——它是主业务的伴生行，
跟着主业务走。（`2221` 单独出现时仍然管用：直接交税就是「借 2221 / 贷 银行」，
唯一对方科目 → 0106 支付的各项税费。）

#### 内部划转不是现金流量

提现（借 1001 库存现金 / 贷 100201 银行）的对方科目也是货币资金。这类凭证要**整行跳过**，
既不能归集也不能算「未归集」——以前它会让未归集金额凭空多出两笔正负相抵的数。

#### 方向决定项目

同一个科目，收和付可能归到不同项目：

| 对方科目 | 现金流入 | 现金流出 |
|---------|---------|---------|
| 2221 应交税费 | 0102 收到的税费返还 | 0106 支付的各项税费 |
| 1601 固定资产 | 0203 处置长期资产收回 | 0204 购建长期资产支付 |
| 2001 短期借款 | 0302 取得借款 | 0303 偿还债务 |

规则用**最长前缀匹配**，所以「660301 利息支出」能比「6603 财务费用」更具体地归到筹资活动
（0304 偿付利息），不用为了一个特例改结构。

#### 三端同一句话

归集情况的措辞收在 `CashFlowStatement::assignment_note()` 一处，桌面端、网页、Excel 导出
都用它。这是 v1.8.27「打印版式」的教训：同一件事写在三个地方，迟早会分叉。

#### 守它的测试

- `fincore` 的 9 条规则测试：含「规则里写的项目编码必须真的存在」——手打错一位（`0101`
  写成 `0110`）的后果是整类现金收支静默落到未归集，报表上既没有金额也没有报错。
- `findb` 的 8 条端到端：带税销售 / 带税采购 / 交税 / 利息支出 / 提现 / 冲突对方科目 /
  人工标注优先 / 整月勾稽。
- 5 条变异：规则表静默不生效、未归集不计入净增加额、税额伴生行也投票、提现被当成未归集、
  人工标注被规则覆盖。

### 4.94 月结向导：清单化比错误串值钱

`periods::precheck` 的输出是一串错误文字。它回答的是「为什么不能结账」，但用户真正要的是
「我现在该做什么」——这两件事不是同一个问题。

#### 形状决定可用性

错误串：

```
本期还有 3 张凭证未记账
有 4 个损益类科目尚未结转（如 600101 主营业务收入…）
```

清单：

| # | 步骤 | 状态 | 现状 |
|---|------|------|------|
| 2 | 凭证全部记账 | ✖ 未完成 | 还有 3 张未记账（草稿 1 / 已审核 2）<br>去「凭证」页全选后点「记账」 |
| 4 | 损益已结转 | ✖ 未完成 | 还没结转：600101 主营业务收入<br>点「结转损益」自动生成凭证 |

差别在于**「下一步点哪里」被写进了数据里**，而不是靠人从错误文字里翻译。所以
`CloseStep` 有 `code`（前端据此决定跳哪页）、`detail`（现状带数字）、`hint`（怎么做）。

#### `blocking` 是分级，不是遗漏

- **阻断**：做完才能结账，而且做完确实更对（未记账、未结转、试算不平、跳月）
- **提醒**：真实发生了，但拦住它只会催生绕路（现金余额为负）

现金为负几乎一定是记错方向。把它做成阻断项，用户的标准动作会是「先反结账、改一下、
再结账」——校验被绕开，还多了一次敏感操作日志。所以它是 `blocking: false` 的黄色 ⚠。

#### 一份判定，两个出口

`periods::precheck` 与 `month_close::report` 必须同口径，否则出现「向导全绿，点结账报错」。
钉住它的测试是 `blockers_matches_precheck`：

```rust
assert_eq!(mc.can_close(), periods::precheck(&db, p, true).unwrap().is_empty());
```

这类「两个入口同一件事」的地方，测试要断言**两者的结论相等**，而不是各自写一份期望值——
后者在口径漂移时两边一起错，测试照绿。

#### 成本类为什么要单独一步

5101 制造费用既不在 `is_profit_loss()` 里（利润表用 `expense()` 直接点名 6401/6402），
也不一定进资产负债表存货项（只有在产品余额非零时）。于是它能在账上永久挂着：
利润表看得见这笔支出，余额表看不出它「没被结转」。v1.8.45 修的是取数口径，
v1.8.47 把「有没有转出去」变成清单上可见的一步。

#### 守它的测试

- `empty_first_period_is_ready_to_close`：空账套第一期可结，且**步骤清单与顺序固定**
  （少一步就红——漏掉的那一步正是没人会注意的那一步）
- `blockers_matches_precheck`：与 precheck 结论相等
- `uncarried_profit_blocks_closing`：收入没结转必须拦住
- `closed_period_cannot_be_closed_again`：已结账期间只报状态，不再说「可以结账」
- 3 条变异：向导把未记账当完成 / 未记账不再阻止结账 / 已结账期间仍说可以结

### 4.95 账期：一个填了两年却没人读的字段

`prop::PAY_DAYS`（账期天数）从一客一税点那一版就在客商档案里，桌面端和网页端都能填。
但全仓 `grep pay_days` 除常量定义外零命中 —— **填什么都一样**。

它值钱的地方很具体：账龄 54 天是不是要催，取决于约定了多少天。没有账期的账龄只会
说「这笔挂很久了」，说了等于没说；有了账期才能说「逾期 24 天，该打电话了」。

#### 「账龄」和「逾期」是两个数

| 概念 | 算法 | 能用来说什么 |
|------|------|------------|
| 账龄 | `as_of − 单据日期` | 这笔挂了多久 |
| 逾期 | `账龄 − 账期`（小于 0 记 0） | 超过约定多少天 |

界面必须同时给，不能只给一个：只给账龄，账期 90 天的客户才挂 60 天就被标红；
只给逾期，看不出这笔到底放了多久。

#### 逾期按「最老一笔未核销单据」算

一个客户有十笔未核销单据时，逐笔算逾期会得到十个数字，而催款只需要一个：**最保守的
那个**。所以用 `AgingLine.max_days`（最老单据天数）减账期 —— 正好就是「最早那笔超期
了多少天」。十笔里最老的那笔最急，这个选择不需要解释。

#### 不知道就写「未设账期」，不能写 0

`pay_days: Option<i64>` 而不是 `i64`：

- `None` → 界面写「未设账期」，Excel 那一格**留空**
- `Some(0)` → 才是真的「现款现货，当天到期」

把两者混成一个 0，Excel 里导出的一列会让「没约定」看起来像「立即到期」，
而真实情况可能是一个二十年的老客户从来没谈过账期。

#### 一次全读，不在循环里查档案

账龄一屏几十个客户，逐行 `aux_get` 就是几十次查询。`pay_days_map(db, kind)` 一次把
该维度的账期全读进 `HashMap`，循环里只做 `get`。

顺手定了一条容错：账期解析不出来（用户填了「月结30天」这种）就**当成没填**，
不让整张账龄报错 —— 账期是辅助信息，不该有能力把主表打挂。

#### 守它的测试

- `aging_uses_pay_days_to_compute_overdue`：9/1 的单、账期 30 天、10/25 看 → 账龄 54、逾期 24
- `overdue_is_zero_without_pay_days_or_before_due`：没填账期 → `None`/0；账期 60 天、挂 19 天 → 逾期 0
- 变异 2 条：账期不参与逾期计算 / 账龄读不到客商档案的账期

### 4.96 账套参数：导得出、导得回，且「恢复默认」不能把账一起改了

参数页有十六个字段（编码级长、启用期间、企业名称、税号、本位币、五个开关、六个业务
默认科目、预算控制、单据前缀、打印版式、凭证字）。手记是不可能的——换台机器、或者
误改一处想回去，都得有个「把这一套拿走 / 拿回来 / 回默认」的出路。

#### 导出必须是整个对象，不能挑字段

少导出一个字段，导入后它就静默回到默认值，而症状是「换了机器某个设置不一样」——
这种问题极难自查，因为没有任何报错。所以导出的就是 `BookOptions` 本身，
`serde` 序列化什么就是什么，没有一层「只导重要的」。

#### 导入时，结构项不同就整体拒绝，一个字段都不改

`code_scheme`（科目编码级长）和 `start_period`（启用期间）**与已有的科目树和期初
数据绑在一起**：改级长，存量科目就对不上上下级；改启用期间，期初就从另一期开始算。
所以 `adopt_config` 先比这两项，不同就 `Err`，**一个字段都不改**。

为什么不做成「跳过这两项、其余照搬」：配置文件里明明写着 4-2-2-2-2，导入后账套还是
4-2-2-2，用户只会以为导入没生效，然后开始怀疑别的设置也没进去。**报错比静默降级好**。

#### 「恢复默认」只清偏好，不清身份

`reset_preferences()` 只动四项：生产模块开关、预算控制、单据前缀、打印版式。

| 不动 | 为什么 |
|------|--------|
| 企业名称 / 税号 | 这是这个账套的身份，不是偏好 |
| 编码级长 | 改了存量科目树对不上级 |
| 启用期间 | 改了期初从另一期开始 |
| 业务默认科目 | 改了自动生成的凭证记到别处，且新科目可能不存在 |
| 审核 / 出纳开关 | 属内控决定，不该被一个「恢复默认」按钮默默关掉 |

用户点的是「恢复默认」，不是「重开一套账」。

#### 三端同一套逻辑

`reset_preferences` / `adopt_config` 写在 `fincore::account::BookOptions` 上，
桌面端和网页端都只调它。网页三个入口：`GET /api/options/export`、
`POST /api/options/import`、`POST /api/options/reset`；桌面端三个按钮走 `rfd` 文件对话框。
**校验和语义在一处，两端只是外壳**——这是 v1.8.27 之后一直的口径。

#### 守它的测试

- `reset_preferences_keeps_what_is_bound_to_existing_data`：恢复后企业名称/级长/期间/默认科目/审核开关全在，且 `validate()` 仍通过
- `adopt_config_moves_preferences_but_refuses_structural_mismatch`：结构相同整套照搬；级长或期间不同 → 报错且**一个字段都没变**
- `crates/finweb/tests/options_config.rs` 3 条：导出的 JSON 覆盖全部字段（含 `print` 的十项）、导入生效且结构不符被拒、恢复默认不动身份字段
- 变异 3 条：恢复默认顺手清企业名称 / 导入结构不同也不拒绝 / 恢复默认不清预算控制

### 4.97 三件「以为缺、其实要分开看」的事

#### 一、催款单：Excel 有明细，但没有一封「函」

催款单早就能导出 Excel（汇总 + 明细两张表），但导出的是一张表：客户收到不知道这是
一封催款函。这一版给它渲染成一页 A4 文书 —— 抬头、`致：XX 公司`、欠款总额一句话、
逐单明细（含**每单逾期几天**）、合计、落款。

为什么逐单算逾期而不是只给一个总数：客户手里有十几张单，说「你欠我 5 万、最早那笔
超期 24 天」，不如说「XSQ-8801 超期 24 天、XSQ-8802 超期 3 天」——后者能直接对上账。

预收/预付**不进合计**，但在函末单独说明一句：

> 另：账面记有贵方预交款 3,000.00，已单独列示，未计入上面的合计。

混进合计，客户会以为我们记错了账。这也是 `dunning_create` 早就分 `owed/advance`
两笔数的原因，函只是把它如实写出来。

版式仍走账套的 `PrintOptions`：能打印的东西就该认账套里的纸张设置（v1.8.27 口径）。

#### 二、现金流量表：只有本期，看不出一件事是好是坏

「经营现金流 5 万」本身没有信息量——比上期多了还是少了才有。现在现金流量表多一张
**「本期与上期对比」**：项目 / 本期 / 上期 / 变动，Excel 第二张纸、网页表底一行摘要、
JSON 里 `prev` 与 `delta` 两个块。

三条口径：

1. **上期取「等长的上一段」**，不是「上月」。本期 3 个月就取上一个 3 个月，否则季度
   报表里会出现「3 个月 vs 1 个月」的假对比。
2. **上期有、本期没有的项目不能消失**，要单列并标「（上期有）」。按本期循环一遍就
   收工，「上月买了设备、这月没买」这件最该看见的事会凭空不见，而两张表看起来都挺对。
3. 对比只比**净额**。流入/流出两列加进对比表会把 A4 横向挤爆，而决策看的就是净额。

#### 三、期初收集表：低频科目其实一直在，只是没人验证过

我一度以为模板只列了常用科目（在建工程、预付账款没进去）。查代码发现模板按
1xxx / 2xxx **末级科目全量**生成，只是排除了由 ①② 两张纸自动生成的 1122/2202。

也就是说「缺」是我的错觉。既然如此，这一版的产出不是补科目，而是**补一条测试**
把这件事钉住：`opening_template_lists_low_frequency_accounts_too` 断言 1123 预付
账款、1604 在建工程、2203 预收账款、2501 长期借款都在表里，且 ③ 账户余额里
**没有** 1122/2202（那两个由客户/供应商两张纸生成，再填一遍会双计）。

「以为缺」和「真的缺」之间隔着一行断言。以后谁想「让表短一点」加白名单，
这条测试会当场报红。

### 4.98 一张纸、一个窗口、一行断言：v1.8.51 的三处收口

#### 一、打印页不能是「唯一一份只有本期的表」

v1.8.50 给现金流量表加了「本期 vs 上期」，落地在 Excel 第二张纸、网页表底一行、
JSON 的 `prev`/`delta` 三处 —— 唯独打印页没有。而**打印页恰是最需要它的地方**：
拿纸去开会的人手里会是唯一一份「只有本期」的表，讨论时没人知道这个 5 万算好算坏。

所以 `cash_flow_html` 多一个 `prev: Option<&CashFlowStatement>`，表头由 4 列变 6 列
（流入/流出/净额/上期净额/变动）。三条与 Excel 对齐的口径：

1. 上期某项目按 **code** 匹配，不按名字 —— 名字会改，code 不会。
2. 上期有、本期没有的项目**单列并标「（上期有）」**，不能因为本期循环里没有它就消失。
3. 三段活动的小计、净增加额都要带「上期 / 变动」两个数，只给明细不给小计等于没算。

#### 二、上期窗口的 off-by-months：这是测试抓出来的

`prior_range(from, to)` 是「与本期等长的上一段期间」。原来的写法：

```rust
let mut prev_to = from.prev();
for _ in 1..months { prev_to = prev_to.prev(); }   // ← 错在这里
let mut prev_from = prev_to;
for _ in 1..months { prev_from = prev_from.prev(); }
```

`prev_to` 和 `prev_from` **各自**往前推了 `months - 1` 个月，于是 3 个月的对比实际取的是
「再往前两个月的那 3 个月」。1 个月时循环不跑，所以单月对比一直是对的 —— 只有季度、
半年、年度报表才错，而且错的是一段**看起来也很像**的时间。

修法是只推起点：

```rust
let prev_to = from.prev();
let mut prev_from = prev_to;
for _ in 1..months { prev_from = prev_from.prev(); }
```

补了三条纯函数测试（单月 / 季度 / 跨年），并把这条变异加进变异清单 —— 这类错只有
「把窗口算出来的两端打印出来对一遍」才抓得到，翻代码看不出来。

#### 三、桌面端补上催款函

桌面版一直**没有催款单页**（`SettleTab` 只有手工 / 自动 / 互冲 / 账龄 / 对账单），
要发催款函只能开网页。这一版加「催款函」标签页：填往来编码 → 生成 → 打印函 /
标记已发出。

信的内容与网页端**同一份实现**：html 生成器从 `finweb::report_html` 搬到了
`findb::printform::dunning_letter_html`。理由很直白 —— 两端各写一份，改一处忘另一处，
最后同一张催款函在两个端长得不一样，客户手上会有两个版本。

桌面端打印走现成的 `export::print_html_content`（写临时文件 + 系统浏览器打开），与
凭证套打、账簿套打同一条路。

### 4.99 桌面端补齐三处：发票、期初收集表、现金流对比

这一版做的是「网页有、桌面没有」的三件事。它们的共同点是**不是新功能，是同一件事的
两个入口**——而两个入口最容易长成两套逻辑。

#### 一、发票管理：进项认证决定能不能抵扣

一般纳税人能不能抵进项，看的是「有没有专票 + 认没认证」。`crates/findb/src/taxdecl.rs`
里只有 `status == "verified"` 的进项才计入可抵扣。而在这版之前，登记与认证**只能在
网页端做**。

后果不是「少个按钮」：桌面版是记账的主入口，记完账没有地方登记发票，于是「记了账但
没登记发票」这件事谁都不会发现 —— 直到申报时进项凭空少一截，再去翻三个月的凭证。

页面给三张卡：待认证进项税额（还不能抵）、已认证进项税额（可抵）、销项税额（应缴）。
**这三个数必须分开**，加起来没有意义。

税额拆分单独抽成纯函数 `split_amount_tax`，因为它是「13% 的 10300 到底拆成多少」：
不含税 = 合计 ÷ (1 + 税率)，税额 = 合计 − 不含税。**先算不含税再相减**，不要用
「合计 × 税率 ÷ (1+税率)」各算一遍——两条路径在分位上会差 1 分，而发票上
「不含税 + 税额」必须刚好等于合计。

新增 `invoices::tax_summary`：原来的 `summary` 把待认证与已认证加在一起，报税时看到
那个数是错的。

#### 二、期初收集表：数据搬到 `findb`，两端只负责渲染

四张纸（客户应收 / 供应商应付 / 账户余额 / 基本资料）原来整个构造逻辑在
`crates/finweb/src/sheets.rs` 里，桌面端用不了。

搬法不是复制一份，而是**把数据搬到 `findb::opening_book::collection_template`**，
返回与 xlsx 无关的 `CollectionSheet { name, title, subtitle, headers, rows, cols }`；
网页端与桌面端各自只做「把它摊成自己的 Sheet 类型」这一件事。

为什么非搬不可：这张表**同时是导出和导入的契约**。用户在桌面下载、在网页导入，列头
必须一模一样；两端各写一遍，第一列一改就有一边悄悄错位，而 xlsx 不会报错。

三条测试把契约钉在 `findb` 侧：

- `collection_template_has_the_four_sheets_and_expected_headers` —— 表名与列头逐字比对
- `balances_sheet_excludes_generated_ar_and_ap_but_keeps_the_rest` —— ③ 里**不能**有
  1122/2202（由 ①② 生成，再填一遍就是双计，而双计之后借贷两边各多一份、看起来还是平的）
- `customer_and_supplier_rows_are_prefilled` —— 有档案就预填行，没档案只有表头，两种都能导

桌面上的三个按钮就是流程本身：**期初收集表（下载）→ 导入期初收集表（先预检、不落库）
→ 确认导入 → 导入后对账**。预检结果里借贷不平会红字提示「直接导入会被拒绝」，
不会让人填完两百行再被拒一次。

#### 三、现金流打印带上期对比

`crates/finui/src/views/reports.rs` 的 `cash_flow_sheet(cf)` 只有本期四列。现在导出走
`cash_flow_sheet_with_prev(cur, prev, cur_label, prev_label)`：

- 上期取 `findb::reports::prior_range` 算出的**等长上一段**（季度报表不能拿 3 个月比 1 个月）
- **上期有、本期没有的项目要单列并标「（上期有）」**。按本期循环一遍就收工，「上月买了
  设备、这月没买」这件最该看见的事会被吞掉，而两张表看起来都挺对
- 只比净额：流入/流出再乘两期，A4 横向放不下

取不到上期数据时自动退回原来的四列，不报错。

### 4.98 设备绑定：能做的不是「验证客户端」，而是「不给它扩容的机会」

`SECURITY_TODO` 的 M-4 记了两年：「`device_id` 由客户端上报，可伪造换绑」。

先说清为什么没法真验：`device_id` 是浏览器/客户端自己生成的一串字符串，服务端没有任何
办法证明「这台机器确实是上次那台机器」——没有可信硬件标识、没有客户端证书，加 TLS 也
只证明通道安全，不证明设备身份。所以「校验 device_id 真实性」这条路是走不通的。

能做的只有改**政策**，让伪造换不来东西：

| 版本 | 政策 | 结果 |
|------|------|------|
| 最初 | 一人一机，第二台直接拒 | 用户「手机+电脑」直接被卡死，太硬 |
| 中间 | 最多自动绑 2 台 | **这是错的**：拿到口令的人可以悄悄绑一台自己的设备长期用，而名单里那行看起来跟用户自己的手机没区别 |
| v1.8.53 | 首次登录自动登记，此后新设备一律拒绝 | 换设备走管理员「重置设备绑定」，不给扩张留后门 |

三条实现要点：

1. **「首次」的判定是名单为空**，不是「这台没登记过」。否则攻击者第一个登进来就占住了
   首绑名额 —— 那是把门交给先到的人。
2. **比对用指纹** `sha256(盐 | 账号 | device_id)`，盐每库随机生成存 `realm_option`。
   它挡不住什么要说清楚：盐就在同一个库里，能被读库的人一起读走；它的作用是让
   「名单里抄一行出去」不再是一张通行证，且换个部署（换盐）同一设备指纹也对不上。
   真正起作用的是第 1 条的「不再扩容」。
3. **存量行必须回填指纹**，否则升级那一刻全员匹配不上 → 症状是「登录成功但每个请求都
   说设备未授权」。同理 `device_allowed` 对指纹为空的行保留 `device_id` 兜底比对，
   兜底只为「升级瞬间的请求」存在。

拒绝时的文案也要能落地：「这台设备还没有被授权。该账号已在 1 台设备上绑定过；换设备
需要管理员在「账号」页点「重置设备绑定」，之后用新设备重新登录。」——只说「登录失败」
等于让用户去猜是不是口令错了。

守它的三条变异：把 `if count > 0` 改成 `if false`（政策回潮）、把「已登记就只刷新」
改成每次都插新行、把存量回填的 `WHERE device_hash = ''` 改成 `WHERE 1 = 0`。三条都是
「不报错、只是悄悄变松」的典型。

### 4.99 数据范围：漏一个出口，就是一套"看着都对"的两份数

权限分两层：**角色**决定能干什么，**数据范围**（`DataScope`）决定能看哪些数据。
这一版把数据范围逐个出口对了一遍，并把两个漏的补上。

#### 一、为什么漏的总是"不是报表页"的地方

报表页有权限检查是本能。漏的是那些**不是报表、却显示同一批数字**的地方：

| 出口 | 改前 | 现在 |
|------|------|------|
| 试算平衡（JSON / CSV / PDF / 打印 / Excel） | 带范围 | 带范围 |
| 三大报表（打印 / Excel / JSON） | 带范围 | 带范围 |
| 明细账 / 总账 / 日记账 | 带范围（`ledger_query_from` 统一收口） | 带范围 |
| 凭证列表 / 凭证打印 / Ctrl+K 搜索 | 带范围（`VoucherQuery::with_data_scope` + `can_see_voucher`） | 带范围 |
| 工作台 | 带范围 | 带范围 |
| **首页**（经营结果 / 钱在哪 / 本年累计） | **不带**（`financial_totals(.., None)`） | 带范围 |
| **往来**（账龄 / 未核销清单） | **不带**（只查权限，不查科目） | 范围外一律 **403** |
| 存货账龄 | 不适用（存货不是科目维度） | 不适用 |

漏的那两个的症状是一致的：**首页看到全公司、点进利润表只剩自己的**。两边
都"看起来对"，数字不一样但没有一处报错 —— 这类 bug 靠人眼对不出来，只能靠
"同一批数必须走同一个验权口"这条纪律。

#### 二、范围外加 403，不能返回空清单

账龄、未核销清单这类页面，空清单是有明确含义的：「这户真的没欠款」。如果越权时
也返回空，会计会拿着这个结论去催款或者去对账 —— 更糟的是他会以为账套数据丢了。

所以：

```
403 无权查看该科目
```

空与无权限必须分开，因为**下一步动作完全不同**（一个去催款，一个去要权限）。

#### 三、怎么知道还漏没漏：从"科目"倒着找

不看权限代码，看**取数**。做法是：

1. 在 `crates/finweb/src/handlers.rs` 里把每一处取金额的调用列出来 ——
   `financial_totals` / `financial_ytd` / `financial_analysis` / `money_position` /
   `statement_table` / `cash_flow_statement` / `equity_statement` / `trial_balance` /
   `settle::aging` / `open_entries` / `invoices::tax_summary`；
2. 逐个看它拿到的 `scope` 是 `Some(&user.user)` 还是 `None`；
3. `None` 的要么接上，要么在表里写明"为什么不适用"（存货账龄就属于后者）。

这个方法比"翻权限中间件"可靠：中间件只管"能不能进这个页面"，而**页面里查了几批数、
每批数带不带范围**，只有取数点自己知道。

#### 四、守它的方式：一条从"违规侧"写的测试

`crates/finweb/tests/scope_dashboard.rs` 两条，都从"越权者"视角写：

- 范围只给 `600101`（主营业务收入）的会计，首页「手头现金」不能是 100.00
  （那 100 是范围外的 1001）；
- 同一会计查 `112201` 的账龄与未核销 → **403** 且错误信息说"无权查看该科目"；
- 反向一条：查自己范围内的科目仍然 200 —— 加闸门最容易顺手把正常路径也堵掉。

变异验证两条都拦得住：把首页的 `scope` 改回 `None`、把账龄的科目判断改成
`if false`，测试都会红。

### 4.100 数据范围的两条延伸：部门与写侧

#### 一、同一个判断抄了两遍，就一定会漏一遍

工资的四个出口共用 `scope_payroll`（部门范围 ∧ 仅本人经手）；报销却是 `list_claims`
与 `export_claims` 各写一遍，**两份都只写了 `own_doc_only`，没有部门**。设了「生产部
会计只看生产部」之后，报销列表与导出照样带出别的部门 —— 不报错，就是多了。

收成两个函数后，口径只存在一处：

| 函数 | 用途 |
|------|------|
| `scope_claims(user, rows)` | 读：列表 / 导出 |
| `claim_visible(user, c)` | 写：改 / 删 / 审批流转 / 生成凭证 / 新建时的部门校验 |

判断"这处该不该用统一函数"的标准很简单：**同一句话在第二个地方出现时**。第一次可以
直接写，第二次就该提函数 —— 否则第三次必然有一个地方忘了改。

#### 二、"看不到"与"改不了"是两件事

`own_voucher_only` 让会计看不到别人的凭证。但**拿着 id 直接调写接口**是另一条路：

```
POST /api/vouchers/{id}/post     ← 记账
POST /api/vouchers/{id}/void     ← 作废
POST /api/vouchers/{id}/audit    ← 审核
```

审计下来 9 个写接口（含 `save_voucher` 与 `batch-post`）全部过 `can_see_voucher`，
是守住的。但"守住了"和"有测试证明守住了"是两件事 —— 这一版补的是后者。

写侧越权比读侧越权隐蔽得多：**列表里看不到，所以没人会发现**。所以凡是"按 id 操作
单张单据"的接口，进门第一件事都该是"我能不能看见它"，而不是"它当前状态允许什么操作"。

#### 三、先验权限再验参数

`claim_voucher` 原来先判断"请填写支付科目"再验权限。对范围外的单子，服务端连"你的
参数对不对"都不该告诉调用方 —— 那是个可以用来探测单据存在性、字段结构的信息面。
顺序统一为：**取单据 → 验权限 → 验参数 → 干活**。

### 4.101 低危项复查：先量，再决定改不改

`SECURITY_TODO` 的 L-3~L-14 原文只留下"边界处理、死代码清理、格式瑕疵等"这一句
（详见 `docs/archive/FINAL_SECURITY_REPORT.md`），逐条清单已不可考。所以这一轮不是
"照着清单改"，而是**重新量一遍**，用工具说话：

| 量什么 | 怎么量 | 结果 |
|--------|--------|------|
| 悬挂 TODO / FIXME | `grep -rn "TODO\|FIXME\|XXX\|HACK" crates/` 排除测试 | **0 条真实待办**（9 处命中全是文档里引用 `SECURITY_TODO` 的说明文字） |
| SQL 注入面 | 找 `format!("SELECT/INSERT/UPDATE/DELETE ...")` 里拼变量 | 68 处全部只拼**占位符**（`?,?,?`），值一律走 `params![]` —— 无 |
| 非测试 `unwrap/expect` | 按文件切到 `#[cfg(test)]` 之前再数 | **173 处**（finweb 68 / findb 各文件零散 / finui 21 / fincore 25），其中 `realm.rs` 一家占 46 |
| 截断型转换 | `clippy::cast_possible_truncation` | 166 处，**没有一处在金额/数量/单价路径上**（都是计数、下标、长度） |
| pedantic 噪音 | `clippy -- -W clippy::pedantic` | 568 条，集中在 `needless_pass_by_value` / `too_many_lines` / `doc_markdown` 之类，改它没有收益 |

结论：**只有一处值得改** —— `realm.rs` 的锁。

#### 一处真问题：一次 panic 让登录永久不可用

`RealmDb` 的 40 处写法是 `self.inner.lock().unwrap()`。`Mutex` 有"中毒"语义：
任一处**持锁时 panic**，锁就永久标记为中毒，此后**每一次** `.lock().unwrap()` 都 panic。

在这个项目里，这意味着：登录、改密、开号、设备绑定登记 —— 全部失效，只能重启进程。
一次局部 bug 变成永久不可用。

改成从毒化里取回内值：

```rust
fn conn(&self) -> MutexGuard<'_, Connection> {
    self.inner.lock().unwrap_or_else(|e| e.into_inner())
}
```

**为什么这是安全的**：这把锁保护的是一条 SQLite 连接，不是"必须完全一致的内存不变量"。
数据一致性由 SQLite 自己的事务保证，毒化后继续用这条连接不会读到半截事务。反过来，
如果谁把锁保护的是一段"三步写完才算对"的内存状态，那就该保留 `unwrap()` 让程序崩，
因为崩掉比带着半截状态跑安全。

#### 不改的那几类，理由

- **`scm.rs` 的 `serde_json::to_value(枚举)?.as_str().unwrap()`（10 处）**：枚举序列化
  成字符串必然成功，改成 `unwrap_or_default()` 只会把 panic 换成**静默写空串** —— 更糟。
  真要改是加个 `as_str_or_err()` 返回 `DbResult`，属于重构不属修 bug。
- **166 处截断转换**：没有一个碰金额。为了消 lint 引入 `try_into()` 会让每处多两行
  错误处理，收益为负。
- **568 条 pedantic**：`too_many_lines`（17）指的是 `handlers.rs` 里那些大函数——拆它
  是另一件正经事（按域拆 handler 文件），不该混进"低危项"里偷偷做。

#### 守它

`realm::tests::a_poisoned_lock_does_not_kill_login`：故意在持锁时 panic 把锁打成中毒，
然后断言 `get_user` / `authenticate` / `create_user` 全部照常工作。没有这条测试，
"改回 `unwrap()`"是可以悄悄发生的 —— 变异验证确认它会被拦下。

### 4.102 拆 `handlers.rs`：18119 行是怎么来的，又是怎么拆的

#### 一、它为什么会长到一万八

`crates/finweb/src/handlers.rs` 原 **18119 行 / 525 个顶层项 / 374 条路由**，
`clippy::too_many_lines` 报了 17 处。它不是一天长成的：每个版本的「加个接口」都在
文件末尾追加，从没人为「放哪儿」做决定。后果不是丑，是**改错**：

- 想改凭证相关的东西，得先在一万八千里 `grep`，然后一路滚到不知哪一段；
- code review 看不到边界 —— 一个 PR 里「往来」和「工资」的改动混在同一坨 diff 里；
- 想找「哪些接口真的调了 `settle::aging`」，只能全文件搜。

#### 二、拆的判据：只搬位置，不改一行逻辑

这是硬约束，也是验收标准：

| 判据 | 拆前 | 拆后 |
|------|------|------|
| 全量测试 | 1081 | **1081**（套件数 36，逐条数不变） |
| `finweb` lib 警告 | 251 | **251** |
| 变异套件 | 112 条全拦下 | 112 条全拦下（路径跟着搬） |

「拆完测试还是绿的」是最低要求；**条数一样**才说明没有测试在城市搬迁中被悄悄丢掉。

#### 三、拆成什么样

按**业务域**切（不是按「大文件切一半」）：

| 模块 | 行数 | 装什么 |
|------|------|--------|
| `handlers.rs` | 4707 | 路由表（654 行）+ 跨模块共用的 DTO/工具（123 个结构体、86 个函数） |
| `handlers/export.rs` | 1685 | 导出、导入、基础资料、模板 |
| `handlers/settle.rs` | 1346 | 往来核销、账龄、催款、未核销清单 |
| `handlers/reports.rs` | 1297 | 三大报表、科目余额表、打印、期间 |
| `handlers/inventory.rs` | 1293 | 存货、仓库、BOM、MRP/MPS、落地成本 |
| `handlers/funds.rs` | 1248 | 收付款单、银行、现金 |
| `handlers/books.rs` | 1191 | 账套、备份、参数、健康检查 |
| `handlers/sales.rs` | 1046 | 销售、发票、税务 |
| `handlers/prod.rs` | 1035 | 生产、工序、成本、审批 |
| `handlers/voucher.rs` | 955 | 凭证、明细账 |
| `handlers/procure.rs` | 715 | 采购 |
| `handlers/auth.rs` | 708 | 登录、会话、设备、角色 |
| `handlers/hr.rs` | 601 | 工资、报销 |
| `handlers/assets.rs` | 380 | 固定资产 |
| `handlers/platform.rs` | 292 | 平台用户、安全策略 |
| `handlers/misc.rs` | 69 | 附件 |

`handlers.rs` 剩下的 4707 行**不是残渣**：路由表必须在同一处（否则「这个 URL 谁处理」
要翻 16 个文件），123 个请求/响应结构体是各模块共用的词汇表。现在改一个业务域只开
一个文件。

#### 四、三个踩过的坑

1. **「搬走的函数」要显式开可见性**。原文件里 `async fn foo(...)` 是模块私有的，
   搬进子模块后父模块 `use self::x::*` 看不到它 —— 编译错误会指向**路由表**说
   `cannot find value foo`，看着像路由写错了。搬过去的定义统统要 `pub(super)`。
2. **父模块的导入对子模块不可见**。子模块写 `use super::*;` 只能看到父模块里
   `pub(crate) use` 的**重导出**，普通 `use serde_json::json;` 是私有的，搬过去的代码
   会报 `cannot find macro json`。所以 `handlers.rs` 头部的依赖必须先转成
   `pub(crate) use`。
3. **搬完要重跑「变异套件的目标是否还在」**。`tools/mutate-rust.js` 里每条变异都写着
   `file:` 与要替换的原文，搬文件后 `file` 会指向空 —— **变异脚本不会报错，它只会
   「测试没跑」然后算通过**。所以加了一条机械校验：`--list` 输出的每一条，其 `from`
   必须能在它声明的文件里找到，否则报红。这一版因此重写了 19 条变异的路径。

#### 五、没动的

`crates/finweb/tests/api.rs` 两万行**这一版没动**（下一版 §4.103 拆了，14 个域文件、仍是 194 条）。它的问题是另一个：文件大但**测试之间没有
耦合**，切分收益远小于改坏风险（每个测试都自带夹具），留到真有痛点再说。

### 4.103 一万行文件的第二课：把「词汇表」和「用例」也搬出去

v1.8.57 把 `handlers.rs` 从 18119 行拆到 4707 行，剩下的部分看着"已经不大"了。这一版
接着把里面两类东西搬走，两件都验证了一件事：**拆分不是一次动作，是一个持续的分类习惯**。

#### 一、请求/响应结构：谁用谁负责

移走 115 个类型：

| 去向 | 数量 | 判据 |
|------|------|------|
| `crates/finweb/src/dto.rs`（共享契约） | 8 | 被 ≥2 个域模块引用，或主模块/测试也用 |
| 各自的域文件（`handlers/hr.rs` 等） | 107 | 只被一个域引用 |
| 留在 `handlers.rs` | 12 | 只在主模块内部用 |

判据不是猜的：逐个类型数引用点（主文件其余部分、15 个域文件、`tests/`、`lib.rs`）。
「只被一个域引用」的结构体留在共享文件里，等于把**实现细节**挂在了公共词汇表上——
下次有人改它，会以为在改契约。

搬完 `handlers.rs` 4707 → **3426 行**，`dto.rs` 577 → 673 行。

#### 二、`tests/api.rs` 两万行：拆文件，但不拆测试二进制

这里有个 Rust 的硬约束值得记：**`tests/api.rs` 里的 `mod foo;` 会去 `tests/foo.rs` 找**
（crate 根文件的子模块放在**它所在目录**，不是同名子目录）。所以要把一个测试文件拆成多个
文件、又保留「一个测试二进制」，正确形状是：

```
tests/api/main.rs      ← 共享夹具（imports + 17 个 helper）
tests/api/auth.rs      ← mod auth;
tests/api/settle.rs
...
```

改成 `tests/api/` 目录（Cargo 自动发现 `tests/api/main.rs` 作为名为 `api` 的测试目标），
`main.rs` 里 `mod auth;` 就能找到同目录的 `auth.rs`。

拆法：按用例里出现的路由前缀归属（`/api/settle` → `settle.rs`），194 条用例、14 个域文件。
判据仍然只有一条——**测试条数必须还是 194**，多一条少一条都说明搬错了。

三个具体的坑：

1. **`mod common;` 的路径变了**。根文件从 `tests/api.rs` 变成 `tests/api/main.rs` 后，
   `tests/common/mod.rs` 要靠 `#[path = "../common/mod.rs"]` 指过去。
2. **`use common::*;` 不会被子模块看见**。子模块只写 `use super::*;`，而父模块里的
   `use`（非 `pub use`）不是重导出 —— 25 条用例会集体报 `cannot find function authed_get`。
   把共享 `use` 改成 `pub use` 即可。
3. **夹在用例之间的 helper 会被整段漏掉**。我第一版只把「文件开头到第一个 `#[tokio::test]`」
   当夹具区，于是 17 个定义在中间的 helper（`authed_delete`、`provision_plain_user`…）
   既不在头段、也不在任何用例块内，直接被丢掉。发现方式是编译错误一条条报「找不到函数」。
   **正确的自检是比对拆前拆后「顶层 fn 名字集合」**，而不是只数测试条数。

#### 三、又一处「假绿」：检查脚本自己的判据

`tools/check-ci.js` 靠「`crates/finweb/tests/api.rs` 存在」来定位仓库根。文件一搬，
15 条探针、两处夹具检查全部报「定位不到仓库根」。改成认两个路径，并把自检探针的
改坏点跟到新的 `isRepoRoot(c)` 上 —— 探针本身也是代码，它改坏的位置同样会过期。

### 4.104 部门口径的边界：明细收窄，汇总不收窄

部门数据范围下推 SQL 之后（v1.8.60），下一处对不上的地方是**账簿**：同一个部门会计，
凭证列表 192 张（看不到别的部门），科目余额表却是三个部门合计 238800（本部门真值
79600）。两个入口各说一套，谁也不敢拿它做数。模拟数据体检脚本 `qa_sim` 里这条挂了
两个版本才修。

#### 一、先想清楚「汇总能不能收窄」，再动手

第一版把 `depts` 加进了 `BalanceQuery::with_user_scope`，所有账簿与报表一起收窄。
跑测试立刻露馅：**试算不平衡**——借方 400、贷方 600。

原因不在代码，在账务事实：一张费用凭证，借方 `660201/生产部` 挂了部门，贷方 `1001
银行存款` 不挂。按部门收窄后，借方只剩本部门那段，贷方却整笔都在（无标签按全公司
放行）。这不是 bug，是**按部门切分录必然切不平**。

所以口径按出口分成两类：

| 一类 | 出口 | 部门 |
|------|------|------|
| 逐笔 | 凭证列表 / 导出、明细账、总账、日记账、出纳日记账、科目日报表 | **收窄**（和凭证列表同一条判定） |
| 汇总 | 科目余额表、试算平衡、资产负债表、利润表、现金流量表 | **不收窄**（公司口径） |

汇总类是公司级控制表：它必须平衡、必须是法定口径，资产科目根本不挂部门，收窄到某个
部门既不成立也没人看得懂。部门口径的损益请看「多维损益」里那一行部门。

代码上这条边界是显式的：`with_user_scope` **故意不动部门**，需要收窄的账簿再调一次
`with_dept_scope`。两个方法名并排出现的地方，就是这条边界所在。

#### 二、一条判断写三处，就用一个函数

账簿的部门条件要出现在四个 SQL 里（期初扫描、发生额扫描、明细账行集、总账聚合、日报）。
抄四遍必然漏一遍，所以收成一个 `dept_scope_cond(alias, depts, params)`：

```sql
((char(31) || e.aux_key || char(31)) NOT LIKE '%\x1fdept=%'      -- 没打标签：放行
 OR (char(31) || e.aux_key || char(31)) LIKE '%\x1fdept=D01\x1f%') -- 打了且在范围内
```

用定界符包夹而不是 `LIKE '%dept=D01%'`，是为了让 `D01` 不会误配到 `D010`。

#### 三、测试要能证明「边界没被顺手抹平」

两个变异守这条线（`tools/mutate-rust.js` ㉟）：

- **明细账不吃部门范围** → 部门会计在凭证列表看不到、明细账看得到，测试必红；
- **余额表也按部门收窄** → 借方本部门、贷方银行全公司，一张本来平的表算成不平。

第二条是我自己差点犯的错：改完第一版跑测试时，红的是 `trial_balance` 的平衡断言，
而人第一反应是「测试写错了」。所以这条变异留在了清单里。

### 4.105 多维损益：同一张表算两遍，口径一定会分叉

#### 一、先把「一个数只有一处算法」做到

多维损益原本有两套算法：`findb::mgmt::dim_profit` 出部门/客户那几行，桌面端
`views/dim_profit.rs` 自己在本地算「未分配」那一行。两处看起来一样，差别在一个参数上——
前者 `with_exclude_carry(true)`（剔除结转损益凭证），后者忘了。

后果不是数字错位，而是**这一行会凭空消失**：一期结转过，损益科目借贷相抵，未分配金额
算出来是 0，页面就只剩几个部门行。用户只会觉得「上月还有，这月没了」。

所以现在只有一个函数：`findb::mgmt::dim_profit_report(db, period, dim)` 返回

```rust
DimProfitReport { dim, rows, unallocated, total }
```

- `rows`：各维度的损益行，按利润降序；
- `unallocated`：`total − Σ rows`，为空则 `None`；
- `total`：公司口径合计。

三个字段出自**同一张快照**，恒等式 `total == Σ rows + unallocated` 在测试里钉住。桌面端
和 Web 端都调它，桌面端那个本地 `unallocated()` 已经删掉。`dim_profit()` 保留成
`Ok(dim_profit_report(..)?.rows)` 的薄壳，给还在按老签名调用的地方用。

顺手把「哪类科目算收入/成本/税金」这套前缀规则也收到一处（`bucket_of`：
`6001|6051|6301` 收入、`6401|6402` 成本、`6403|6801` 税金、其余费用）。原先这套规则在
`dim_profit` 里写一遍、在界面里再写一遍，改一处就对不上。

#### 二、末级科目：快照已经把子科目的钱上卷了

第一版按 `accounts::list()` 全表遍历，收入算出来是 2000 —— 真值 1000。原因：余额快照会把
子科目的金额上卷到父科目，`6001` 与 `600101` 各来一遍就是双份。

现在过滤条件是 `a.category.is_profit_loss() && chart.is_leaf(&a.code)`。凡是从快照里按科目
取数的统计，都要先问一句「这张表是末级还是含上卷」。

#### 三、数据范围在这张表上怎么落

「多维损益」是汇总类，按 §4.104 的口径不整体收窄；但**部门维度**是另一回事：让只授权到
D01 的会计看到 D02 那一行，等于把别人的数据范围当摆设。所以只对 `dim=dept` 调
`report.narrow_to_depts(&scope.depts)`：

- 只留授权部门那一行；
- 被藏起来的部门**并进未分配**，行名改成「未分配（含未授权部门）」，合计保持不变。

为什么并进去而不是直接丢掉：合计是利润表上人人看得到的数，丢掉别的部门行会让
「合计 ≠ 各行之和」，用户只会以为报表算错了。这里踩过一次：第一版写成「旧未分配 − 被藏
行」，得到的数是 100 而不是 500 —— 因为旧的未分配里只有「没挂部门」那部分，被藏起来的
部门行根本不在里面。正确做法是**用完剩下的行重新加回未分配**：`total − Σ(留下的行)`。

#### 四、编译警告从 262 条到 0

存量警告一直是两百多条，v1.8.60 的发布说明里就写着「还没清」。这次清完了：

- `cargo fix --workspace --all-targets` 处理了绝大多数（主要是 handler 里没用到的
  `State(state)` 参数、未用的 import、needless mut），60 秒；
- 剩下十几条手工收尾：函数体内误写的 `///`（会挂到下一个语句上，报 unused doc comment）、
  只在测试里用的 `is_ar`/`is_ap`（补 `#[cfg(test)]`）、最后一次自增后没人读的 `param_idx`、
  与 `tests/common` 重复的两个助手（删掉本地的）、`tests/common` 里「这个二进制没用到」的
  助手（按模块 `#![allow(dead_code)]`）。

为什么要清到 0：只要还挂着两百条，新写出来的那一条就混在噪音里，没人会看见。警告归零以后
「这次改动引入了警告」才是一个能立刻发现的事实。代价是以后新增一个「暂时没人用的助手」会被
拦下来——那就顺手删掉，或者写清楚为什么留着（`qa_sim` 的 `known()` 就是这么留的）。

### 4.106 受托加工的三件事：数量、单价、工件

小型氧化（来料加工）厂的现场侧有三个动作是账务系统原本接不住的：**客户的料怎么管**、
**加工费怎么算**、**工人按件拿多少钱**。三件事都做了，也都刻意**没有**动既有表结构。

#### 一、客供料台账：只记数量，不进存货

客户的料不是自己的资产：不估值、不进存货、不出凭证、不参与成本。所以客供料是**独立的两张表**
（`consign_doc` 单据头 + `consign_line` 行），用四类单据维护结存：

| 类型 | 码 | 符号 | 场景 |
| --- | --- | --- | --- |
| 来料 | `in` | + | 客户送货进厂 |
| 交货 | `out` | − | 加工完交回客户 |
| 退料 | `return` | − | 余料退回客户 |
| 损耗核销 | `loss` | − | 加工中损耗掉的部分 |

结存维度是 **客户 + 物料 + 批次**（同一物料两个批次不互相顶账）。三条规矩：

1. **减项必须先有余额**。交货/退料/损耗保存前逐行校验 `available()`，不够就报
   「现存客供料 X，本次 Y 超出可核销数量（先补登记来料）」——先出现负结存再回头查，
   是最难查的一类账。
2. **编辑要排除自身**。改一张已经存在的交货单时，本单原本占用的数量不能算进"现存"，
   否则"把 60 改成 70"会被自己的 60 拦住。`available(.., exclude_doc)` 就是干这个的。
3. **聚合在 Rust 侧做**。结存和对账单都是"取平表 → 在内存里加"，**不用 `SUM()`**：
   SQLite 的 `SUM()` 对 TEXT 存的钱会退化成浮点，一分钱的误差会一路带到对账单上。

对账单按客户 + 期间区间出，列是 期初 / 来料 / 交货 / 退料 / 损耗 / 期末，
期初 = 该客户在区间起点之前的累计结存（所以跨月账能对上）。

#### 二、加工费规则：最低收费和加急费的**顺序**是会吵起来的

按面积（㎡）报价的厂，规则里得同时放三样东西：单价、最低收费（起步价）、加急费。
实现是 `price_rule` 表 + 一个纯函数 `quote()`，顺序写死：

```
基础价 = 数量 × 单价（四舍五入到分）
补差   = max(0, 最低收费 − 基础价)      ← 先兜底
小计   = 基础价 + 补差
加急   = 固定费 + 小计 × 比例%          ← 再按兜底后的金额算比例
合计   = 小计 + 加急
```

顺序反过来（先算加急再兜底）会出现"加急费被最低收费吃掉"的情况，客户和厂里各有一套说法。
规则匹配用四级优先级：**物料+客户 > 只限物料 > 只限客户 > 通配**，同精度取先建的。
这里踩过一次：给"物料+客户"分支写了 `continue`，忘了通配兜底，结果只维护了一条通配规则时
报价直接报"没有匹配的加工费规则"——**兜底分支必须在每个精度上都可达**。

`GET /api/price-rules/quote?item=&customer=&qty=&rush=1` 只算不存，开单页可以拿它试算。

#### 三、计件工资：先补一张流水表，再谈汇总

`prod_op`（工序）存的是**累计值**：`qty_done`、`hours`、`worker`，没有期间、没有时间戳。
点一次"报工"是往上加，加完就分不出"这个月做了多少"——按期间算计件工资缺一个维度。

所以新增 `prod_op_log` 报工流水：`advanced::prod_op_report()` 在同一个事务里，
既更新 `prod_op` 的累计值，也往流水表写一条（日期取当天、期间由日期推出）。
然后：

- `piece_rate` 表存计件单价（物料 + 工序，两者不能都空——都空等于给所有人所有活定价）；
- `piecepay::compute(db, period)` 按 `prod_op_log.period` 汇总到人，无单价的行**保留**
  但 `matched=false, amount=0`（看得见"这活没定价"，而不是悄悄少一行）；
- 回填工资表走 `piece-fill`：只把**应发提上去到不低于计件额**（`gross >= amount` 就跳过），
  然后调既有的 `business::payroll_calc` 重算社保和个税，`payroll` 表结构一行没动。
  重复点不会重复加钱（幂等），因为判据是"应发是否已经够了"，不是"有没有回填过"。

顺手补的：Web 端原先**没有任何生成工序清单的入口**（只有桌面端有按钮），
所以网页上根本走不到计件这一步。现在下达生产订单时，若该存货有工艺路线就自动生成工序清单，
另给了 `POST /api/prod/:id/ops/init` 手动补建、`POST /api/prod/op/dispatch` 派工。

#### 四、这一轮踩到的测试坑

- **`Money` 序列化成 JSON 不带尾零**：`40` 不是 `40.00`、`0` 不是 `0.00`。
  API 用例里比金额要用 `money_num()` 比数值，别拿字符串直接比。
- **"只限物料"的单价不分工序**：给 MB01 定 1.5 元，MB01 换哪道工序都命中；
  想造"这行没定价"，物料和工序得**都对不上**。
- **报工流水的期间取的是当天**，所以用例里的期间要用 `Period::from_date(今天)` 算，不能写死。

### 4.107 一个功能两种界面：算钱的地方只留一处

v1.8.63 的三块受托加工功能只做了 Web 端。桌面端（`crates/finui`）里连入口都没有，
`grep 计件|客供料|加工费 crates/finui/src/` 只命中注释——同一套软件，同一个账套，
换个界面就少三个功能。这轮把桌面端补齐，顺手把「算钱」这件事的位置重新摆正。

#### 一、先算账：这段逻辑要写几遍？

「把计件额回填到工资表」在 Web 端原本是 handler 里的六十行：读旧工资行、
比应发与计件额、拼备注、调 `payroll_calc` 重算社保个税、`payroll_upsert` 写回、
记操作日志。桌面端要同样的按钮，这段就得再写一遍。

两遍的代价不是六十行字，而是**口径漂移**：某天发现"应发等于计件额时也该更新备注"，
改了 Web 忘了桌面，于是同一个账套在网页上算出 150.00、在客户端算出 150.00 但备注不同——
再往上就是对不上账的凭证。所以把它抽进数据层：

```rust
piecepay::fill_one(db, period, &pay) -> DbResult<Option<PieceFill>>
```

返回值 `None` 就是"不用动"（应发已不低于计件额），这是**唯一**的判据，
也就成了回填幂等的依据——不是"有没有回填过"这种需要额外状态的说法。

留在上层的只有两件与算钱无关的事：

- **权限**：`piece_fill` 要 `Perm::VoucherNew`；
- **数据范围**：看不见的部门/人不改写工资表（`doc_in_scope` + `allows_dept`）。

「谁能看」属于边界，「怎么算」属于数据层，两者混在一起写，就一定会出现
"界面上看不见这个人，但回填把他工资改了"这种最难查的问题。

#### 二、E2E 只判 toast 等于没判

客供料"超交要被拦下"这条，接口层已经有用例。到了界面层，最省事的写法是点保存、
断言 `#toast` 里有「超出可核销数量」。**这条断言守不住真 bug**：
报错提示只要弹出来就够了，单据到底有没有落库它不管——而"提示报错但单据已经存进去"
恰恰是这类表单最典型的失效形态（校验在写库之后才做，或者事务没回滚）。

所以那条用例同时断言列表条数：

```js
await expect(page.locator("#toast")).toContainText("超出可核销数量");
await page.click("#cs-load");
await expect(page.locator("#cs-docs tbody tr")).toHaveCount(2); // 还是 2 张，没多出一张
```

同一条用例里也顺手写了结存的两次断言（100 → 交货 60 → 40），
因为"单据存了、结存没动"是另一种失效，只判单据表看不出来。

#### 三、桌面端怎么补：列表 + 录入 + 删除，算术一律外包

三个界面（`crates/finui/src/views/process.rs`）都只做三件事：
查出来、摆成表、把用户填的东西交给 `findb`。报价不自己在界面里算
（`数量 × 单价 → 最低收费兜底 → 加急`三步顺序一错就差钱），直接调
`processfee::quote_by()` 把拆解结果原样显示：

```
规则「氧化-普通」：12.5 ㎡ × 18 = 225
不足最低收费 30，补差 21
加急：固定 20 + 比例 10%（合计 42.5）
合计 267.50
```

删除一律走统一确认框（`ConfirmAction::DeleteConsignDoc / DeletePriceRule / DeletePieceRate`），
不是随手一个"删"——客供料单据删了结存跟着变，且单据不占期间结账，删错只能重登。

#### 四、诚实说明覆盖到哪

容器里装不上 Chromium（`npx playwright install chromium` 在这里下载失败），
所以新写的 `e2e/tests/process-extra.spec.js` 只能由 CI 复核，本地跑不了。
为了把 CI 往返的成本压到最低，三条用例里只在**被测的那一层**点真按钮：

- 客供料、加工费：全程点界面（这两块的失效形态在表单）；
- 计件：工艺路线、生产订单、派工、报工全部走接口造前置数据（那是四步表单，
  UI 层的失败信号对"计件汇总对不对"没有信息量），界面只点"算计件 → 回填"。
