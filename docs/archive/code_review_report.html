总体结论

工程底线是扎实的：金额全链路使用定点 Decimal（无 f64 入账）；SQL 全部参数化（未发现任何 SQL 注入面）；口令采用 argon2id + 每用户随机盐，并在登录时透明升级旧哈希；会话令牌为 128-bit 加密随机；凭证落库有「界面 + validate_for_save 持久层」双重校验；复式记账借贷平衡、期末损益结转方向、折旧尾差拉平等核心逻辑正确。

最需要警惕的风险集中在「授权完整性」与「账务口径」两处：Web 层做了「仅本人凭证」的数据范围设计，却在所有凭证读写接口里完全没有落地（IORD）；凭证删除与反审核存在缺守卫 / 缺权限的越权路径；核销与资产负债表的备抵科目各有一处「算错钱 / 虚增资产」的正确性缺陷。此外，首次登录即获管理员的初始化流程叠加默认全网卡明文监听，构成部署即被接管的现实风险。

判定：作为原型 / 内网单机财务工具可用且质量中上；但在修掉下述高危项之前，不建议暴露到不可信网络或用于真实多用户核算。修复优先级见文末路线图。

二、严重问题 1 项

可能导致系统在部署/初始化阶段即被完全接管的问题。

CRIT

首次登录者自动成为管理员，叠加默认全网卡明文监听 → 部署即被接管

finweb/src/handlers.rs:146-163 · findb/src/users.rs:188-206 · finweb/src/main.rs:23,68-70
安全权限提升初始化竞争

账套用户数为 0 时，任何人第一次调用 /api/login 即用其提交的用户名+口令直接建为管理员（仅要求口令 ≥6 位，绕过 PasswordPolicy，且 must_change_pwd=false）。同时服务默认监听 0.0.0.0:8080、纯 HTTP，启动日志还印出「首次登录的账号将自动成为管理员」。未初始化完成的账套一旦暴露到网络，攻击者可抢先完成首登，成为系统管理员并完全接管账套。

// handlers.rs
if count == 0 {
    if username.is_empty() || req.password.len() < 6 { /* 仅长度校验 */ }
    users::create_admin(&db, &username, &req.password, &username)?; // 直接 Role::Admin
}
// users.rs create_admin: must_change_pwd = false

修复：默认监听改为 127.0.0.1；首次建账收口为一次性初始化流程（本地回环 / 一次性 token / 环境变量设定管理员）；管理员口令必须通过 policy.check 并强制 must_change_pwd=true；部署层强制 HTTPS。

三、高危 — 安全与越权 7 项

已登录用户可越权查看 / 篡改他人或全盘数据的授权缺口。

HIGH

Web 层完全未执行「仅本人凭证」数据范围 → 任何会计角色可全盘查看/改/删凭证（IDOR）

finweb/src/handlers.rs:527-560 (list) · 562-574 (get) · 628-647 (edit) · 752-762 (delete)
越权IDOR失效访问控制

建号时对非管理员设置了 data_scope.own_voucher_only = true（注释明确「防越权翻看他人/全盘数据」），但在 Web 层该字段从未被读取：凭证列表/详情/编辑/删除均按裸 Path(id) 或 VoucherQuery::default() 处理，从未调用已实现的 with_data_scope / can_see_voucher。后果：拥有 VoucherEdit/VoucherDelete 的普通「会计」账号可读取、修改、删除全账套凭证。

// handlers.rs:536 —— 未应用数据范围
let mut query = VoucherQuery::default(); query.asc = true;
let list = vouchers::list(&db, &query)?;  // 缺少 .with_data_scope(&user.user)

修复：list 用 query.with_data_scope(&user.user)；get/edit/delete 取回后校验 user.user.can_see_voucher(&v)，不满足返回 403。

HIGH

voucher_unaudit 无任何权限校验，且语义错误（任意登录用户可退审他人凭证）

finweb/src/handlers.rs:735-750
越权缺失鉴权状态机

该处理函数全程无 user.require(...)（对比同组 voucher_audit 有 Perm::VoucherAudit、voucher_delete 有 Perm::VoucherDelete，这是唯一缺口）。更糟的是逻辑：注释写「取消记账」，却调用 vouchers::unaudit（要求状态为 Audited），而「取消记账」应调用 vouchers::unpost（Posted→Audited）。

async fn voucher_unaudit(...) -> ... {
    if v.status == VoucherStatus::Posted {
        vouchers::unaudit(&db, id)?;   // 无权限校验；且 unaudit 只接受 Audited
    }
}

修复：函数开头补 user.require(Perm::VoucherAudit)?（或按语义改 VoucherUnpost 并调用 unpost），并明确该接口到底做「反审核」还是「反记账」。

HIGH

凭证删除持久层无守卫，validate_delete 全仓库零调用

findb/src/vouchers.rs:392-396 · fincore/src/engine/validate.rs:275-286 · finui/src/lib.rs:82
数据完整性死代码防线

vouchers::delete 是裸 DELETE FROM voucher WHERE id=?，不校验状态、不校验结账期间、不校验所有权——与同文件 save/audit/post/unpost/set_void「持久层最后防线」的自述相矛盾。已实现、本应拦截「已记账不能删 / 已结账期间不能删」的 validate_delete 从未被调用。Web（handlers.rs:759）与桌面端（finui/lib.rs:82）均直删。后果：有 VoucherDelete 权限者（或桌面端）可删除已记账 / 已结账期间 / 他人的凭证。

修复：在 delete 内先 get 再 validate_delete，或由两个调用方显式校验 status/closed 后再删。

HIGH

prepared_by 身份字段三种口径并存，导致数据权限与「制单人/审核人分离」失效

finui/src/views/voucher_edit.rs:188,397 · finweb/src/handlers.rs:666 · findb/src/vouchers.rs:64-71 · fincore/src/user.rs:410
一致性数据权限

同一字段四处用三种口径：桌面端存 display_name、Web 端存 username、with_data_scope 按 display_name 过滤、can_see_voucher 按 username 比较。当 display_name != username 时，桌面端 own_voucher_only 用户把自己凭证全被过滤掉（看不到自己的凭证）；两终端交替访问时过滤进一步错乱。显示名不唯一、可改，还造成同显示名用户互相可见。

修复：全项目统一 prepared_by 只存唯一不可变的 username，两处过滤都按 username 比较。

HIGH

DataScope 默认全放行 + can_see_voucher 忽略部门维度 + 科目区间「任一命中即放行」

fincore/src/user.rs:184-193 · 408-421
默认放行越区泄漏

DataScope::default() 全空 → is_unrestricted()==true，收敛依赖外部建号逻辑事后补设置，一旦遗漏则普通用户默认可见全盘。且 can_see_voucher 只判断 own_voucher_only 与科目区间，完全忽略 scope.depts；科目区间过滤用 entries.any(允许)，凭证只要有一条分录在范围内整张可见，超出范围科目的金额随之外泄。

修复：非 Admin 账号在 User::new 默认 own_voucher_only=true；can_see_voucher 增加部门校验；科目范围改「全部分录均在范围内」或对范围外分录脱敏。

HIGH

must_change_pwd（强制改密）仅前端约束，后端照发全量会话、逐请求不拦截

finweb/src/handlers.rs:170-185 · finweb/src/state.rs:334-375 · findb/src/security.rs:214-235
策略执行不完整会话

登录返回 MustChangePassword(u) 时，post_login 仍用 u 创建会话并下发 Cookie（Ok(u) | MustChangePassword(u) 同分支）；CurrentUser 提取器只校验 disabled 与 device_id，从不校验 must_change_pwd。知道旧口令者拿到有效令牌后可直接调用业务接口，绕开「管理员重置后必须立即改密」。

修复：must_change_pwd 时仅签发受限会话；提取器中拦截除 /api/change-password、/api/logout、/api/me 外的请求。

HIGH

会话 Cookie 缺 Secure 标志，配合默认明文 HTTP，令牌可被窃听重放

finweb/src/state.rs:438-444 · finweb/src/main.rs:23,68
会话安全传输层

Cookie 只设 HttpOnly; SameSite=Lax; Max-Age，无 Secure，而默认监听 http://0.0.0.0:8080。令牌（128-bit 加密随机，本身安全）在网络明文传输，可被同网段窃听重放至上限 7 天，取得完整权限。

format!("finbook_sid={}; Path=/; HttpOnly; SameSite=Lax; Max-Age={}", token, max_age_secs)

修复：生产强制走 HTTPS 反代并给 Cookie 加 Secure；或至少默认绑定回环地址并对局域网风险文档化。

四、高危 — 账务正确性 4 项

会直接导致金额算错或报表失真的缺陷。

HIGH

资产负债表坏账准备 / 存货跌价准备 .neg() 方向错误，资产被高估 2 倍备抵

fincore/src/report/balance_sheet.rs:45 · 81
报表符号约定虚增资产

坏账准备(1231)、存货跌价准备(1471) 是贷方余额的备抵科目，在全引擎「正=借、负=贷」约定下其 End 取数本就是负数。模板却用 .neg() 把符号翻正，结果把准备加回资产。对照同表「固定资产」累计折旧(1602)/减值(1603) 是「不加 .neg() 靠负号自然冲减」，说明这两处 .neg() 属笔误。

Term::acct(&["1231"], AmountKind::End).neg(),   // 应收账款——坏账准备，负号被翻转
Term::acct(&["1471"], AmountKind::End).neg(),   // 存货——跌价准备

修复：去掉这两个 .neg()（负号本身即代表「减」）。收入/费用表的 PeriodDebit/PeriodCredit 是非负发生额，其 neg() 语义正确、勿动。

HIGH

往来核销在 SQL 侧对 TEXT 金额做加法 + 千分位存储 → 直接算错金额

findb/src/settle.rs:169-185
金额精度SQL 算术

settle() 用 ON CONFLICT ... DO UPDATE SET amount=amount+excluded.amount 让 SQLite 对 TEXT 金额列做加法，插入参数却用 amount.to_string()（Display 带千分位）。金额 ≥1000 时存成 "1,000.00"，SQLite 算术到逗号截断为 1，同一对分录再次核销得到错误累计；即便 <1000，TEXT 相加也走 REAL 引入浮点误差。

// settle.rs:173
ON CONFLICT(from_entry,to_entry) DO UPDATE SET amount=amount+excluded.amount
// settle.rs:180 —— 带千分位的字符串
amount.to_string(),

修复：不要在 SQL 里做金额加法；先读回、在 Rust 侧用 Money 累加后写回；金额统一用无千分位的 money_param/fmt_plain 落库。

HIGH

余额 / 账簿 / 报表只排除作废凭证，未排除「未审核、未记账」凭证

findb/src/balances.rs:167-171,586,592,674 · vouchers.rs:719 · reports.rs:177 · bank.rs:188
账务口径状态机

模块文档写「余额 = 期初 + 已记账凭证发生额」，但 SQL 统一是 WHERE v.status != 'void'，即草稿、已审核未记账也全部计入科目余额/试算平衡/明细账/总账/现金流量。与之呼应，LedgerQuery.posted_only 字段因此完全失效；counts() 对 Draft 也返回 true、can_edit() 对 Posted 返回 true，状态机边界不严谨（记成 Posted 后修改金额不会强制重新过账）。

-- balances.rs:170
WHERE v.status != 'void' AND e.period <= ?1

修复：明确「记账是否构成余额边界」的产品决策后，统一余额/账簿/报表过滤为 v.status = 'posted'（至少让 posted_only 生效），并同步修正注释与 counts/can_edit 语义。

HIGH

业务凭证生成与单据回写不在同一事务 → 部分提交并催生重复凭证

findb/src/business.rs:1073-1075 · 287-293 · 611-617
事务边界幂等

claim_voucher/stock_cost_voucher/payroll_accrue_voucher 里，vouchers::save() 内部自行 commit 后，回写 voucher_id 的 UPDATE 是另一独立写。若回写失败：凭证已入库但单据未关联；claim_voucher 靠 voucher_id.is_some() 防重，失败后重试会再生成一张凭证。

修复：把「生成凭证 + 回写单据/流水」包进同一事务（或让 save 接受外部事务句柄）。

五、中危问题 18 项

加固项、数据完整性与若干认证/口令流程缺陷。

MED

登录响应可枚举用户名（与注释意图相反）

findb/src/security.rs:163-168 · finweb/src/handlers.rs:187-197
信息泄露

不存在用户返回 401「用户不存在」，存在用户口令错误返回 400「口令错误，还剩 N 次」，状态码与文案均不同，构成用户名枚举 oracle。

修复：两种失败统一返回 401 与同一文案；剩余次数仅对已认证上下文显示。

MED

登录失败仅按用户名锁定，无按 IP 限流

findb/src/security.rs:177-187
暴力破解

失败计数与锁定都 key 在 username 上，不记录来源 IP，攻击者轮换大量用户名可无节流撞库，锁定机制对分布式字典攻击失效。

修复：Web 层按 IP 增加失败计数与延时（固定窗口限流），失败响应加线性退避。

MED

锁定失败计数窗口单位错误：lock_minutes×60 → 15 分钟锁定时长变成 15 小时窗口

findb/src/security.rs:180
正确性

recent_fails(db, username, policy.lock_minutes.max(1) * 60) 把「分钟数×60」传给按分钟解释的 recent_fails，使默认失败窗口变成 900 分钟。相隔数小时的 5 次失误也会触发锁定，属过度锁定。

修复：失败窗口用独立常量（如 10~15 分钟），与锁定时长解耦。

MED

设备绑定（一人一机）完全信任客户端自报 device_id，无服务端核验

finweb/src/handlers.rs:165,175 · findb/src/security.rs:192-207 · finweb/src/state.rs:361-366
可欺骗软控制

请求体里的任意字符串直接作为 device_id 参与首次绑定与后续比对，全程无服务端生成/签名/挑战。拿到口令者可自报目标设备 machine-id 编造指纹，或新设备首登时把自己绑成唯一合法设备。

修复：登录时下发随机 challenge，客户端用本机密钥签名；或绑定改管理员显式审批。

MED

附件上传无大小上限、整文件读入内存、无 MIME/扩展名校验

findb/src/attach.rs:158-201
资源耗尽上传

INLINE_LIMIT 只是内存/外存分界并非上限；add_file 用 std::fs::read 整读入内存；kind 仅取原始文件名扩展名，不校验 MIME。可致磁盘/内存耗尽，任意扩展名落盘。

修复：设最大大小（如 20MB）并在读取前 metadata().len() 校验；限定白名单扩展名；大文件流式写入。

MED

附件读取/删除/导出路径用 join/push 拼接，未做规范化（潜在路径穿越）

findb/src/attach.rs:139-148 · 204-212 · 352-357
路径穿越

read/delete 用 dir_of(db).join(rel)，rel 取自 DB 的 path 列；temp_export_path 用 push("stamp_name") 把用户可控附件名拼进路径。若 path 列被污染或附件名含分隔符，可读写附件目录之外。

修复：对 rel/name 拒绝含 \ / .. 与绝对路径前缀的内容；或只取 file_name() 并断言父目录等于 base。

MED

数据导入不在事务中，中途失败留下半套数据

findb/src/imports.rs:465-529 · 568-656
事务数据完整性

每行/每张凭证的 upsert/save 各自独立提交，整个导入无外层事务；第 N 条违反约束时前 N-1 条已落库且只体现在 warnings，难以回滚。

修复：用 unchecked_transaction() 包住整个 import_*，全部成功再 commit。

MED

桌面端管理员重置口令走弱校验路径，绕过口令策略且不强制改密

findb/src/users.rs:246-251 · finui/src/views/users.rs:236
口令策略

reset_password 不调 policy.check、不设 must_change_pwd；change_password 仅校验「至少 6 位」。与管理端 security::admin_reset_password 的完整校验行为不一致，管理员可设 123 这类弱口令且用户不被强制修改。

修复：桌面端统一改调 security::admin_reset_password / change_password_checked。

MED

未认证接口泄露账套文件绝对路径与公司信息

finweb/src/handlers.rs:110 · 124
信息泄露

/api/setup/status 与 /api/books 无需登录即返回账套 SQLite 文件全路径及公司名，向未认证访问者暴露服务器目录结构。

修复：去掉 path 字段（前端不需要），或要求该接口已登录。

MED

argon2 失败静默降级为弱式 SHA-256 + 时间种子 LCG 盐

fincore/src/user.rs:439-447 · 477-512
口令密码学

argon2id 参数达标（符合 OWASP），但 hash_password 失败时 unwrap_or_else(|_| legacy_hash_password) 静默降级为 salt$sha256，且 random_hex 用 SystemTime 做种子的 LCG（可预测盐），而它正是 legacy 盐来源。

修复：兜底改为返回错误（或重试），绝不让新哈希走非 argon2 路径；盐一律 OsRng。

MED

借贷平衡按 2 位小数判定，容忍亚分位差额；Web 端非法金额静默转 0

fincore/src/voucher.rs:393-395 · fincore/src/engine/validate.rs:90-97 · finweb/src/state.rs:469-474
金额精度静默兜底

balanced() = diff().round2().is_zero()，借方 100.004 vs 贷方 100.002 差额 0.002 会被判平衡入库；且 Money::parse 接受任意位小数未规约到 2 位。Web 层 parse_money 解析失败静默返回 ZERO，"12.34.56"/"abc" 被当 0，配合可保存「借贷全 0」凭证。

修复：平衡判定用全精度 diff().is_zero()，或入账前强制每条分录 ≤2 位小数；Web 层金额解析失败返回 400 而非归零。

MED

导入 parse_money 丢弃 Unicode 负号、非法金额静默记 0

findb/src/imports.rs:270-277
